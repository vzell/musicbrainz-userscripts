sl-song (proposed)

  • @include lyrics.php?song=… and ?item=N; tableMode: 'multi'; no request (fetchText = the page itself, as the sl-*-item PTs).
  • Head: byline from the <em> version line through _slLyricsParseVersion(), so Type, Date and Show match the index.
  • Each .blog-post row: the line Artist -- Title, then FORMAT - LABEL (CAT#) - COUNTRY, YEAR. The rest goes to Note; track lines become a nested tracklist.
  • Live releases: one sentence per row, "The live date version … was released on release kind in year". A row that does not fit keeps its sentence in Note.
  • Album panels (.panel-group): one sub-table per edition. Sides pair into records (answer 4 of the item pages); the site's "Disc 5:" inside a list of sides counts as a side.
  • Private Info: a closed section, logged in only, never in a card. Same rule as the item pages.

What a live version adds

  • The date comes from the version line (and the slug _1975-11-18) through the index's own reader, so DD/MM/YYYY/Day match the lyrics index.
  • The page has no card for the venue: it is only in prose. The Show card reads it best-effort and stays empty when the sentence reads otherwise.
  • The release section is named after the release (an <em> heading). Its three panels become one sub-table per edition, with the CD's "Disc 1:/Disc 2:" as two.
  • A song without a page of its own is plain text in the list (<li>SHE'S THE ONE</li>). Song links are left to the "URLify the tracklist" TODO.
  • The site's vinyl list has "Disc 5:" among "Side 1:" to "Side 8:". It is read as side 5.

One reader, two uses

  • The card and window use _dpParseSlSong(), which reads the song page. The page view would use the same reader, so both show the same facts (the pattern of _slParseTracklist()).
  • A change in what the reader returns bumps _DP_PARSER_VERSION (now 10).
  • From MusicBrainz the card is the PUBLIC page (anonymous request): no song number, no cover-release links.
  • The window's "Live page" view shows the site's own page in a frame. Logged in on SL, that page still includes Private Info: see question 7.

Where the links sit on a MusicBrainz page, and whether a hover reaches them

  • Relationships and the sidebar's external links: table.details and ul.external_links are in _EXT_SCOPE_SEL. Yes.
  • An entity's annotation: .annotation a[href] is in _EXT_SCOPE_SEL. Yes. Pinned by the U4 spec and by today's new spec, which covers every form above.
  • The Annotation column of our tables: table.tbl > tbody a[href]. Yes, clones included (the selector is read at every event).
  • An annotation inside an MB entity window: links a reader takes open in the window (_DP_WIN_ALL_LINKS_SOURCES; the springsteen reader is in _DP_WIN_EXT_READERS). Yes.
  • A bare URL in annotation text: MusicBrainz's wiki formatting turns it into a link, so it is covered as above.

So item 5 is mostly there

  • Every live SL form MusicBrainz uses already gets SL's own card, read anonymously (curl got 200 with no Cloudflare check today).
  • The real gap is the two old forms, 453 links in the sample, nearly all in work annotations. Today their card says the page was not found.
  • Proposal: an alias step in the springsteen reader that reads the current address, plus a line in the card: "old address; the site now serves this at …".
