● All fixes are implemented, verified against the real page, and stable across repeated runs. Summary of what happened:

  Root causes found (more precise than my initial hypothesis — verified line-by-line against the actual code):
  1. A input[type="text"] vs input[type="search"] selector bug, present in 14 places. The real sub-table-filter (STF) input's type is forced to "search" by an autofill-hardening call, so every STF-active check using the wrong selector was silently dead — including the internal
     "reapply STF after a re-render" mechanism (reapplyAllSubTableFilters(), which never fired at all) and the h3 "Clear all filters" button visibility check.
  2. First-render row aliasing: the very first render of a multi-table page inserted row elements by reference instead of cloning them, while every later filter/sort re-render already cloned. STF's own row-hiding mutated those live rows in place, and once a sort triggered a
     rebuild from that now-contaminated canonical array, the contamination became permanent — explaining the "stuck forever, no way back" clear-button bug.
  3. The CAA "big picture" stripe/badge revert was a separate, narrower issue: the full rebuild pass that follows any re-render was blind to STF-hidden rows.

  Fixes (all in ShowAllEntityData.user.js, on branch fix/multi-table-sort-filter-caa):
  - New _getStfInput()/_getAllStfInputs() helpers, replacing all 14 broken selector call sites.
  - CAA/EAA bigbox wrappers now start hidden for STF-filtered-out rows (rather than being skipped entirely, which I initially tried — that broke the global badge's page-wide-total semantics, caught by the live test and corrected).
  - Row insertion on first render now clones, matching every later re-render.
  - STF filters are now reapplied synchronously inside renderGroupedTable() itself, before the CAA rebuild — replacing the dead debounced mechanism (deleted).
  - A defense-in-depth guard so a late-arriving image load can't creep a per-table badge count back up.

  Testing: new tests/live/subtable-filter-sort-caa-interaction.spec.js (using real CAA network access, per the .org file's requirement) reproduced all 3 reported bugs pre-fix, and now passes post-fix — run twice for stability. All 17 existing @core/@extended live specs and the

** a

● Good question — let's take these one at a time.

  1. Sort order persisting across views — this IS the designed behavior

  _resetDiscographyViewState() explicitly resets the global filter, column filters, STF filters, sort UI indicators (glyph highlighting, sort-status text), and collapse state on every view switch — but it never resets groupedRows[idx].rows's actual array order. A sort mutates
  that array in place (targetGroup.rows = sortedData) and nothing ever un-sorts it back. So every subsequent render (including the ones triggered by a view switch) rebuilds each table's rows from that still-sorted array, faithfully reproducing the sort order.

  For the merged view specifically, there's a dedicated mechanism for this: mergedSortComparatorRegistry (registered once per table by makeTableSortableUnified, line 50530). When rows from multiple same-named groups get combined into one table, _applyDiscographyViewFilter()
  (lines 45093-45106) explicitly re-sorts the combined set using whichever comparator is currently registered for the first-occurrence table — "Without this, switching into merged view on an already-sorted table would show non-first-occurrence contributors' rows in their original
  concatenation order instead of the active sort" (its own comment). This is why your merged view's 23 rows stayed correctly sorted even though they came from two different source tables.

  So: no, nothing should reset the sort order across a view switch, and nothing does. This matches what you observed and is intentional.

  2. The stuck orange header — this is a real, confirmed defect

  I traced this precisely. makeTableSortableUnified() — the function that builds the multi-sort tint classes (mb-mscol-hdr-0, amber, applied to the <th>) and registers the closures that can clear them (multiSortTintRegistry) — is only ever called once, on a table's very first
  render. Every render after that (sort, filter, or a discography-view switch) goes through the "reuse" branch, which explicitly does not call it again — confirmed by the code's own comment at line 43556-43559: "re-apply any active multi-sort tints... covers the
  reuse-existing-table branch (query truthy) where makeTableSortableUnified is NOT called, so the trailing restore block never fires."

  That reuse-branch workaround only re-applies a tint (via multiSortTintRegistry.get(tintKey).applyTints()) — it never registers a new closure. Meanwhile _resetDiscographyViewState()'s step 5d does multiSortTintRegistry.clear() unconditionally, on every view switch. Since nothing
  ever repopulates that registry entry afterward, this table's tint-clearing capability is destroyed the moment you switch views — permanently. That's exactly why it "stays like this whatever switch we do from now on."

  Two separate, independent visual systems represent "this column is sorted": the glyph's sort-icon-active class (cleared correctly, every time, by _resetDiscographyViewState() step 5b — hence the glyphs losing their highlight, as you noticed) and the header's mb-mscol-hdr-0 tint
  class (governed by the fragile, one-shot registry above). They're not kept in sync, which is why you end up with an inconsistent state: glyphs say "nothing sorted," header background says otherwise.

  What I haven't pinned down with full certainty is whether step 5a's own clearTints() attempt (which runs once, right before the registry gets wiped) actually throws on that first switch (its try/catch explicitly anticipates failure — "table may be mid-rebuild" — silently
  swallowed, no log) or simply doesn't fire for some other reason. Confirming that exactly would need a live breakpoint/console check rather than static reading. Either way, it doesn't change the core finding: this is a structurally one-shot cleanup mechanism with no way to retry
  or recover once the registry entry is gone — a real bug, independent of the STF fix, and unrelated to the row-aliasing question you originally asked me to check.
