Done with Part 1. Here's where things stand.

The bug is fixed and the fix is verified. Root cause was an asymmetry I hadn't expected to find documented elsewhere in the file: renderFinalTable moves the rows it's handed, so on single-table pages the Picard <td> lands on the source rows for free — but renderGroupedTable always clones, including on the first render. So groupedRows[i].rows never got the cell, and every re-render cloned blank rows. The code's own comment asserted the opposite, which is why it went unnoticed; the artwork code states the same fact correctly right next door.

Two things worth flagging that changed my understanding of your report:

- It wasn't sort-specific. runFilter's multi branch re-clones every group, so the column emptied page-wide on the first filter keystroke. Your snapshot showed one affected sub-table only because the scoped-sort path had narrowed that particular render.
- The mirror had to clone the built cell, not rebuild it. _picardExtractRowEntities skips .mb-sticky-col, and only live rows carry that class. On your page td[0] (sticky) and td[18] both hold /release/76415396-…, so rebuilding on the master row would have harvested the other cell — same release, different tooltip text.

Perf, per the gate you approved: restoring the cells means multi-table keystrokes rebuild them again. Smaller than the review claimed, though — _picardExtractRowEntities was already the unconditional first line, so the expensive per-row anchor walk was always being paid; only the DOM construction is new. The _mbPicardWired marker means a scoped sub-table sort now pays only for the group it sorted.

I also fixed four adjacent defects the change would otherwise have made worse — most importantly the discography-view path, which re-clones rows without going through renderGroupedTable and would have started serving inert ♪ buttons instead of missing ones.
