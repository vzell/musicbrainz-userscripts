* picard

Session notes for the Picard-column work. Part 1 shipped in *9.99.1056* and
Part 2 in *9.99.1057*; both are done, and Part 2's full plan is kept below as
the design record — see the deltas under its own heading before following it.

The three questions this started from:

1. What exactly would happen when implementing "Step 23: Convert the
   re-wire-after-clone family to event delegation"?
2. A bug on multi-table pageTypes, e.g.
   https://musicbrainz.org/release-group/c497fc44-ddaf-3cce-a9b4-bfec958a0f3c —
   initially the Picard column shows the right glyph "♪" in e.g. the sub-table
   "Official release", but as soon as a sorting/filtering is done on that
   sub-table the glyph is not rendered anymore. See ~debug/picard-missing.html~.
3. Can we implement in the "Picard" column header, like in the "Length" column
   (e.g. https://musicbrainz.org/release/3ec14d03-2c03-4764-a69d-8155817a040f),
   a collapse/uncollapse picard glyph which only renders the picard data cell
   "♪" when an end-user clicks it?

** Answered — question 1 (Step 23)

Not implemented, and no work planned. The findings are recorded where they
belong rather than here: ~PERFORMANCE.org~ Step 32 has the ordering decision
against Step 23, and Step 32's own "What was accepted and built" subsection
(it was titled "A NARROWER design was accepted" while it was still an
addendum) plus Step 23's "Three corrections found while fixing the Picard
multi-table clone bug" carry the rest — the roster is 7 functions not 4,
~initAnnotationCompareRadios()~ cannot be fixed by delegation at all,
~_cdtocInitTracklistToggles()~ yields nothing, and the real prize is the
~_colHeaderCountsCache~ drop.

/Updated 2026-09-10:/ that last point said the drop was something "the current
perf harness structurally cannot see (~artist-events~ has no ~/release/~
links)". True at the time, no longer: ~artist-releases-dylan~ was instrumented
for exactly this, and the drop is now measured — the ~expanded~ arm pays 1.26x
on ~headerCountsRestore~ against a ~collapsed~ arm that is within 1.01x of
having no Picard column at all. See ~PERFORMANCE.org~ Step 32's "MEASURED"
subsection and ~tests/MEASUREMENTS.org~.

** DONE — question 2, shipped in 9.99.1056

Root cause, fix, the four adjacent defects it also fixed, and the verification
are all in ~DEBUG-NOTES.md~ under *## 2026-09-10 — Picard column emptied on
every multi-table re-render (fixed)*. Read that, not a summary.

The one-line version: ~renderFinalTable~ MOVES the rows it is handed while
~renderGroupedTable~ ALWAYS CLONES, so in ~tableMode: 'multi'~ the Picard
~<td>~ only ever landed on the rendered clones and ~groupedRows[i].rows~ never
received it. That asymmetry is now written up in ~CLAUDE.md~'s "Common

** DONE — question 3: per-sub-table ▶♪/▼♪ header toggle

Built on branch ~picard-column-collapse-toggle~, shipping as *9.99.1057*.
The plan below is kept as the design record; read it with the following
deltas, and read ~DEBUG-NOTES.md~'s *## 2026-09-10 — Picard column: on-demand
▶♪/▼♪ header toggle* entry for the full account.

*Where the plan was wrong.* The master-row mirroring is NOT load-bearing for
correctness. "If collapse only emptied the live cells, the next re-render would
clone still-populated masters and the column would silently re-appear while the
header read collapsed" — measured by mutation, and it does not happen:
~_picardApplyToRow()~ reconciles every freshly-cloned cell against its table's
state on every pass, so the live DOM ends up right either way. The mirror is
kept for what it does buy (masters and live rows never disagree; a collapsed
column stops cloning subtrees it will discard, which on a large table is a
large part of the cost this feature removes), and its JSDoc now says that
instead.

*What the plan did not anticipate.* ~_cleanColHeaderText()~'s step-3 strip
selector was missing ~.mb-col-collapse-hdr-btn~, so once the Picard column had
multi-row cells that header resolved as ~"Picard▶3▤"~ —
~initCollapsableColumns()~ appends its own button DIRECTLY to this ~<th>~ (the
no-flex fallback branch, and Picard's is the only such header). Latent, not
live, and fixed in the same pass. Found by the mutation run, from a completely
unrelated direction.

*Two plan items deliberately not done, with reasons.* The three snapshot
baselines were NOT re-captured — it needs a logged-in session
(~npm run auth:login~) and the saved one had expired; the exact expected
numbers are recorded in ~tests/snapshots/registry.org~'s "Expected drift"
instead. And nothing was added to ~tests/MEASUREMENTS.org~, because nothing was
timed: the perf harness's only instrumented page is ~artist-events~, which has
no ~/release/~ links and therefore no Picard column at all, so the measurement
~PERFORMANCE.org~ Step 32 keeps prescribing still cannot be taken without an
instrumented release-listing page.

*One plan URL was simply wrong.* The "Verification" section names
https://musicbrainz.org/release/3ec14d03-2c03-4764-a69d-8155817a040f as the
single-table page to check. It *has no Picard column at all* — verified against
the live page — because the guard asks whether a table's tbody links a
~/release/<mbid>~ and a release TRACKLIST's rows link RECORDINGS. Correct and
pre-existing; the plan's mention of that URL was about the ⏱ Length toggle's
precedent, not about Picard. ~series-releases~
(https://musicbrainz.org/series/aa3694d3-a3d0-48ed-8f07-5b576de87908) is the
single-table pageType that does carry the column, and it is what
~tests/live/picard-header-toggle.spec.js~ uses.

*One thing the plan did not ask for and got anyway.* That live spec —
~@extended~, 2 tests, one per table mode, registered in
~tests/live/registry.org~. The plan's verification step said "then manually
on …", and a live spec is the reviewable, re-runnable form of exactly that.
Both tests pass.

*Everything else in the plan below was implemented as written*, including the
~__saTest~ hook it only suggested considering (~picardEntityScans()~), which
turned out to be the only way to pin the gate at all.

*** Decisions already taken with the user — do not re-litigate

- *Scope: PER SUB-TABLE.* Each table's header button toggles only its own
  cells. Follow ~_artInitCaaColHeaderToggle~ (grep ~mb-caa-col-hdr-btn~), not
  ~_msRepaintColHdrBtns~'s page-wide repaint. Add the page-wide companion
  following ~_artInitGlobalCaaColHdrToggle~.
- *ONE setting, default ~true~, and ~true~ means the column renders
  COLLAPSED.* So on the final rendered page the Picard header shows the
  collapsed glyph (~▶♪~) and every Picard ~<td>~ is empty until the user
  presses it.
- *The toggle itself is always present*, independent of that setting — the
  setting decides only the STARTING state, exactly as ~*_initially_collapsed~
  reads elsewhere. Consequence worth stating in the setting's own description:
  turning it off reproduces the pre-9.99.1057 behaviour exactly (cells built at
  render) while keeping the toggle available. This is the reading of "make the
  feature configurable (default: true)" that was implemented; the alternative —
  a hard feature on/off that removes the button entirely — was not, because the
  always-present button is what the ⏱ and 🖼 precedents both do.
- *Part 2 depends on Part 1 having shipped*, which it has. A toggle that fills
  cells on demand is meaningless while the next sort destroys them.

*** Why this is NOT what PERFORMANCE.org Step 32 deferred

Read Step 32's "What was accepted and built: defer the CELL CONTENT, never
the column" subsection first — it is the authority and it already carries the
argument. (It was titled "A NARROWER design was accepted" while it was still
an addendum; folding it into the body was itself one of this plan's own docs
items.) Short form: Step 32 rejected
inserting/removing a COLUMN at runtime because the column count is what every
index churns off. Here the ~<th>~ and every ~<td>~ always exist and only the
cell CONTENT is deferred, so no index moves and
~addColumnFilterRow~'s ghost-cell path still runs exactly once.

*** Where the state lives, and the proof it survives

~<table>.dataset~ — grep ~picardThInjected~ for the existing precedent on the
same element.

Do NOT model this on ~data-mb-ms-shown~ (grep ~_msLengthPrecisionShown~). That
flag is INFERRED from cell content, and for Picard "no content" is ambiguous:
~tests/snapshots/notes-received/rendered.html~ carries *1688*
~mb-picard-cell~ against only *8* ~mb-picard-btn~, because 1680 of those rows
have no taggable release. A collapsed cell and an "expanded, nothing to tag"
cell are byte-identical, so the state has to be stored explicitly.

Survival, from the code rather than by inference: ~renderGroupedTable~'s reuse
branch is ~table = existingTables[index]~ followed by ~tbody.innerHTML = ''~ —
the ~<table>~, its ~dataset~ and its ~<thead>~ are never replaced — and
~runFilter~'s multi branch always passes a truthy query
(~globalQuery || 're-run'~), so every keystroke, sort and view switch takes
that branch. Independently measured by
~tests/live/caa-icon-survives-sort-multi.spec.js~'s ~tagSubTables()~, whose own
comment records its ~data-probeTag~ survival as always N/N. State is lost only
on the ~!query~ new-table branch — an initial render, a fresh fetch, or a
disk-load — which IS the "initially collapsed" contract.

Read-and-stamp on first sight inside the per-table loop so the value is
explicit from then on, defaulting from the setting.

*** The header control — glyph from CSS, never from text

This is the trap that would otherwise ship silently.

The Picard ~<th>~ is a bare ~<th class="mb-picard-th">Picard</th>~ (grep
~mb-picard-th~) with no ~.mb-col-hdr-flex~, no ~dataset.colName~, no sort icons
and no 📊 — because ~makeTableSortableUnified~ always runs BEFORE Picard
injects, so it never sees that header. It is the one header in the file without
the contract every other column has.

Therefore ~_cleanColHeaderText~ resolves it via its *step-3 clone-and-strip
fallback*, whose selector today is only
~.mb-col-uniq-wrap, .sort-icon-btn, .column-resizer, .mb-col-hdr-flex~ — and
whose last-resort glyph strip does not include ~♪~ and is never reached anyway,
because the fallback is non-empty. A TEXT glyph in that ~<th>~ would make
~th.textContent~ read ~"▶♪Picard"~, and then:

- ~initCollapsableColumns~'s ~headers.findIndex(th => _cleanColHeaderText(th)
  === colName)~ stops matching ~'Picard'~ → *the multi-row Picard cells
  silently lose their collapse toggles*, which
  ~tests/fixtures/search-recordings-continuation.spec.js~ currently pins;
- ~_exportCleanHeaderText~ → CSV/JSON/Org/HTML export headers read
  ~"Picard ♪"~ (~dataset.colName~ is only its fallback for EMPTY text);
- ~openUniqDrop~'s ~isCollapsableCol~ reads raw ~th.textContent~;
- ~_updateAllColHeaderCounts~'s ~_cleanColName~ likewise.

So: prepend a bare ~<span class="mb-picard-col-hdr-btn" role="button"
tabindex="0">~ and put the glyph in CSS ~::before~ keyed on ~[aria-pressed]~,
leaving ~textContent~ exactly ~"Picard"~. Same argument ~CLAUDE.md~ already
makes for the length-mismatch flag being attributes-only with the glyph from
CSS. Add ~.mb-picard-col-hdr-btn~ to ~_cleanColHeaderText~'s step-3 strip
selector as belt-and-braces, and fix that function's stale JSDoc claim that
step 3 removes "all ~[class^="mb-"]~ children" — it removes four named
selectors and never did more.

*Do NOT* set ~th.dataset.colName = 'Picard'~ to fix the lookup instead: it
flips this ~<th>~ from "original" to "extracted" in three Statistics-panel
heuristics. *Do NOT* give it ~.mb-col-hdr-flex~, and *do not* name the button
~.mb-col-collapse-hdr-btn~ or ~.mb-caa-col-hdr-btn~ — ~initCollapsableColumns~'
idempotent cleanup removes both classes table-wide and
~initPicardTaggerColumn~ re-runs it (grep
~_picardRegisterCollapsableColumn~), so the toggle would delete itself on the
pass that built it.

CSS: new rules directly after the ~.mb-ms-col-hdr-btn~ block, same box metrics
and the same hover/~:focus-visible~/engaged-tint idiom. These will be the
*first* ~.mb-picard-*~ rules in the file — everything Picard is inline-styled
today. Leave the existing inline styles alone; they survive ~cloneNode~ and the
save/load round trip, and moving them is out of scope.

Element shape: ~<span role="button" tabindex="0">~ with ~click~ + ~keydown~
(Enter/Space) through one ~activate~ that ~preventDefault()~/
~stopPropagation()~s — copy ~.mb-ms-col-hdr-btn~'s. A ~<span>~ not a
~<button>~: the navigation guard's merge-form branch already has to exempt
~.mb-picard-btn~ from an ~e.target.closest('button')~ check, and a span
sidesteps that.

*** Listener survival — delegate on the <table>

~renderGroupedTable~ rebuilds a per-group ~<thead>~ from
~templateHead.cloneNode(true)~, so a span wired with ~addEventListener~ can
arrive as a live-looking dead clone. A "wired" MARKER on the span would be
copied by ~cloneNode~ and would lie.

Delegate on the ~<table>~ element, guarded by
~table.dataset.mbPicardHdrDelegate~, testing
~ev.target.closest('.mb-picard-col-hdr-btn')~. The table element and that guard
have identical lifetimes, so the guard cannot lie. The ~<thead>~ is NOT a safe
host — unlike the ~<tbody>~, it IS replaced.

Follow ~ensureCollapseDelegate~ but *do not copy its latent bug*: it sets
~table.dataset.mbCollapseDelegate~ BEFORE its ~tbody~ null-check, so a table
with no tbody is permanently marked and never gets a listener. Set the guard
only after ~addEventListener~ has actually run. (Fixing that bug in
~ensureCollapseDelegate~ itself is a separate change — mention it, don't fold
it in.)

Create/refresh the span from a new ~_initPicardColHeaderToggle(table)~ called
from inside ~initPicardTaggerColumn~'s per-table loop on EVERY pass, both
modes, idempotent via a presence check — the "reuse existing button if present"
shape ~_artInitCaaColHeaderToggle~ uses. Not from the ~<th>~-creation block,
which runs once in full mode only.

Two defensive one-liners while there, both covering "a second full render on a
page that already injected Picard": have ~makeTableSortableUnified~'s header
loop skip ~th.mb-picard-th~ so it can never wipe the toggle or hand this column
sort icons and a 📊 dropdown; Part 1 already added the DOM-presence half of the
header guard and the thead-template strip.

*** What "collapsed" must actually skip — the whole point

Restructure so the entity scan sits BEHIND the state check. Today
~_picardExtractRowEntities()~ is the first line of ~_picardFillCell~ (grep
~_picardFillCell~), which is why a collapsed column has to short-circuit
earlier:

#+begin_src js
resolve/create the <td>                       // unchanged — the column always exists
if (!expanded) { if (td.firstChild) td.textContent = ''; return; }
const entities = _picardExtractRowEntities(tr); …   // only when expanded
#+end_src

Skipped per row when collapsed: a full
~tr.querySelectorAll('td:not(.mb-sticky-col):not(.mb-rel-cell) a[href]')~
subtree walk, a regex per anchor, and the construction of a ~<ul>~, N ~<li>~,
N ~<button>~, N ~<img>~ and N ~addEventListener~ calls.

*Additional win, and it is the one Step 23 calls "Picard defeats Steps 3 and
4":* ~initPicardTaggerColumn~ calls
~_invalidateUniqDropDataCacheForTable(table)~ unconditionally on every pass,
which also drops ~_colHeaderCountsCache~. Track a per-table "something actually
changed" flag and invalidate only then. Correct by that helper's own JSDoc,
which exists for populators that fill previously-empty cells. *Do not
retrofit this into Part 1* — there, every pass really does rebuild.

*** Toggling — mutate in place, do not call runFilter()

On the toggled table only: flip the dataset flag; walk its ~tbody tr~ applying
the new state to the live cell AND to its master via Part 1's
~_buildMasterRowIndex~ + ~_picardEnsureRow~ (both already extracted for exactly
this reuse), plus the owner sweep; on expand call
~_picardRegisterCollapsableColumn~ (also already extracted) because while
collapsed ~_anyMultiRowPicardCell~ is never set and the multi-button cells
would get no per-cell toggle; then
~_invalidateUniqDropDataCacheForTable(table)~; then repaint that table's own
header span.

*Both directions must mirror.* If collapse only emptied the live cells, the
next re-render would clone still-populated masters and the column would
silently re-appear while the header read "collapsed".

Why not ~runFilter()~: ~_msApplyLengthPrecision~ has to call it because the
Length column's rendered TEXT is what sorting, filtering, highlighting and the
colon-alignment finalizers all read. A Picard cell contributes to none of them
— its content is a ~<button>~ + ~<img alt="♪">~, so ~getCleanColumnText~ was
always ~''~ for the whole column — it has no ~dataset.colName~ and no filter
input, and it is never a sort key. In-place mutation is also what the existing
re-wire path already does on every keystroke. And ~runFilter()~ is page-wide,
which would defeat the per-table scope outright.

The ~<td>~ must stay for one more reason: ~applyStickyColumn~ stamps a
rest-background on every cell of every row (grep ~mbRestBg~ — it reaches the
DOM as ~data-mb-rest-bg~, so the source spelling is the greppable one), so because the cell already
exists and already has its rest-bg, uncollapsing needs no sticky re-run and
cannot desynchronise the hover colour map.

*** Consequences of an empty cell — mostly already answered

Sorting, column filtering and the 📊 dropdown *do not apply to this column at
all* and so cannot regress: no ~.sort-icon-btn~, no ~.mb-col-uniq-wrap~, no
~dataset.colName~, and ~addColumnFilterRow~ gives the filter row a bare
~<th class="mb-picard-th"></th>~ with no input and no ~data-col-idx~ — all four
confirmed in ~debug/picard-missing.html~.

Left to confirm during implementation, and in every case the collapsed column
should look exactly like today's already-supported "no row has a taggable
release" case (which ~notes-received~ proves is real, 1680 times over): the
collapse-count badge path (~_classifyCollapseCell~ /
~_updateAllColHeaderCounts~), export, and the statistics panel.

*** The page-wide companion

~_picardInitGlobalColHdrToggle()~ modelled on ~_artInitGlobalCaaColHdrToggle~,
called after the per-table loop.

- *Multi-table only* — early-return on ~activeDefinition.tableMode !== 'multi'~,
  as the CAA global does. A single-table page has exactly one Picard header, so
  its own toggle already IS the page-wide control.
- Rendered only while at least one ~.mb-picard-col-hdr-btn~ exists; aggregate
  state from the per-table spans; click fans out ~.click()~ to those not
  already in the target state, then re-syncs itself.
- *Placement needs care.* The CAA/EAA globals insert with
  ~globalCollapseBtn.after(btn)~ into ~.mb-global-actions-container~
  immediately after ~#mb-col-collapse-all-btn~. Because
  ~initPicardTaggerColumn~ runs AFTER ~renderGroupedTable~'s artwork tail, a
  naive ~.after()~ would wedge the Picard button BETWEEN collapse-all and the
  CAA one. Insert after the LAST existing ~[data-mb-caa-col-all-ctx]~ button if
  any, else after ~#mb-col-collapse-all-btn~, for a deterministic reading order
  — collapse-all, CAA-all, EAA-all, Picard-all — whichever pass ran first.
  Idempotent via a fixed ~id~.

Where the plan was wrong, and where I went beyond it

Three findings I want to flag rather than bury:

1. The master-row mirroring is not load-bearing for correctness. The plan said collapse-without-mirroring would make the column silently re-appear. Mutation-tested it — it doesn't: _picardApplyToRow() reconciles every clone against the table's state each pass, and every visible assertion stayed green. I kept the mirror (it stops a collapsed column cloning subtrees it discards, which is a real part of the cost) but rewrote its JSDoc to claim only that.
2. A real latent defect fell out of the mutation run. _cleanColHeaderText()'s step-3 strip was missing .mb-col-collapse-hdr-btn, so once the Picard column had multi-row cells that header resolved as "Picard▶3▤" — initCollapsableColumns() appends its button directly to that <th> (the no-flex fallback; Picard's is the only such header). Latent, not live. Fixed, with a changelog entry.
3. The plan's single-table verification URL has no Picard column at all. release/3ec14d03-… is a release tracklist; its rows link recordings, and the guard asks for /release/<mbid>. Verified against the live page. I used series-releases instead, and documented the tracklist case in HELP — it was never written down.

I also added tests/live/picard-header-toggle.spec.js (@extended, 2 tests, one per table mode, registered in tests/live/registry.org) as the reviewable form of the plan's "then verify manually". Both pass against real pages.
