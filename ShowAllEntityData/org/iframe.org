** Design: one engine, many sources

*** Sources replace =_DP_SITES=

A source says which links (or containers) it serves and how to read their
target:

#+begin_src js
{
    id: 'mb-release-group',             // debug channel and cache namespace
    host: 'musicbrainz',                // 'musicbrainz', or a _foreignHost value
    setting: 'sa_pop_mb',               // its gate; the foreign hosts keep sa_*_detail_preview
    kind: 'Release group',              // the dialog's title
    match: (url, el) => key || null,    // from an href, or from data-mb-pop
    load: async (key, ctx) => record,   // the card; ctx = {gate, fetchJson, fetchText, wanted, force}
    more: async (key, record, ctx) => record, // optional: what only the pinned dialog needs
    live: { url: (key) => '/release-group/' + key, charset: null,
            liveRoot, liveHide, liveCss, livePrepare },
    step: 'column',                     // the arrows stay in one column ('row' = today's rule)
    ttlMs: 24 * 3600 * 1000,
    parserVersion: 1,
}
#+end_src

- The four foreign sites become four sources with their current parsers and
  =step: 'row'=. That is a pure refactor, pinned by the unchanged
  =detail-preview= specs and =scripts/mutations/detail-preview.json=.
- =_dpActiveSite()= becomes "the sources of this host whose setting is on";
  =_dpSiteForLink()= becomes =_popResolve(el)=, which returns
  ={source, key, anchor}= or null.
- The record keeps =_dpEmpty()='s shape and gains:
  - =pills=: short facts ("Album", "Official", "12 releases");
  - =links=: related entities, ={kind, label, href}=, clickable in the dialog;
  - =table=: ={cols, rows, sortable}= for a release group's releases, a
    recording's releases, a work's recordings;
  - =art=: cover or poster URLs, only where the Web Service answer says the
    archive has them (=cover-art-archive.front=, to be confirmed in Phase 0).

*** Resolving what is under the pointer

First hit wins:
1. ~[data-mb-pop="<source>:<key>"]~ on the element or an ancestor, stamped by a
   converter or extractor during pre-processing. An attribute survives
   =cloneNode(true)=, so every re-render keeps it for free.
2. A page-definition container (=features.popTargets=, see 1b).
3. An =a[href]= that a source's =match()= accepts.

Never a card for: a link that wraps an =<img>= (artwork has its own preview), the
=.tabs= navigation, the page header and footer, the script's own toolbar and
menus, edit/create/merge/add-cover-art links, =#= anchors, and links inside a
card.

*** Gates on MusicBrainz

- One setting, =sa_pop_mb= ("Preview linked entities on hover"), *off by
  default*, in a new ⚙️ section. No per-kind switches (answer 3).
- The Ctrl gate as on the foreign hosts: hover with Ctrl held, or rest the
  pointer and press Ctrl. It follows =sa_dp_hover_without_ctrl=, relabelled
  "every preview"; the "#" cell keeps =sa_event_rg_tooltip_without_ctrl=, and
  no new key replaces the two (answer 2). The release page's subheader link
  stays on a plain hover (answer 8).
- Installed at page init on every =@include=d MusicBrainz page, table rendered or
  not: the native rows and the rendered rows hold the same links, and the
  listeners are delegated on =document=, so =cloneNode= re-renders need nothing.
- Scope: =table.tbl= bodies first; =#content= page-wide in Phase 4.

*** Requests, cache, freshness

- Every MusicBrainz request waits on =_relAwaitRateSlot()=, the gate whose own
  JSDoc calls it "one gate for every request". =_rgWsGet= moves onto it too. The
  foreign hosts keep =_dpAwaitSlot()=: another origin, another budget.
- A card makes at most ONE request. The pinned dialog may add one or two
  (=more()=); a paged browse shows its progress ("200 / 312").
- Cache: the detail-page database =vz-saed-detail-pages=, store =pages=, keyed by
  the request URL (which carries the inc set), ={url, v, at, data}=. IndexedDB
  is per origin, so on musicbrainz.org it starts empty, and the art cache's
  =_ART_IDB_VERSION= stays as it is.
- Time to live per source: 30 days for the foreign sites, as today; 24 h by
  default for MusicBrainz (=sa_pop_mb_ttl_hours=). ⟳ bypasses both tiers. Only
  a successful answer is cached, as everywhere in the script.
- *NOT* =_relFetchWs2()=: its two cache tiers are keyed =type:mbid= with no inc
  set (=_relIncOptionsForEntityType()= fixes one per type), so a popup's answer
  and the Relationships column's would overwrite each other's.

*** The dialog

- =#mb-dp-dialog= keeps its id and shell. Its title becomes the source's kind
  ("Release group", "Release", ...) instead of "Detail page".
- ‹ › and ← → step through the same column (=cellIndex=) and the same source in
  the visible rows of that table: a MusicBrainz row links an artist, a release
  group and a label, and "the first link of the row" would mix them. In a
  multi-table page the step continues into the next visible sub-table.
- The Live page on MusicBrainz: the entity's own page, fetched same-origin
  through the shared gate and cleaned by =_dpLiveDocHtml()= (no scripts, so React
  does not hydrate and the userscript does not run again inside); =liveRoot=

** 1b. Containers beyond <a href> (suggestions)

Everything here ends up as rule 1 of the resolver (=data-mb-pop=), so the engine
keeps one path. Stamping an attribute changes no cell text, so none of the four
post-render cache duties (docs/claude/filter-and-cache-invariants.md) apply when
it happens during pre-processing, before the rows are captured.

| #   | Container                 | How it is declared                                        | Example                                                                             |
|-----+---------------------------+-----------------------------------------------------------+-------------------------------------------------------------------------------------|
| i   | any element, by attribute | ~data-mb-pop="<source>:<key>"~, stamped at pre-processing | the release-tracks "#" cell: ~data-mb-pop="mb-event-rg:<event key>"~                |
| ii  | a column, by header name  | =features.popTargets: [{column, source, key(td)}]=        | Catalog# to its label; Barcode to a barcode search; Format to the format's doc      |
| iii | the row                   | the row's main entity cell carries i                      | rows whose main entity is plain text; on a touch screen a small magnifier opens it  |
| iv  | text patterns             | the existing formatters stamp i                           | ISRC (=initIsrcFormatting=), barcode (=initBarcodeHighlight=), MBIDs in annotations |
| v   | the script's own UI       | i on the element                                          | UVD entries (an artist entry, its artist), h3 medium headers (the disc IDs)         |
| vi  | links inside the dialog   | the dialog's own links                                    | Space on a release inside the release-group dialog: that release, with a Back       |

- ii is the declarative form of i for a whole column: resolved by header name
  at pre-processing, like =collapsableColumns=, and turned into i on every cell.
- iii is the touch answer as well: a phone has no hover and no Ctrl.
- vi turns the dialog into a small browser of linked entities: a back stack,
  the dialog title showing the path ("Release group > Release").

** Risks and traps

- *The =_relFetchWs2()= cache ignores =inc=.* Use the engine's own cache.
- *One rate budget.* Every MusicBrainz request through =_relAwaitRateSlot()=;
  never a new gate.
- *The other floating boxes.* Add the card to =_OTHER_RICH_TIPS= (it is already
  there as =mb-dp-peek=); a link wrapping an image keeps its artwork preview; the
  Relationships tooltip stays on its own cells; the card's z-index stays above
  the dialog's (a card can open over the dialog in Phase 5).
- *Third-party userscripts* add their own links and icons to MusicBrainz tables:
  run the =kitchen-sink= combination of =tests/support/run-live-interop.js= once
  per phase.
- *Ctrl+click opens a new tab* in every browser. The Ctrl keydown shows a card
  but is never consumed, so Ctrl+click and the Ctrl+M shortcuts keep working.
- *Typing*: Space pins only outside a field, or 1.5 s after the last keystroke
  in one (=_DP_TYPING_GRACE_MS=): the render focuses the global filter itself.
- *Stale data*: MusicBrainz data changes daily, hence the short TTL and ⟳.
- *Playwright trace*: a spec that counts "Blocked script execution" messages
  runs with =test.use({ trace: 'off' })= (see docs/claude/detail-pages.md).
- *A freshly fetched release page re-renders itself* when its bundle hashes are
  current: abort =static.metabrainz.org/**= in fixture specs
  (docs/claude/release-tracks-and-length.md).

** Performance

- Nothing on the filter, sort or render path: the listeners are delegated on
  =document= and return at once for anything that is not a candidate. A
  =mouseover= costs one =closest()= and one =new URL()= per link entered.
- Stepping walks the visible rows once per key press, never on a render.
- Network: hover requests and the Relationships column's auto-load share one
  1.1 s gate. With both running, the column's load slows by one slot per card
  opened. That is the price of staying within MusicBrainz's 1 request per second
  (open question 7).
- A wider =@include= (Phase 4) means the whole script, now 110,379 lines, is
  parsed on every MusicBrainz page. Measure it before deciding.
