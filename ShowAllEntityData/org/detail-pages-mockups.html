Detail pages, without leaving the list

Every row on the four Springsteen sites links to a detail page the script never opens. These mockups show five ways to bring that page to the row. Each one is built from 28 real detail pages fetched and parsed on 2026-10-07. Only the cover images are stand-ins, because this page cannot load the sites' images.

sl-collection / sl-bootlegs → bootlegs.php?item=6739 jl-list → html/19760930.htm bs-records → detrec.aspx?code=CR1AD1 bb-songs → song:4th-of-july-asbury-park-sandy
Question 1 · popup on hover, Esc closes
Yes, on all four sites

feasible Each detail page has the same origin as its list, so the script can fetch it and parse it into the same cream card it already uses for cover art and relationships. A plain hover card cannot be scrolled, so Space pins it into a dialog you can scroll and drag (options A and B).

Question 2 · detail data in the row
Yes, as columns loaded on demand

costs fetches One page per row at the polite 1.1 s spacing. A whole jungleland list takes about 1 h 47 min, so detail columns must load only when asked for, per table or per cell, and be cached. The values then filter, sort and appear in 📊 like any other column (option D).

Question 3 · suggestions
Peek and pin first, then columns

One parser per site feeds every option, so the first phase builds the parts the second phase reuses. The side drawer (C) is an alternative to the dialog. The inline row (E) is shown only to explain why it should not be built.

Recommended path

Phase 1 · foundation + A + B

Peek, then pin

  • DetailPageParsers: one parser per site, returning {title, fields, tracks, images, notes}
  • A same-origin detail fetch with a 1.1 s gate and per-host decoding (windows-1252 for jungleland)
  • An IndexedDB store detail-pages with a TTL; each host gets its own database
  • Hover card through data-mbtt-fn="detail"; Esc closes it; Space and 🔍 pin it
  • A setting per site, off by default, under the existing site gate
Phase 2 · D

Detail columns

  • A "📄 Details" column group per site, with a header toggle and a progress badge
  • Relationships-style load states: queued, loading, none, failed, retry
  • Tracklists and source shows as multi-row cells with the existing ▶ collapse
  • Reads phase 1's cache, so every row already peeked costs nothing
Optional · C

Browse mode

  • The same content as B, docked to the right edge
  • Pays off on jungleland, where the detail page is mostly covers
  • Build it only if B feels cramped in practice

Found while probing

mustThe detail pages are outside every @include

The script never runs on them, so everything has to be fetched and parsed from the list page.

mustjungleland.it is windows-1252 with no charset

fetchHtml() calls res.text(), which decodes as UTF-8. Use arrayBuffer() with TextDecoder('windows-1252').

parseSome springsteenlyrics tracklists have no numbers

Items 1331 and 1332 list bare titles straight after Duration. The parser falls back to plain lines and says so (see B, row 4).

parsebrucespringsteen.it repeats sources with "

The From column uses a ditto mark for "same as above", so the parser has to fill each one from the row above it. Its song links are href="#", so they have nowhere to point.

sizeA brucebase song page is 65–115 KB

Parse it once and cache only the extracted fields, not the HTML.

okFraming is allowed

None of the sites block same-origin iframes; brucebase sends SAMEORIGIN. That is what makes B's "Live page" view possible.

Compared with B

D · Detail columns

A column group the script fills from the detail pages, loaded on demand like the Relationships column. Once loaded, the values filter, sort and show up in 📊. Click one cell to load just that row, or press the header toggle to load the whole table.

Columns per site
  • sl: Tracks, Discs, Lineage, Scans
  • jl: Uploader, Covers
  • bs: Recorded, Source show, Tracks, Notes
  • bb: Origin, Played live, Last played, Releases
The rules it must follow

Never add or remove a <td>; only fill cells that already exist. Write to the master rows too. After each write: clear the 📊 cache, the filter cache and _rowTextCache, and re-run runFilter().

How long a load takes

Rows already in the cache cost nothing, so a second visit is instant. Above a threshold the group starts collapsed, as sa_rel_collapse_threshold does for Relationships.

E · Inline expand row: not recommended

Opening a ▶ under the row to show the tracklist feels natural, but an extra <tr> inside the table's tbody breaks assumptions the table code relies on everywhere.

Expanded, unsorted
After a sort: the detail row lands under the wrong show
✕Sorting

sortLargeArray() reorders source rows. A detail row is not one of them, so it stays where it was or is dropped.

✕Re-rendering

renderGroupedTable() clones its source rows, so a detail row added to the live table is gone after the next filter.

✕Counting and filtering

Row counts, runFilter() and the 📊 tallies would count the detail row as a record.

✕Column indexes

A full-width colspan cell has none of the indexes the column extractors and the sticky column expect.

The safe version

Put the tracklist inside a cell of D's column group as a multi-row ul>li with the existing ▶ collapse toggle. The cell lives on the source row, so sorting, cloning and filtering all keep working.
