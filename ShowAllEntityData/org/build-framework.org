** 1. Delivering a script this big, without annoying the developer

*** 1.1 For users: keep ONE installed artifact

One ~.user.js~ is still the right shape for users. Each extra ~@require~ is another URL that
Tampermonkey caches separately and, since 4.16, refreshes ONLY when the main script itself
updates ("External ~@require~ and ~@resource~ content is not updated by default anymore unless
the script was updated"). It is one more thing that can be stale or unreachable (the
2026-10-04 jsdelivr outage failed 72 tests before the harness vendored iro and pako).

Three header changes, none of which touches runtime code:

1. *Header-only ~ShowAllEntityData.meta.js~ as ~@updateURL~.* Lines 1–54 only (stop at the
   FIRST ~// ==/UserScript==~; the credits block at 99–200 carries nine other scripts'
   ~// @name~ / ~// @version~ / ~// @downloadURL~ lines). Keep ~@downloadURL~ on the full
   file. Existing installs are safe: their next check still uses the old URL, which still
   serves the full script, and installing that update brings the new header. Keep the old
   URL alive forever. ~check-publish-ready.py~ must then fail when the mirror's ~.meta.js~
   is not byte-equal to the mirror ~.user.js~'s header, ALWAYS, not only at parity: a stale
   meta file silently stops updates for everyone who has switched.
2. *Pin iro exactly.* ~@require https://cdn.jsdelivr.net/npm/@jaames/iro@5~ floats within
   major 5; the harness already vendors exactly 5.5.2 (byte-identical to what jsdelivr serves
   for ~@5~, checked 2026-10-04). Write ~@jaames/iro@5.5.2~ and tighten
   ~tests/fixtures/harness-required-libs.spec.js~'s "major only" assertion to an exact match.
3. *Optional: pin the library to an immutable URL, with SRI.* Today the library ~@require~
   points at the mirror's ~master~ branch, so a user's library is whatever ~master~ held when
   SAED last updated — which can be newer OR older than the SAED version it was tested with.
   A tag or commit URL (~raw.githubusercontent.com/vzell/mb-userscripts/<tag>/lib/…~) plus
   ~#sha256=…~ (Tampermonkey supports SRI on ~@require~, checked at install) makes the pair
   exact. Cost: ~check-publish-ready.py~'s ~NETWORK_LIB_URL~ equality check becomes a pattern
   plus "ref exists on origin/master, its ~@version~ equals the dev library's, the hash
   matches"; ~check-publish-ready-gate.py~ needs planted cases for each; and a ~#sha256=~
   suffix breaks the ~$~-anchored patterns in ~harness-required-libs.spec.js~ and
   ~check-vendored-libs.py:31~.

** 2. Would an automatic build pipeline be more effective?

Yes — but split into "having a build" and "splitting the source", and never a bundler.

*** 2.1 Why not the bundler (and what REFACTORING.org got right)

~REFACTORING.org~ "NOT RECOMMENDED: full module split via bundler" (written at 65k lines)
rejected webpack/esbuild/rollup because (1) no tooling existed, (2) shared mutable module
state (~activeDefinition~, ~CAA_CTX~ caches, ~ctrlMFunctionMap~ …) crosses every boundary,
and (3) "nothing changed" could not be verified (10 of 86 PTs had snapshots). (2) is still
true and is the decisive one: a module system would need an import/export design at every
boundary of a file with ≈600 top-level declarations that all see each other. The plan below
keeps ONE scope, so (2) never arises; (1) shrinks to a ≈100-line Python script; (3) is
answered by byte identity. Revisit that REFACTORING.org verdict with this section in hand,
rather than re-litigating it from scratch.

*** 2.2 Phase 0 — no build (do now)

The dev loader + stage step (1.2) and the header fixes (1.1). Zero runtime change.

*** 2.3 Phase 1 — a build that DERIVES artifacts from the single file

~scripts/build-userscript.py~ reads today's ~ShowAllEntityData.user.js~ (still the only
source, still edited by hand and by Claude exactly as now) and writes:

- ~dist/dev/~ — the stage of 1.2;
- ~ShowAllEntityData.meta.js~ — header lines 1–54, for the mirror;
- optionally ~dist/publish/ShowAllEntityData.user.js~ — comments and leading indentation
  removed with acorn TOKENS (never regex: the CSS at 59305 contains ~/* */~ and URLs contain
  ~//~), EVERY newline kept so a user's stack-trace line number still points at the right
  source line, lines 1–211 (header, licence, credits) kept verbatim, acorn pinned exactly

*** 2.4 Phase 2 — optional: split the source into ordered fragments

Only if editing the single file becomes the bottleneck. Design constraints found:

- *Concatenation, not modules.* ~src/NN-name.js~ fragments joined in order back into the
  same IIFE. Hoisting, TDZ order and shared mutable state are untouched, as long as
  fragments are never reordered (make that a rule and a check).
- *Byte-identical first cut is realistic and is the safety proof.* The file is LF-only,
  has no BOM and ends with ~})();\n~. Join in binary mode, compare SHA-256 with today's file.
- *Cut only at verified top-level boundaries.* Checked with acorn: 214, 4612, 5720, 9897,
  14381, 24219, 27722, 31312, 38815, 42100, 56955, 57204, 62027, 83722, 90072, 96372,
  97477, 105148, 106139, 118990, 120530. A line-based guess like 42773 falls inside the
  declaration at 42756–42774. ~openUniqDrop~ and ~startFetchingProcess~ cannot be split at
  all.
- *Fragments are not valid scripts.* 31 top-level ~if (…) return;~ statements (the host
  gates, the pageType gate) and the IIFE's open/close in the first/last fragment. So
  ~node --check~ and eslint run on the BUILT file only (~tests/lint-baseline.json~ is
  keyed by that path anyway); fragments get an acorn check with
  ~allowReturnOutsideFunction~.
- *Two-way tool.* Claude and 10 of the 12 skills name the built file and will keep editing
  it. The tool must split AND join by anchors, and refuse to build over a hand-edited
  artifact rather than silently drop the edit.
- *Freshness as a fixture spec*, so ~npm run test:full~ (the merge gate) catches a stale
  artifact. There are no git hooks and no CI.
- *Merges.* Mark the artifact ~linguist-generated~; resolve artifact conflicts by rebuilding
  (a keep-ours merge driver lives in local git config, so each host must set it up), and
  make ~merge-push-remove~ rebuild after the merge.
- *Watchers vs mutation-check.* A ~--watch~ rebuild would overwrite a running mutant, and
  then ~restore_all()~ would leave the artifact stale. The env-var redirect (1.2) comes
  first.
- *History.* ~git blame -C -C -C~ follows lines across the split commit; history scripts
  keep reading the artifact path.

** 3b. Split the non-MB code into its own files, or its own userscript?

*Own fragment(s): yes, as part of Phase 2 (2.4).* The main body 9897–14379 is already one
contiguous, cut-safe block (9897 and 14381 are verified top-level boundaries), so it can be
the first fragment cut out. The settings, PTs, ~_DP_SITES~ and readers stay where the engine
expects them, because of TDZ order and the ~pageDefinitions~ reads.

*Own userscript: no, not today.* Reasons, strongest first:

1. *The engine would be duplicated, not shared.* Tampermonkey runs each userscript in its own
   scope; two scripts cannot share one engine instance short of exposing it on the page's
   ~window~ (which with ~@grant~s on is a different world from both scripts'). So "SAED-
   Springsteen.user.js" would ~@require~ or contain the whole engine: the same 6.7 MB parse,
   just on fewer pages.
2. *MusicBrainz needs the Springsteen parsers anyway* (link previews; 2.5).
3. *Settings would split.* GM storage is per installed script: colours, filter defaults,
   column choices and the art cache keys would be configured twice, and exported twice.
4. *Two update channels, two changelogs, two HELP files*, and every engine change would have
   to be released twice.

*When that flips:* if the engine itself becomes a versioned ~@require~ library that both
scripts load (a big refactor — the "engine" is ≈95 % of the file and full of module state),
or if a site needs Tampermonkey features that conflict with MusicBrainz's (a different
~@run-at~, ~@sandbox~, ~@noframes~). Neither is true today.

*** Proposed contract (not implemented)

Small, namespaced, versioned, and zero-cost when nobody listens:

- ~saed:ready~ — once, right after the pageType gate passes. ~detail~ = JSON string
  ~{"v":1,"pageType":"…","tableMode":"single|multi","host":"musicbrainz.org|…"}~.
- ~saed:rendered~ — after every completed render, with ~reason~ = ~initial~ / ~filter~ /
  ~sort~ / ~view~ / ~disk-load~ and ~{"v":1,"pageType","reason","rows","total","gen"}~.
  One event instead of a separate ~saed:filtered~: filter typing is already debounced
  (~sa_filter_debounce_delay~), every pass already clones rows, and a ≈100-byte JSON string is
  noise next to that. Never put row data in it.
- Dispatched on ~document~ through one helper ~_saedAnnounce(reason)~ on ~setTimeout(0)~:
  listeners see the finished DOM, and a listener that types into a filter cannot re-enter
  ~runFilter~ mid-pass. Call sites: ~_finishRender~ (≈79556, only when not superseded —
  this also covers ~runFilter~'s single-table branch) and the end of ~runFilter~'s grouped
  branch after the re-wiring, plus the initial grouped render.
- *Why JSON strings:* with ~@grant~s, scripts run in isolated worlds. DOM events cross
  worlds, but a ~CustomEvent.detail~ object arrives as ~null~ in another world unless it is
  structured-cloneable, and Firefox needs ~cloneInto~. A string always arrives.
  (SpringsteenCoverArtUploader passes objects containing functions; that only works while both
  sides share one JS context, so the contract must not copy it.)
- *Late listeners:* the order in which document-idle userscripts start is undefined, so
  also mirror the state on ~document.documentElement~: ~data-saed="<pageType>"~ and
  ~data-saed-gen="<n>"~. A script that starts after SAED's first render reads the attribute
  instead of waiting for an event that already fired. (The harness can use ~data-saed-gen~
  too, instead of guessing completion from ~#mb-render-heading~.)
- *Rules for a cooperating script:* use event delegation on the ~table~ or ~document~, never
  per-row listeners; or re-apply on every ~saed:rendered~ (idempotently, keyed by a marker
  class). Mark your own injected elements with a ~data-saed-keep~ attribute if they must
  survive SAED's cleanup passes — that would need one generic check in the strip passes
  instead of the per-script exceptions SAED carries today (~#grcfr-header-controls~).
- *Testing:* the harness injects SAED in the page's own context (~loadPage.js:215~), so it
  cannot see the cross-world behaviour. A listener script under
  ~tests/fixtures/thirdPartyScripts/~ covers the event timing; the ~null~-detail case needs
  one manual check in Tampermonkey.
