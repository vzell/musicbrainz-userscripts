* F1 — one SAVE pins every setting forever
:PROPERTIES:
:CUSTOM_ID: F1
:END:

The library's SAVE handler iterates the whole schema rather than a dirty-set,
and =settingsInterface.save()= writes every key it is handed. So the first time
a user presses SAVE — *even having changed nothing* — all ~238 current defaults
freeze into their GM storage, and every default shipped afterwards is invisible
to them permanently.

There is no migration, no key-rename map, and no cleanup of orphaned keys. A
renamed key silently orphans its old value and the new key starts at its default;
=GM_listValues= is not even granted, so nothing could enumerate the strays.

The same applies harder to the 5 =type: 'table'= settings. They are lazy-seeded
from code on first use (=_loadDefaultHiddenColumnsMap()=, =_initRelMappings()='s
=_loadMap()=, =_loadUnicodeCharsMappings()=) and never reconsult the built-ins
again, so new rows shipped in a later version never appear. The only escape is to
delete every row in the table editor, save, and reload so the empty-table
re-seed fires.

This reframes =bfb8ac3='s own release note — /"Only affects fresh installs;
existing explicit user settings are untouched"/ — which is true of more users
than intended: it also spares everyone who pressed SAVE once and changed nothing.

*Said here to be unfixable-for-now, and that was wrong.* The original note read:
/"A dirty-set save plus a migration table is a shared-library change with a real
blast radius (=MB_PageEnhancer= uses the same schema mechanism) and no
obviously-correct answer for values already frozen."/ Two of those three claims
survive and the conclusion does not. The dirty-set save IS a library change and
does carry that blast radius — so it is feature-detected, and an ungranted
consumer keeps its old behaviour exactly. But *the migration does not have to
live in the library at all*: it went consumer-side, where
=_coerceNumericSettings()= already sits for [[#F2][F2]], and ships with the userscript
instead of waiting on [[#F6][F6]]. And "no obviously-correct answer for values already
frozen" was really "no answer without evidence" — see below, where git turned
out to have it.

** What shipped

Three parts, deliberately in two places, because they reach users on different
days:

1. *=lib/VZ_MBLibrary.user.js= 4.1.0 — SAVE is a dirty set.* A value equal to
   its schema default is deleted, not written. New =settingsInterface.persist()=
   holds the writes and returns ={stored, cleared}=; =save()= is =persist()= plus
   the reload, split so the write half is testable at all. Comparison is
   string-wise (every non-checkbox widget hands back =input.value=, so a number
   default of 30 arrives as ="30"=) and case-insensitive for =color_picker= (the
   schema writes =#FFD700=, iro.js writes back =#ffd700= — otherwise re-picking
   the colour a setting already had would pin it for ever). *=GM_deleteValue= is
   feature-detected*: a =@require='d library runs in the consumer's sandbox with
   the consumer's grants, and =MB_PageEnhancer= does not grant it, so there it
   falls back to =GM_setValue=, i.e. to 4.0.0's behaviour, rather than throwing
   inside SAVE and losing the user's edits. This half reaches nobody until [[#F6][F6]].
2. *=_migrateFrozenSettings()= — the one-time repair.* Consumer-side, so it
   ships with the userscript. Three passes, each of which only DELETES: adopt
   the ten retired defaults, drop the four orphans, then prune every remaining
   key already sitting at its own current default. Guarded by
   =sa_settings_migration_level=, so a value set afterwards is never revisited.
   Everything removed goes into one backup key first.
3. *=_applyConfigSettings()= applies the same rule.* The exported file is a FULL
   DUMP of all ~232 importable keys, so one 📂 Load configuration re-froze
   everything the migration had just freed — and reported a clean success.

*The third pass is the one that actually fixes this finding.* Adopting the ten
repairs what has already drifted; pruning at the current default changes nothing
observable and is what makes the NEXT =default:= flip reach these users without
waiting for another SAVE. Its cost, stated rather than hidden: a value
deliberately chosen that happens to equal today's default stops being pinned.
Storage holds values, never intentions, and today the two are already
indistinguishable in effect.

*The notice is the answer to "no obviously-correct answer".* The ten change what
the page does, so a silent adoption would read as a bug. A one-time dismissible
banner names them, with ↩︎ Undo restoring the whole backup — and deliberately
NOT resetting the migration level, or the next page load would undo the user's
undo.

*Still not done, and recorded rather than attempted:* the five =type: 'table'=
settings. They are lazy-seeded from code on first use and never reconsult the
built-ins, so rows shipped in a later version never appear. Merging built-in
rows into stored ones cannot tell "the user deleted this row" from "the user has
never seen it", and unlike the scalar case there is no historical value to
recognise — a row is not a default. The escape is still to empty the table in
the editor, save, and reload.

*A parser trap worth carrying into [[#item-4][Item 4]].* The obvious entry regex — key, body,
=\n        },= — silently drops =sa_edits_color_zebra_even=, the LAST entry in
the schema, because it ends =}= with no trailing comma. That is a
238-vs-237 undercount that looks like nothing. =dump-config-defaults.py= must
brace-count or tolerate the missing comma, and its own test should assert the
count against a =grep -c "type:"= of the block.

* F2 — =number= settings are stored as strings, and four of them are dead
:PROPERTIES:
:CUSTOM_ID: F2
:END:

=input.value= is always a string and the SAVE handler does not coerce it back —
only =checkbox= gets a real type, via =input.checked=. So after *any* SAVE all 38
=number= settings are strings in GM storage, and =settingsInterface.init()= hands
them straight back on the next load without re-coercing.

Four settings are read with the ~typeof v === 'number'~ guard that =CLAUDE.md=
holds up as the *correct* fix for the falsy-zero bug. The guard fails on a
string, so the user's value is silently discarded:

| Setting                            | Read in                     | Effect after the first SAVE                          |
|------------------------------------+-----------------------------+------------------------------------------------------|
| =sa_rel_collapse_threshold=        | =_relTableExpanded()=       | always 200; =0= ("never auto-collapse") does nothing |
| =sa_rel_auto_retry_max_failed=     | =_relAutoRetryMaxFailed()=  | always 25; =0= (disable) does nothing                |
| =sa_rel_completion_toast_duration= | =_showRelCompletionToast()= | always the default                                   |
| =sa_caa_completion_toast_duration= | =_showCaaCompletionToast()= | always the default                                   |

The bitter part: =_relTableExpanded()='s own JSDoc explains at length that it
reads the setting *without* =||= precisely to avoid the =0 || 200= defect — and
the replacement guard fails for the identical input, for a different reason.

*The export path already knows.* =_buildConfigJson()= coerces =number= back with
=Number()= and its comment says why: /"After a RESET → SAVE cycle the settings
dialog stores all values via input.value which is always a string"/. The runtime
read path never got the same treatment.

** Why no test caught it

Fixture specs seed booleans only — =tests/pagetypes.json='s =seedGmValues=
entries and =loadPage.js='s =FIXTURE_SETTINGS_OVERRIDE= are all =true=/=false=.
The post-SAVE string state is therefore never exercised anywhere in the suite.

** The interaction that forces two fixes into one commit

=startFetchingProcess()= reads =Lib.settings.sa_render_threshold || 5000=, which
=CLAUDE.md= already records as the falsy-zero defect. But trace it *post-SAVE*:
the stored value is the string ="0"=, which is *truthy*, so it survives the =||=;
then ="0" > 0= is false and the dialog is skipped. *"0 to disable" currently
works — by accident.*

Coercing to a real =0= would restore the documented bug. So the coercion and the
=||= fix have to ship together, or [[#item-2][Item 2]] is a regression. Same shape at
=renderFinalTable()= and =renderGroupedTable()=, both reading
=sa_chunked_render_threshold || 1000=.

* F3 — config import silently wipes the editable tables
:PROPERTIES:
:CUSTOM_ID: F3
:END:

💾 /Save configuration/ and 📂 /Load configuration/ have shipped since 9.99.273,
injected into the library's settings-modal footer by
=_injectSettingsConfigButtons()=.

=_loadSettingsConfig()= skips only =divider=, then coerces every
non-checkbox/non-number value with =String(value)=. The 5 =type: 'table'=
settings are arrays, so they become strings; =Lib.getTableRows()= rejects the
non-array and the lazy-seeders refill from built-in defaults.

*Net effect: importing a config file silently discards every hand-entered row* in
Default Hidden Columns, the three Relationships icon tables, and the Unicode
picker — the settings that are by far the most laborious to re-enter. Nothing
crashes and nothing warns; the summary dialog reports the keys as applied.

=type: 'function'= is mishandled at both ends too: =_buildConfigJson()= exports
it (its =default:= is an internal method name, not a value) and
=_loadSettingsConfig()= writes that string into GM storage. The library's own
save/snapshot/reset loops all skip =['divider','function','table']=; the
consumer's two loops skip only =divider=.

** Two smaller defects in the same feature

- *The header comment is false.* It claims the export contains /"ONLY non-divider
  keys whose value differs from the schema default, making files short"/.
  =_buildConfigJson()= has no delta filter — it dumps all ~238 keys. The export
  is, already, a full defaults snapshot.
- *Undocumented and untested.* =ShowAllEntityData_HELP.txt= has a /Settings
  dialog safety guards/ section and references ⚙️ Settings 30-odd times, but
  never mentions Save/Load configuration. No file under =tests/= references
  =_buildConfigJson=, =_loadSettingsConfig= or either button label.

** What the fix established (9.99.1137)

*The direction was not a judgement call, and git settled it.* =bfb8ac3=
("adjust configuration setting defaults to sensible values", 2026-08-17)
contains =default: 8= → =default: 30= on =sa_uniq_dropdown_visible_rows=, and
left =Number(Lib.settings.…) || 8= untouched several thousand lines away. The
schema default is the deliberate value; the inline literal is what that commit
missed. So every one of the 15 was fixed by moving the LITERAL, never the
default — and the same is true of the descriptions.

*The drift was almost entirely INERT, which is why it survived a year.*
=settingsInterface.init()= writes =GM_getValue(key, schema.default)= into
=Lib.settings= for every schema key, so =Lib.settings.sa_X= is never undefined
in normal operation and the =||= never fires. It fires in exactly two places:

1. the stored value is FALSY — a colour field the user cleared and saved
   (=''=), or a =0=; and
2. the =VZ_MBLibrary= =@require= failed, where =Lib= is the stub whose
   =settings= is ={}= and each consumer's own fallback is all there is.

This matters for how the change is described: *nobody's colours were wrong*.
The fix removes a trap, it does not repair a visible fault. Anyone tempted to
write the changelog entry as "your headers were the wrong colour" should read
this paragraph first.

*The four contradicting descriptions were the user-visible half*, and they were
worse than the literals, because the settings dialog SHOWS them:
=sa_ui_h3_bg= said /"Default is a light green"/ while =#f7dfdf= is a pale rose
(the light green was =#f0fff4=, the inline fallback); both hover settings
claimed /"the original MusicBrainz light grey (#f9f9f9)"/ while their defaults
are oranges; both non-hover settings promised /"the existing grey hover
background is preserved"/, which the orange hover defaults had already broken.
=sa_ui_thead_th_bg= claimed its default /"matches the original MusicBrainz
grey"/, which stopped being true when it became =#bababa=.

*A count this file got right and a script got wrong at first.* F4 says "four
descriptions"; a scripted check that only compares NAMED hex colours finds two.
The other two contradict in words rather than hex ("a light green", "the
existing grey hover background is preserved"). Prose contradictions are not
mechanically checkable, which is the same conclusion [[#item-4][Item 4]]'s =--docs= worklist
reached from the other side.

* F5 — settings-dialog friction
:PROPERTIES:
:CUSTOM_ID: F5
:END:

Recorded, not proposed for fixing. Each is small; together they are why 238
settings are hard to live with.

*All seven are now fixed* — see the Shipped-since table above for the versions.
The bullets below are left as they were written, at 9.99.1129, with a /fixed/
note appended to each; the reasoning is worth more than a tidy list, and two of
the bullets turned out to describe the symptom rather than the cause. The
seventh, the export's scope, was a config-file FORMAT change (=schema_version=
1 → 2) that interacts with everything 9.99.1136-1138 landed — the table
round-trip, the dirty-set prune, the version guard — so it took its own branch
and its own round-trip tests rather than riding along with the dialog fixes.
See [[#item-5][Item 5]] for what shipped and where it departed from the bullet.

*What the dialog had going for it, and why none of this was ever filed:* every
one of these frictions is silent. Nothing errors, nothing is missing from the
DOM, and in the entry-point case the dialog opens and looks entirely normal —
it simply has less in it than the same dialog opened another way. A user who
only ever took one route would never see the difference. **The dialog also had
no test coverage at all**: 238 settings and ~1200 lines of =showModal()=, and
the only thing any spec had ever done with it was avoid it. That is now
=tests/fixtures/settings-dialog.spec.js=.

- *Three of six entry points are second-class.* The ⚙️ toolbar button, =Ctrl+,=
  and =Ctrl+M ,= go through =openSettingsWithConfigButtons()=, which arms the
  config-button observer and passes a =functionRegistry=. The Tampermonkey GM
  menu item and the MusicBrainz /Editing/ menu link call the library's
  =showModal()= with no arguments — so via those two the 💾/📂 buttons never
  appear *and* the 🔧 /Edit Pinned Filter List/ button silently does nothing.
  /Fixed./ Not by threading the registry and the observer through those two
  paths, which this bullet proposed and which would have fixed only the paths
  that exist: the library now REMEMBERS what a consumer registers once
  (=settingsInterface.configure()=, public as =Lib.configureSettings()=) and
  =showModal()= falls back to it, so a seventh entry point is correct by
  construction. =beforeOpen= is try/catch guarded — a consumer's broken hook
  must not cost the user their settings dialog.
- *All 38 sections re-collapse on every open*, and the search filter does not
  expand a section to reveal a match inside it. The two mechanisms both write
  =row.style.display= and the last writer wins. /Fixed, and this bullet named
  the cause exactly./ Collapse state is remembered per section in
  =<scriptId>-section-collapse=, storing only EXPANDED sections so an untouched
  profile — and any section a later version adds — keeps the all-collapsed
  default. Visibility is now computed in ONE pass from three inputs (the
  needle, the changed-only toggle, each section's state), and a filter opens
  the sections holding matches WITHOUT touching their stored state, so clearing
  it restores the user's own layout. Two symptoms this bullet did not mention
  were the same bug: a search left all 38 headers standing with nothing under
  most of them, and a filter matching nothing showed a blank body.
- *RESET is global, widget-only, and still needs a SAVE.* No per-section or
  per-setting reset exists. It also skips =divider=/=function=/=table=, so it
  cannot restore a mangled lookup table. /Half fixed./ Each section header now
  carries a ↺ that resets that section only, and only the settings in it that
  actually differ, saying how many first; =resetSettingWidget()= is factored
  out so the global and per-section paths cannot drift. *Widget-only is kept
  deliberately, not fixed* — a reset that wrote immediately would make a
  mis-click unrecoverable, and the point of scoping it was to make the button
  pressable at all. The =table= carve-out also stands: a lookup table has no
  =default:= to restore, which is [[#F1][F1]]'s closing note.
- *No "changed from default" indication anywhere.* Across 238 settings there is
  no way to see what you have altered without exporting the JSON and diffing it
  against a virgin export — which is another thing [[#item-4][Item 4]]'s snapshot makes
  possible. /Fixed, and [[#F1][F1]] is what made it cheap:/ the comparison
  (=isSchemaDefault()=) already existed for the dirty-set SAVE. A changed row
  gets an orange edge and a bold label, each section header a ● count badge,
  and the toolbar a ● /Changed only/ filter. **The badge is the half that
  matters** — a per-row marker you can only see by opening all 38 sections does
  not answer the question. Recomputed on every widget event rather than
  tracked, because RESET, the colour pickers and the popup sub-editors all
  write values without a common choke point.

* Question 2 — should the defaults be stored in git?

*Yes, as a generated artifact. No, as a runtime source.*

** Why a committed snapshot is worth having

1. *It makes [[#F4][F4]] checkable.* 17 drifted fallbacks exist today and nothing can
   see them, because there is no artifact saying what a default is. This is the
   whole return on the idea.
2. *A default flip becomes legible in review.* Today it is a one-character diff
   inside a 2,813-line block. =bfb8ac3= changed seven at once; =TODO.org= records
   that the =sa_art_idb_metadata_ttl_days= 7 → 30 flip was release-note-worthy
   and had a real dependency (it was only safe *after* the F5 503 fix, because a
   503 was being persisted as "no artwork" and a longer TTL would have
   quadrupled the damage). That is exactly the kind of change that deserves to be
   visible.
3. *It gives the existing export something to diff against.* =_buildConfigJson()=
   already states the diffability contract — 2-space indent, one key per line,
   /"allowing standard line-diff tools to show exactly which settings changed"/.
   A committed defaults file in the same shape turns a user's exported config
   into a readable "here is what I changed" report, which is [[#F5][F5]]'s missing
   changed-from-default indicator arriving by another road.
4. *The repo already does this in three partial forms* —
   =tests/pagetypes.json='s =seedGmValues=, =perfDescriptors.js='s =PICARD_ARMS=/
   =REL_ARMS= named presets, and the shipped export format. What is missing is
   any artifact recording the *defaults themselves*, and any check that fires
   when one changes. =tests/snapshots/registry.org= even states the motive
   outright: =sa_enable_event_parts_extractor= is seeded =true= /"explicitly so
   the baseline does not silently go blank if that default ever flips"/.

** Why it must not be read at runtime

Rejected, with reasons, so it is not re-proposed:

- *=init()= is synchronous at construction.* The library reads every default
  while building =settingsInterface.values=. A remote fetch is async and
  1-hour-cached, so the script would have to either block startup or run a whole
  page load on the wrong defaults.
- *Defaults are behaviour; the changelog and help text are display content.* A
  stale =HELP.txt= is a cosmetic annoyance. A stale defaults file changes what
  the script does, on a network hiccup, with no signal to the user.
- *=default:= is welded to =label=/=type=/=description=/=min=/=max= in one
  object.* Splitting only the defaults out leaves two files that must stay in
  lockstep, with nothing enforcing it — a new failure mode in exchange for
  nothing.
- *It would fix nothing.* [[#F1][F1]] means a user who has pressed SAVE once never reads
  a default again. Moving where defaults live does not change who reads them.
- *[[#F6][F6]] is the empirical version of the same argument*: the one channel that
  would carry a runtime defaults file is seven weeks out of date.

** Why not just commit a live config export

The 💾 export is *your profile*, not the defaults — it encodes personal colour
and shortcut choices. Committed unlabelled it would be read as authoritative and
drift. If one is ever wanted, it belongs beside =PICARD_ARMS=/=REL_ARMS= as a
*named preset*, clearly not "the defaults".

*** Tooltips carry the one thing the UI never showed

Each setting's label, widget, Default cell and Description share ONE string
holding the label, the description, the default and *the GM storage key*. That
key appears nowhere else in the dialog and is exactly what someone hand-editing
an exported config file needs — [[#item-5][Item 5]]'s whole =settings= block is keyed by it,
so the two halves of this branch meet here.
