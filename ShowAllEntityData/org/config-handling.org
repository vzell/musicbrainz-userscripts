* F1 — one SAVE pins every setting forever
:PROPERTIES:
:CUSTOM_ID: F1
:END:

The library's SAVE handler iterates the whole schema rather than a dirty-set,
and =settingsInterface.save()= writes every key it is handed. So the first time
a user presses SAVE — *even having changed nothing* — all ~238 current defaults
freeze into their GM storage, and every default shipped afterwards is invisible
to them permanently.

There is no migration, no key-rename map, and no cleanup of orphaned keys. A
renamed key silently orphans its old value and the new key starts at its default;
=GM_listValues= is not even granted, so nothing could enumerate the strays.

The same applies harder to the 5 =type: 'table'= settings. They are lazy-seeded
from code on first use (=_loadDefaultHiddenColumnsMap()=, =_initRelMappings()='s
=_loadMap()=, =_loadUnicodeCharsMappings()=) and never reconsult the built-ins
again, so new rows shipped in a later version never appear. The only escape is to
delete every row in the table editor, save, and reload so the empty-table
re-seed fires.

This reframes =bfb8ac3='s own release note — /"Only affects fresh installs;
existing explicit user settings are untouched"/ — which is true of more users
than intended: it also spares everyone who pressed SAVE once and changed nothing.

*Not fixed, deliberately.* A dirty-set save plus a migration table is a
shared-library change with a real blast radius (=MB_PageEnhancer= uses the same
schema mechanism) and no obviously-correct answer for values already frozen.
Recorded so the next default flip is proposed with this in view.

* F2 — =number= settings are stored as strings, and four of them are dead
:PROPERTIES:
:CUSTOM_ID: F2
:END:

=input.value= is always a string and the SAVE handler does not coerce it back —
only =checkbox= gets a real type, via =input.checked=. So after *any* SAVE all 38
=number= settings are strings in GM storage, and =settingsInterface.init()= hands
them straight back on the next load without re-coercing.

Four settings are read with the ~typeof v === 'number'~ guard that =CLAUDE.md=
holds up as the *correct* fix for the falsy-zero bug. The guard fails on a
string, so the user's value is silently discarded:

| Setting                            | Read in                     | Effect after the first SAVE                          |
|------------------------------------+-----------------------------+------------------------------------------------------|
| =sa_rel_collapse_threshold=        | =_relTableExpanded()=       | always 200; =0= ("never auto-collapse") does nothing |
| =sa_rel_auto_retry_max_failed=     | =_relAutoRetryMaxFailed()=  | always 25; =0= (disable) does nothing                |
| =sa_rel_completion_toast_duration= | =_showRelCompletionToast()= | always the default                                   |
| =sa_caa_completion_toast_duration= | =_showCaaCompletionToast()= | always the default                                   |

The bitter part: =_relTableExpanded()='s own JSDoc explains at length that it
reads the setting *without* =||= precisely to avoid the =0 || 200= defect — and
the replacement guard fails for the identical input, for a different reason.

*The export path already knows.* =_buildConfigJson()= coerces =number= back with
=Number()= and its comment says why: /"After a RESET → SAVE cycle the settings
dialog stores all values via input.value which is always a string"/. The runtime
read path never got the same treatment.

** Why no test caught it

Fixture specs seed booleans only — =tests/pagetypes.json='s =seedGmValues=
entries and =loadPage.js='s =FIXTURE_SETTINGS_OVERRIDE= are all =true=/=false=.
The post-SAVE string state is therefore never exercised anywhere in the suite.

** The interaction that forces two fixes into one commit

=startFetchingProcess()= reads =Lib.settings.sa_render_threshold || 5000=, which
=CLAUDE.md= already records as the falsy-zero defect. But trace it *post-SAVE*:
the stored value is the string ="0"=, which is *truthy*, so it survives the =||=;
then ="0" > 0= is false and the dialog is skipped. *"0 to disable" currently
works — by accident.*

Coercing to a real =0= would restore the documented bug. So the coercion and the
=||= fix have to ship together, or [[#item-2][Item 2]] is a regression. Same shape at
=renderFinalTable()= and =renderGroupedTable()=, both reading
=sa_chunked_render_threshold || 1000=.

* F3 — config import silently wipes the editable tables
:PROPERTIES:
:CUSTOM_ID: F3
:END:

💾 /Save configuration/ and 📂 /Load configuration/ have shipped since 9.99.273,
injected into the library's settings-modal footer by
=_injectSettingsConfigButtons()=.

=_loadSettingsConfig()= skips only =divider=, then coerces every
non-checkbox/non-number value with =String(value)=. The 5 =type: 'table'=
settings are arrays, so they become strings; =Lib.getTableRows()= rejects the
non-array and the lazy-seeders refill from built-in defaults.

*Net effect: importing a config file silently discards every hand-entered row* in
Default Hidden Columns, the three Relationships icon tables, and the Unicode
picker — the settings that are by far the most laborious to re-enter. Nothing
crashes and nothing warns; the summary dialog reports the keys as applied.

=type: 'function'= is mishandled at both ends too: =_buildConfigJson()= exports
it (its =default:= is an internal method name, not a value) and
=_loadSettingsConfig()= writes that string into GM storage. The library's own
save/snapshot/reset loops all skip =['divider','function','table']=; the
consumer's two loops skip only =divider=.

** Two smaller defects in the same feature

- *The header comment is false.* It claims the export contains /"ONLY non-divider
  keys whose value differs from the schema default, making files short"/.
  =_buildConfigJson()= has no delta filter — it dumps all ~238 keys. The export
  is, already, a full defaults snapshot.
- *Undocumented and untested.* =ShowAllEntityData_HELP.txt= has a /Settings
  dialog safety guards/ section and references ⚙️ Settings 30-odd times, but
  never mentions Save/Load configuration. No file under =tests/= references
  =_buildConfigJson=, =_loadSettingsConfig= or either button label.

* F4 — 17 inline fallbacks disagree with their own schema default

Four descriptions contradict their own =default:= — =sa_ui_h2_hover_bg= and
=sa_ui_h3_hover_bg= both say /"Default is the original MusicBrainz light grey

(=var(--mbtt-gf-bg, #FFD700)= and friends), including =--mbtt-stf-bg, #90ee90=

*This is the finding that justifies [[#item-4][Item 4]].* None of it is visible today: there
is no artifact recording what the defaults are, so nothing can compare a
fallback against one.

* F5 — settings-dialog friction
:PROPERTIES:
:CUSTOM_ID: F5
:END:

Recorded, not proposed for fixing. Each is small; together they are why 238
settings are hard to live with.

- *Three of six entry points are second-class.* The ⚙️ toolbar button, =Ctrl+,=
  and =Ctrl+M ,= go through =openSettingsWithConfigButtons()=, which arms the
  config-button observer and passes a =functionRegistry=. The Tampermonkey GM
  menu item and the MusicBrainz /Editing/ menu link call the library's
  =showModal()= with no arguments — so via those two the 💾/📂 buttons never
  appear *and* the 🔧 /Edit Pinned Filter List/ button silently does nothing.
- *All 38 sections re-collapse on every open*, and the search filter does not
  expand a section to reveal a match inside it. The two mechanisms both write
  =row.style.display= and the last writer wins.
- *RESET is global, widget-only, and still needs a SAVE.* No per-section or
  per-setting reset exists. It also skips =divider=/=function=/=table=, so it
  cannot restore a mangled lookup table.
- *No "changed from default" indication anywhere.* Across 238 settings there is
  no way to see what you have altered without exporting the JSON and diffing it
  against a virgin export — which is another thing [[#item-4][Item 4]]'s snapshot makes
  possible.
- *The Default column is unreliable.* It renders the literal =undefined= for the
  5 table settings, the internal method name for the function one, and a
  placeholder rather than the value for =popup_dialog=.
- *SAVE always reloads the page*, unconditionally, discarding any fetched table —
  while the dialog header claims settings are /"applied IMMEDIATELY upon
  saving"/.
- *The export covers =configSchema= keys only.* Not column visibility per
  pageType (=vz-mb-colvis-*=), the pinned filter list (=persistent-sa-hist-list=),
  filter history (=lru-sa-hist-list=), panel geometry
  (=sa_stats_panel_geometry=, =sa_load_dialog_geometry=), dropdown section
  collapse (=mb_sa_uniq_section_collapse=), the dialog's size and column widths,
  or =vz-lib-prefs=. The pinned filter list is the sharp edge: it is *edited from
  inside the settings dialog*, so a user has every reason to expect it in the
  file.

* Question 2 — should the defaults be stored in git?

*Yes, as a generated artifact. No, as a runtime source.*

** Why a committed snapshot is worth having

1. *It makes [[#F4][F4]] checkable.* 17 drifted fallbacks exist today and nothing can
   see them, because there is no artifact saying what a default is. This is the
   whole return on the idea.
2. *A default flip becomes legible in review.* Today it is a one-character diff
   inside a 2,813-line block. =bfb8ac3= changed seven at once; =TODO.org= records
   that the =sa_art_idb_metadata_ttl_days= 7 → 30 flip was release-note-worthy
   and had a real dependency (it was only safe *after* the F5 503 fix, because a
   503 was being persisted as "no artwork" and a longer TTL would have
   quadrupled the damage). That is exactly the kind of change that deserves to be
   visible.
3. *It gives the existing export something to diff against.* =_buildConfigJson()=
   already states the diffability contract — 2-space indent, one key per line,
   /"allowing standard line-diff tools to show exactly which settings changed"/.
   A committed defaults file in the same shape turns a user's exported config
   into a readable "here is what I changed" report, which is [[#F5][F5]]'s missing
   changed-from-default indicator arriving by another road.
4. *The repo already does this in three partial forms* —
   =tests/pagetypes.json='s =seedGmValues=, =perfDescriptors.js='s =PICARD_ARMS=/
   =REL_ARMS= named presets, and the shipped export format. What is missing is
   any artifact recording the *defaults themselves*, and any check that fires
   when one changes. =tests/snapshots/registry.org= even states the motive
   outright: =sa_enable_event_parts_extractor= is seeded =true= /"explicitly so
   the baseline does not silently go blank if that default ever flips"/.

** Why it must not be read at runtime

Rejected, with reasons, so it is not re-proposed:

- *=init()= is synchronous at construction.* The library reads every default
  while building =settingsInterface.values=. A remote fetch is async and
  1-hour-cached, so the script would have to either block startup or run a whole
  page load on the wrong defaults.
- *Defaults are behaviour; the changelog and help text are display content.* A
  stale =HELP.txt= is a cosmetic annoyance. A stale defaults file changes what
  the script does, on a network hiccup, with no signal to the user.
- *=default:= is welded to =label=/=type=/=description=/=min=/=max= in one
  object.* Splitting only the defaults out leaves two files that must stay in
  lockstep, with nothing enforcing it — a new failure mode in exchange for
  nothing.
- *It would fix nothing.* [[#F1][F1]] means a user who has pressed SAVE once never reads
  a default again. Moving where defaults live does not change who reads them.
- *[[#F6][F6]] is the empirical version of the same argument*: the one channel that
  would carry a runtime defaults file is seven weeks out of date.

** Why not just commit a live config export

The 💾 export is *your profile*, not the defaults — it encodes personal colour
and shortcut choices. Committed unlabelled it would be read as authoritative and
drift. If one is ever wanted, it belongs beside =PICARD_ARMS=/=REL_ARMS= as a
*named preset*, clearly not "the defaults".

** Item 4 — the committed defaults snapshot
:PROPERTIES:
:CUSTOM_ID: item-4
:END:

Branch =feat/config-defaults-snapshot=.

*Stage 1.* =scripts/dump-config-defaults.py= parses =configSchema= out of the
userscript by brace-counting from ~const configSchema = {~ and writes
=ShowAllEntityData_CONFIG_DEFAULTS.json= — a =_meta= block, the section list, and
a sorted =defaults= map, 2-space indent, one key per line, matching the export's
diffability contract so the two files diff directly against each other. *Nothing
in the userscript reads it.* The 5 =type: 'table'= entries carry no =default:=;
record them with their code-level seed source
(=SA_DEFAULT_HIDDEN_COLUMNS_DEFAULT=, =SA_UNICODE_CHARS_DEFAULT=,
=_initRelMappings()='s literals) rather than omitting them silently.

=scripts/audit-config-defaults.py= regenerates into a temp file and fails on any
difference, so a changed =default:= cannot land without its snapshot line — the
same mechanical-guard pattern as =scripts/audit-changelog.py= and
=scripts/audit-docs.py=.

*Stage 2, the payoff.* Extend the audit to cross-check every
=Lib.settings.sa_X || LITERAL= / =?? LITERAL= site against the schema default and
fail on disagreement. That is [[#F4][F4]]'s 17 drifted fallbacks. *Expect the first run
to fail*; fixing those 17 is its own branch after this one, not part of it.

No version bump and no changelog entry for this item — =scripts/= and a generated
artifact are not part of the userscript runtime, the same reasoning =CLAUDE.md=
applies to =tests/=.
