* Answers (2026-10-03, branch =mobile-basics=)
** 1.) The rich tooltip that stays after a tap — FIXED

Root cause (read from the code, then reproduced under emulation): every hover
tooltip opens on =mouseover=/=mouseenter= and closes on =mouseout=/=mouseleave=.
A tap fires /compatibility/ mouse events (=mouseover=, =mouseenter=, …,
=click=), but Firefox Android sends no =mouseout= until you tap somewhere else.
The tooltip opened on the tap that started the fetch and was never closed.
"Desktop site" changes the user agent and the viewport handling, NOT the
input, which is still touch. That is why it made no difference.

Fix: =_isTouchCompatMouseEvent()= (=TOUCH INPUT= section of the userscript).
Every handler that shows a floating tooltip returns early for a tap: the
=[data-mbtt]= rich tooltip, the Relationships tooltips, the artwork hover
preview and its type tooltip, the bigbox and inline-thumbnail tooltips. A real
mouse is unaffected. Spec: =tests/fixtures/touch-tooltip.mobile.spec.js=.

** 2.) Sticky page headers are garbage on the phone — FIXED (off by default on touch)

Root cause, measured (=tests/support/probe-mobile-sph.js=, live release page,
Playwright Pixel 7 emulation): MusicBrainz has no =<meta name="viewport">=. A
phone therefore lays the page out at a fixed width and then ZOOMS OUT to fit
the very wide table. =document.documentElement.clientWidth= still reports the
unzoomed width (412 px) while the visible area is far wider (=innerWidth=
1648 px). The feature clamps every pinned bar to "the viewport width", so it
squeezed the h1 block, the tabs and every h2/h3 bar into a ~264 px column.
That column is the narrow strip in Image #11.

Fix, two parts:
- On a touch-primary device (=(hover: none) and (pointer: coarse)=, still true
  in "Desktop site" mode) the feature is OFF unless the new setting
  =sa_sticky_page_headers_on_touch= (📌 Table stickiness) is ticked. Pinch-zoom
  pans the visible area independently of the layout viewport that
  =position: sticky= pins against, so even with correct widths the bars cannot
  reliably stay in view on a phone.
- Opted in, the bars are now sized against =innerWidth= (the zoomed-out
  area) instead of =clientWidth=. Desktop still uses =clientWidth=, unchanged.

Spec: =tests/fixtures/sticky-page-headers.mobile.spec.js=. Caveat: Firefox
Android's own viewport numbers were not measured (emulation only). If the
opt-in still looks wrong on the phone, the probe's numbers from the real
device are the next step (see 4.).

** 3.) How are userscripts written for mobile? Should they run in "Desktop site" mode?

Most userscripts are written for desktop and simply happen to run on mobile
browsers that support an extension (Firefox Android + Tampermonkey/Violentmonkey,
Chromium forks that allow extensions such as Lemur or Quetta, Safari + the
"Userscripts" app on iOS). There is
no separate "mobile userscript" API. The ones that work well on mobile follow
the same rules as any responsive web code:
- never rely on hover alone. A tap fires compatibility mouse events but no
  "leave" event (see 1.). Use Pointer Events and check =e.pointerType=, or
  =matchMedia('(hover: none)')=;
- never rely on keyboard shortcuts or right-click alone;
- give touch targets about 44 px. Use =touch-action= and Pointer Events for
  drags (=mousedown=/=mousemove= drags do not work with a finger);
- respect the difference between the /layout/ viewport (=clientWidth=,
  =position: fixed/sticky=) and the /visual/ viewport (=window.visualViewport=,
  what pinch-zoom shows).

"Desktop site" mode is NOT required, and for MusicBrainz it changes little:
MB has no viewport meta, so even in "native" mobile mode the browser lays the
page out as a desktop page (about 980 px) and zooms out. "Desktop site" mainly
changes the user agent string, plus how Firefox treats the (absent) viewport
meta. This script does not look at the user agent, so both modes behave the
same. It decides by input capability (hover/pointer media queries), which is
the robust test.

** 4.) Debugging with Playwright for mobile

- Playwright cannot drive Firefox for Android. Its Android support
  (=_android=, experimental) talks to Chrome/WebView over adb only, and Chrome
  for Android cannot run Tampermonkey. So Playwright cannot run the real
  "Firefox Android + Tampermonkey" combination.
- What Playwright CAN do is emulate a phone in desktop Chromium:
  =devices['Pixel 7']= gives a mobile viewport with zoom-out handling
  (=isMobile=), touch (=hasTouch=, =locator.tap()=), a coarse pointer without
  hover, and a mobile UA. That is the new =chromium-mobile= project
  (=npm run test:mobile=; files named =*.mobile.spec.js=). It reproduced both
  bugs.
- For the real phone use Firefox's remote debugging. On the phone: Firefox →
  Settings → "Remote debugging via USB" on, plus Android developer options →
  USB debugging. On the desktop: Firefox (on Windows, since USB does not reach
  WSL2 without usbipd) → =about:debugging= → "Setup" → enable USB → connect →
  inspect the tab. You get the full DevTools console and inspector for the page
  on the phone, including Tampermonkey's injected script. Running
  =tests/support/probe-mobile-sph.js='s =collect()= body in that console gives
  the real-device numbers.

** 5.) Emulating mobile in a desktop browser

Yes:
- Chrome / Vivaldi / Edge: DevTools → device toolbar (Ctrl+Shift+M). Pick a
  device or set a custom size. Touch emulation, DPR and a mobile UA are
  included. Reload after switching so the page sees the mobile viewport.
- Firefox: Responsive Design Mode (Ctrl+Shift+M), with "touch simulation" on
  (the hand icon). This is Gecko, so it is closer to Firefox Android than
  Chrome's emulation, but it is still a desktop engine with desktop viewport
  handling.
- Tampermonkey keeps running in both, so the script can be checked
  interactively there.
Caveat for all of them: they emulate input and size, not Firefox Android's
exact viewport/zoom behaviour. A final check on the phone is still needed for
anything viewport-related.

** 6.) Proper mobile support without breaking desktop — feasible?

Yes, incrementally, under one rule: every mobile change is either gated on
touch capability (=_isTouchPrimaryDevice()=) or only reacts to events a desktop
never produces (a touch contact). Both fixes above follow it. The full
desktop suite (=npm run test:full=) passes unchanged, and the new
=chromium-mobile= project pins the mobile side.

"Desktop site" mode and native mode need no separate work for MusicBrainz
(see 3.). A truly mobile-native layout (reflowing toolbars, a narrow-screen
table view, injecting a viewport meta) would be a large redesign and is not
recommended. The desktop-style page zoomed out is usable.

Backlog of desktop-only interactions still left (none breaks anything; each
is "does not work by finger"):
- column resize drag (=mousedown=/=mousemove= on the header grip): port to
  Pointer Events with =touch-action: none= on the grip;
- settings dialog drag/resize: same;
- Ctrl-M prefix shortcuts and other keyboard shortcuts: no keyboard. Every
  action is also reachable from a button/menu, so low priority;
- information that exists ONLY in a hover tooltip (the action buttons' full
  label, the Relationships filter-match panel, artwork metadata): no way to
  reach it on touch now. A long-press or a tap-to-toggle info affordance would
  restore it;
- tap-spec coverage for the Relationships, bigbox-wrapper and inline-thumbnail
  tooltip guards (guarded, but not pinned by a spec of their own yet).

** 0. Before testing on a device

- Install the *published* copy from =vzell/mb-userscripts=. This repo's copy
  loads the library through a =file:///V:/…= =@require=. On a phone that fails
  silently: =Lib= falls back to a stub, every setting reads its built-in
  default, and ⚙️ does nothing.
- How the script decides it is on a touch device: =_isTouchPrimaryDevice()=,
  which is =matchMedia('(hover: none) and (pointer: coarse)')=. It never looks
  at the user agent, so "Desktop site" on or off makes no difference. A
  touchscreen laptop with a mouse counts as a desktop. A tablet with a paired
  mouse or trackpad may report =hover: hover= and get desktop behaviour, which
  is worth one check.
- How a tap is told apart from a real mouse: =_isTouchCompatMouseEvent()=. It
  is true when there was a =pointerdown= with =pointerType 'touch'= or a
  =touchstart= in the last 800 ms, or when =sourceCapabilities.firesTouchEvents=
  is set.
- Settings that only apply on touch. All are in ⚙️ and all default to *off*.
  On touch the =_on_touch= key REPLACES the plain key (=_popSettingOn()=), and
  the plain key's value is ignored there:

  | Setting                           | When ticked, on a touch device                                                                               | Desktop twin (default)               |
  |-----------------------------------+--------------------------------------------------------------------------------------------------------------+--------------------------------------|
  | =sa_pop_mb_on_touch=              | a tap on an MB entity link in a table opens the preview window instead of the page                           | =sa_pop_mb= (on)                     |
  | =sa_pop_mb_page_on_touch=         | the same for MB links outside tables                                                                         | =sa_pop_mb_page= (on)                |
  | =sa_pop_ext_on_touch=             | a tap on a link to another site opens its preview window                                                     | =sa_pop_ext= (on)                    |
  | =sa_sticky_page_headers_on_touch= | Sticky Page Headers also run on touch (on Firefox Android this did nothing on 2026-10-03; still undiagnosed) | =sa_enable_sticky_page_headers= (on) |

- Settings reach the phone only through ⚙️ → 💾 Save configuration / 📂 Load
  configuration, because each Tampermonkey install has its own storage. See 2.3.
- On Firefox Android the Tampermonkey menu (💾 Browser cache, ⚙️ Userscript
  Settings Manager, 📜 ChangeLog, 🔧 Library Settings) is under the browser
  menu → Extensions → Tampermonkey. 📜 ChangeLog has no in-page button, so that
  menu is its only route.
- MusicBrainz has no =<meta name="viewport">=, so the page is laid out at
  desktop width and then zoomed out. Most =RISK= items below are about what
  happens after you pinch-zoom in. Device emulation in Chrome or Firefox does
  not reproduce Firefox Android's zoom; only the phone does.

** 2. Save / Load from storage

*** 2.1 Save to Disk (📦 → Save, Ctrl+S, or "Save" in the Save-or-Render dialog)

- =saveTableDataToDisk()= turns the rows into JSON and gzips them with pako. It
  wraps the result in a =Blob= (=application/gzip=) with an object URL, and
  =showSaveDialog()= asks for a file name.
- The file is written by a plain =<a download>= and =.click()=, inside the tap
  on the dialog's Save button. That is a user gesture, so mobile browsers allow
  it. There is no File System Access API and no =GM_download= (not granted),
  so nothing needs a fallback for a missing API.
- The name is
  =<prefix><EntityType>-(<Name>)-<Section>[-detail][-(rows)]_<timestamp>.json.gz=
  (=_assembleExportFilename()=). Android does not ask where to put it; it goes
  to Downloads, possibly after a download prompt or snackbar.
- RISK: the object URL is revoked 1000 ms after the click. Android's download
  manager may read the blob later than that, which would give an empty or
  failed download. If a save seems to work but the file is 0 bytes or missing,
  check this first.
- RISK: the filename field is focused on open, so the keyboard pops up (1.11).

*** 2.2 Load from Disk (📦 → Load, Ctrl+L)

- =showLoadFilterDialog()= has its own hidden file input,
  ~accept=".gz,application/gzip,.json"~, opened from its Load button. It reads
  the file with =FileReader= and =pako.ungzip=. You can set a pre-filter
  before the rows are rendered.
- Whether the file is gzip is decided by its NAME (=file.name.endsWith('.gz')=),
  not by the gzip magic bytes.
- RISK: Android's file picker turns =accept= into MIME types. A =.json.gz=
  that the system labels =application/x-gzip= or =application/octet-stream=
  may show greyed out. Some providers (Drive, other cloud apps) hand over a
  display name without =.gz=; the gzip data is then parsed as text, and the
  load fails.
- Save/Load has no drag-and-drop, so touch loses nothing here.
- The toolbar's =#mb-file-input= has an =onchange= that calls
  =loadTableDataFromDisk()=, but nothing ever opens it. It looks like dead
  code.
- RISK: the dialog's filter is focused once the file is read, so the keyboard
  pops up.

*** 2.3 Settings: 💾 Save configuration / 📂 Load configuration (⚙️ dialog footer)

- Writing: =_saveSettingsConfig()= makes a plain JSON blob, and
  =showExportDialog()= downloads it with =<a download>= as
  =<SCRIPT_ID>-config-<ts>.json=. The same 1 s revoke RISK as in 2.1 applies.
- Reading: a hidden ~<input type=file accept=".json,application/json">~ →
  =_loadSettingsConfig()= (=file.text()=), then the page reloads.
- This is the only way to bring desktop settings onto the phone. It also
  carries workspace state: pinned filters, filter history, column visibility
  and layouts (=_CFG_WORKSPACE_GROUPS=). =secret= keys (the Discogs token)
  never travel.

*** 2.4 Browser cache Export / Import (💾 Browser cache → Export/Import, =_idbx*=)

- Export (=_idbxExport()=): a gzip stream (pako) of JSONL lines, with images
  base64-encoded, saved as =sa-cache-<host>-<date>.jsonl.gz=. The whole
  compressed file is held in memory before the download. Images are unticked
  by default; keep them unticked on a phone.
- RISK: the download starts after a long run of async work, so it is outside
  the user gesture and a browser may block or quietly drop it. "Download
  again" is the retry that does count as a gesture; use it if nothing appears.
- The toast says "Your browser asks where to put it". On Android it does not;
  the file goes straight to Downloads (wording, see 4.).
- Import: "Choose a file…" (~accept=".gz,application/gzip"~, with the same
  picker RISK as 2.2), or drag-and-drop on desktop; the button covers touch.
  Here gzip is detected by CONTENT, so a renamed file still loads. The import
  runs in two passes, check then merge, in batches of 200.
- Pinned under emulation by idb-export-import.

*** 2.5 Other downloads

- 📦 → Export (CSV, JSON, Org, HTML) and the Statistics export use the same
  blob + =<a download>= path as 2.1, with the same 1 s revoke RISK and the
  same focused filename field.
- The viewer's Download (D or the button, =_artViewerDownload()=) fetches the
  image first and clicks the link afterwards, which is outside the gesture
  (RISK). Its blob is revoked after 10 s.

*** 2.6 IndexedDB caches on a phone

- =vz-mb-saed-art-cache= holds images, artwork metadata, the Relationships
  WS/2 answers, ms lengths, "Recording of" data and artist works.
  =vz-saed-detail-pages= holds preview pages, MB preview records and the
  favicons of external sites.
- Entries expire by age only: =sa_art_idb_image_ttl_days= 30, metadata 30,
  plus a TTL per store. There is no size cap and no LRU. Expired rows are
  removed when they are read, and by a sweep when the browser is idle
  (=_artIdbSweepExpired()=).
- There is no =QuotaExceededError= handling. With a phone's smaller quota,
  writes fail quietly and the script goes to the network instead. That is
  correct, but you cannot see it happen. The 💾 overview shows usage against
  quota (=navigator.storage.estimate()=); worth a look on the phone after a
  big page.
- IndexedDB belongs to one origin in one browser profile. The desktop cache
  reaches the phone only through 2.4.
- =sa_art_idb_enable= turns the art cache off if storage is tight.

** 3. Other areas

- *Background tabs.* There is no =visibilitychange= or =freeze= handling. The
  page fetch loop, the WS/2 rate gate and the Retry-After waits all run on
  =setTimeout=, so a background tab slows them down a lot. Firefox Android
  may also discard a background tab, and an unsaved render is then gone. Keep
  the tab in front during a long fetch, and Save to Disk before switching
  apps with a big render on screen.
- *New tabs.* "Show single-table", overflow tables
  (=sa_render_overflow_tables_in_new_tab=, on), help, annotation compare and
  the viewer's "Source page" all open a new tab (=window.open=). On a phone
  that puts the rendered page in the background (see the previous point).
  "Show single-table" hands the table over through a GM storage key
  (=mb_sa_subtable_snapshot_<uid>=), which the new tab deletes when it loads.
  If the new tab never loads, the key stays forever, and it can be megabytes;
  nothing sweeps it.
- *Memory.* The thresholds are the desktop ones and have no touch variant:
  =sa_max_page= 50, =sa_render_threshold= 5000, =sa_render_warning_threshold=
  10000. A phone may run out of memory well below them. They are per install,
  so lower them in the phone's own profile.
- *Native dialogs.* The navigation guard (=initNavigationGuard()=) uses
  =window.confirm()=, and about a dozen =alert()= calls report errors in
  export, save and load. Firefox Android shows them as its own sheets. That
  works, but they block the page.
- *Where custom dialogs land.* =Lib.showCustomConfirm/Alert= and the
  threshold dialogs are placed using =innerWidth/innerHeight=, and their top
  is not kept on screen. While pinch-zoomed they may open partly off-screen;
  zoom out to find them. HELP's troubleshooting note that "a dialog may be
  waiting for you" matters even more on a phone.
- *Double-tap.* With no viewport meta, a double-tap zooms the page. So
  anything that relies on =dblclick= is unreliable. That is the 📊 grip reset
  and the pinned-filter editor's row edit; the row edit also has a button, the
  grip reset does not.
- *=title= tooltips.* Mobile browsers never show them, so information the
  script keeps only in tooltips is invisible on touch (collected in 4.).
- *Tablets.* A Bluetooth keyboard brings the shortcuts back. A trackpad or
  mouse may switch the device to =hover: hover=, and with it to desktop
  behaviour. Check one tablet both ways.
- *Clipboard.* The script never uses the clipboard, so there is no
  secure-context or permission problem.
- *iframes.* The preview window's "Live page" is a sandboxed =srcdoc= iframe
  that the script does not run in. The header has no =@noframes=; the
  Jungleland and brucespringsteen.it gates check =window.top= themselves.
- *Find in page.* The browser's find skips rows that a filter hides
  (=display: none=). That is expected, but it can surprise on a phone.
- *Picard* ♪ needs Picard on the same machine, so it does not apply on a
  phone.
- *Other sites* (SL, JL, KF, BB) use the same engine and follow the same touch
  rules. The SL scope bar and the BB side bar handle are plain clicks. On
  touch, only their preview links inside a table body count.

** 4. Gaps and suspected bugs, by priority

For each item: what it is, where it is, whether the code confirms it, and a
suggested direction. Nothing here is fixed yet.

1. *The keyboard pops up when these open.* Confirmed in the code. These
   =.focus()= calls bypass =_autoFocusInput()=:
   - =showSaveDialog()= and =showExportDialog()=: the filename field.
   - =showLoadFilterDialog()=: its filter, in phase 2.
   - The Statistics panel's quick filter.
   - =createInfoDialog()='s quick filter (Help, Shortcuts, …).
   - =showEditPersistentListDialog()=: =eplQF=.
   - =createFilterHistoryWidget()=: =_histOpen= focuses the quick filter, and
     =_applyEntry= focuses the filter.
   - In the library: the settings dialog's search field.

   Direction: the same fix as on 2026-10-03, that is, route them through
   =_autoFocusInput()=. The library needs its own
   =(hover: none) and (pointer: coarse)= check. Pin it the same way as
   =filter-autofocus.mobile.spec.js=.
2. *The blob is revoked 1 s after the download click.* Confirmed in the code
   (=showSaveDialog()=, =showExportDialog()=); what this does on a device is
   unconfirmed. Direction: revoke later (for example after 60 s, or on
   =pagehide=), as =_artViewerDownload()= already waits 10 s.
3. *📊 closes when its list is scrolled past its end.* Confirmed: any page
   scroll that moves the 📊 button closes it, and the script sets no
   =overscroll-behavior= anywhere. Unconfirmed on a device. Direction:
   =overscroll-behavior: contain= on the panel's scroll area.
4. *The 🔍 prefix and Android Backspace.* Two parts of the code are
   confirmed: the guard checks =e.key=, and the =input= safety net adds a whole
   new prefix whenever the field no longer starts with one. So if the soft
   keyboard's Backspace (=key "Unidentified"=) deletes the space of the prefix,
   the field becomes "🔍 🔍" and filters for "🔍". Unconfirmed on a device.
   Direction: guard in =beforeinput= (=inputType deleteContentBackward=), or
   have the =input= handler repair the existing prefix instead of adding a new
   one.
5. *The column-mode pop-up closes on every window resize.* Confirmed
   (=_closeColModePop()= on =resize=). The keyboard showing or hiding, or a
   rotation, closes it. Direction: on touch, ignore resizes that only change
   the height, or move the pop-up instead of closing it.
6. *Drags work only with a mouse.* Confirmed for:
   - the column width grip (=makeColumnsResizable()=);
   - the ⋮ grips of the GF and STF;
   - moving and resizing every dialog: settings, info window, Statistics, 👁️
     menu, save/load, the table editors.

   Direction: Pointer Events plus =touch-action: none=, modelled on
   =_wireUvdResizeGrip()=.
7. *Information that exists only in tooltips.* This follows from the design,
   since tooltips are suppressed on a tap. Lost on touch:
   - the action buttons' full labels;
   - finding explanations, both in the menu rows and on tinted cells;
   - the Relationships filter-match panels;
   - row-count details;
   - 📊 entry descriptions;
   - "Liner notes" cards;
   - the preview behind the inline thumbnails.

   Direction: one shared long-press or ⓘ affordance that shows the
   =data-mbtt= / =data-mb-tip= card pinned, with an explicit close.
8. *No touch path for "all peers".* That covers:
   - Ctrl+click on h2s, inline sidebar cards, Credits/Annotation sub-headings
     and 📊 sections;
   - Cc/Rx/Ex applied page-wide;
   - Ctrl+2 / Ctrl+3;
   - multi-column sort (Ctrl+click) and length sort (Alt+click).

   Direction: low priority. Menu rows such as 🛠 View → "Expand/collapse all
   h2" would cover the common cases.
9. *The progress card cannot be reopened on touch.* Confirmed: =_ajInitHover()=

10. *Inline thumbnails ignore a tap.* Confirmed: =.mb-caa-inline-ph= has no

11. *The Relationships cell is hard to tap.* The cell is =font-size: 0=, so

    a ⟳ on touch.
12. *Leftover single-table snapshot keys.* Confirmed:
    =openSubtableAsSingleTableTab()= writes them, and only the tab that reads
    one deletes it. Direction: at start-up, sweep
    =mb_sa_subtable_snapshot_*= keys older than a day.
13. *Background tabs are not handled.* Confirmed: there is no
    =visibilitychange= listener. Direction: at least warn when a fetch is
    running and the tab is hidden, or offer Save to Disk.
14. *Text that is wrong, on desktop too:*
    - HELP §Sorting says "Click a column header to sort"; only the ⇅ ▲ ▼
      glyphs sort.
    - The tooltip of =.mb-master-toggle= promises Ctrl+Click for "ALL", but
      its handler never reads =ctrlKey=.
    - The cache export toast says "Your browser asks where to put it". That
      is not true on Android, or in any browser that saves straight to
      Downloads.
    - HELP §"On a phone or tablet" says nothing about Save/Load, downloads,
      moving settings to the phone, or the background-tab risk.
15. *Spec gaps,* already noted on 2026-10-03: no mobile spec pins the
    Relationships tooltip guard, the bigbox guard or the inline-thumbnail
    guard.
