** Shared runtime (all scripts)

*** Request gate — =dev/net/mb-gate.mjs=, inlined as ST-NET (EH:59-284)

- *State*: cross-tab, in localStorage =mbu:mb-gate= ={tat, cool, hot, lead, leadUntil}=, read-modify-written under a
  Web Lock =navigator.locks.request('mbu-mb-gate')= (3 s abort, unlocked fallback). Only =/ws/2= is gated (=mbnGated=).
- *Pacing*: GCRA-style, =MBN_GAP=1000= ms. Background requests may burst to =MBN_BURST=3=; foreground requests book at
  once. A slot is reserved first, then waited for in 250 ms slices so cancellation is prompt (=mbnSlot= ≈94).
  *Since =5d4d464= (2026-11-23, #1095)*: =MBN_GAP=125= ms and =MBN_BURST=4=, eight starts a second sustained (anchor
  =gate-gap-125=). Its comment: MusicBrainz's 503s come from its own load (=X-RateLimit-Who: global=) whatever the
  pace, and Credit Hoarder's preflight took 52 s instead of 173 s. Interactive requests book their own line
  (=itat=/=ilast=) beside the background one (=tat=/=last=); while =hot= no burst after a hold (#1096); retries and
  searches waiting out a hold go to the head (=rhead=, =bslip=). The lock is kept 30 ms after a booking
  (=MBN_LOCK_HOLD=), so the write reaches other tabs before the next holder reads (=gate-lock-hold=). Reads that differ
  only in =inc= merge after 100 ms (#1094/#1097), and a 5-minute Cache Storage cache =mbu:mb-gate-cache= answers a
  repeated read until any write (#1098, =gate-edit-epoch=). String Theory has a gate log viewer (=gatelog.js=, #1093).
  Same protocol version 1; the new fields are written beside the old ones (TODO "The shared gate at eight a second").
- *Transport* (since =1df6193=): the gate's own requests go through =GM_xmlhttpRequest= with a
  =User-Agent= header (=mbnWsFetch=; EH got =@connect musicbrainz.org=), no longer the page's =fetch()=.
- *Lead*: =mbnLead(token, ms)= (≈126), capped at 10 s. The tab whose page is loading leads, and every other script and
  tab waits. A hidden tab never leads.
- *429/503* (=mbnAnswer= ≈132):
  - honours =Retry-After= (seconds or a date);
  - =hot= rises by one per throttle /episode/ (max 6) and resets after 30 s of quiet;
  - hold = =min(max(1 s, RA) × max(1, hot), 60 s)=, written to the shared =cool=, so *every script in every tab holds*
    (since =5d4d464=: without the =hot= factor when the 503 carries =Retry-After= or =X-RateLimit-Who: global=, and a
    =search-shed= 503 holds searches only, in =scool=/=shot=, anchor =gate-search-shed=);
  - =mbnFetch= retries up to 4 times.
- *Browser check*: =mbnIsCheck= / =mbnReverify= (≈193-243) pass "Verifying your browser" in a hidden 1×1 same-origin
  iframe, then retry.
- *SAED today*: a per-tab, in-memory slot (=_relAwaitRateSlot=, 1100 ms), =_ws2GetJson= transient retry,
  =_parseRetryAfterMs=. =_mbIsBrowserCheck= only tells the user to open the page.
- *Verdict*: *adopt*. Booking SAED's ws/2 requests in the same =mbu:mb-gate= key makes SAED pace together with all of
  majkinetor's scripts. Also take the lead idea, the per-episode escalation and the iframe re-verify. SAED's main fetch
  is native HTML, which this gate does not cover; ws/2-heavy columns (Relationships, popups, Discogs MB column) are.

Hi Miodrag - @majkinetor,

I found the cause of this one, and I think the fix on your side is two lines. The wider list of things
between String Theory and SAED is now in one place, https://github.com/majkinetor/musicbrainz-userscripts/issues/938. This reply is only about this race.

Measured with ISRC Scout **2026.11.06.170000** (String Theory 2026.11.06.130902, commit `1df6193`) on
release `22a6802f-d22e-4f47-9f22-6aac257a4194`.

## Cause

SAED's rendered tracklist is a copy of MusicBrainz's: it keeps the `tr.subh` header rows and each row's
track-MBID `id`. To ISRC Scout it therefore looks like a tracklist of its own:

- `showTrackData()` removes **every** `.ii-col` in the document, restores the colspans, and refills;
- the `MutationObserver` on `documentElement` then runs `fillTrackData()`, which adds bare cells to every
  table holding a row whose `id` is a track MBID, and bumps its `thead th[colspan]`.

So it depends on who finishes last. If ISRC Scout's columns are in before SAED renders, SAED copies them
and turns them into normal SAED columns (sortable, 📊, filterable), and all is fine. If SAED renders
first, or ISRC Scout refreshes later (a settled load, closing your window, a settings change), your code
wipes SAED's cells and adds plain ones. Those have no sort glyphs, no 📊, and the colspans are one too
wide. That is exactly what the screenshots above show.

## Proposal

No API needed, one marker is enough. SAED would put `data-mbu-foreign="saed"` on its rendered section and
tables (the name is up to you), and ISRC Scout leaves everything inside it alone:

```diff
 function fillTrackData() {
```

  Thanks again for "use anything from my repo": SAED 9.99.1650 now has your lock race and =mbnSleep()= (credited
  in its header). While porting I went through =dev/net/mb-gate.mjs= (=687b8b1=, unchanged since =0693aea=; the
  copies in Event Horizon, String Theory and ISRC Scout are the same) and found a few things. All of them are in
  how a script reads the shared schedule, so none needs a version bump.

  *1. The hold cap does not cap.*
  - The booking takes the stored value: =at = Math.max(at, cool)=, then =s.tat = Math.max(tat, at) + MBN_GAP=. A
    broken =cool= ten minutes out is booked as a ten-minute wait, and =tat= carries it to every booking after.
  - The wait's cap, =cool = Math.min(cool, now + MBN_MAX_HOLD)=, moves on with =now= every slice, so the loop
    still waits the whole ten minutes.
  - The lead wait has the same shape: =Math.min((s.leadUntil || 0) - Date.now(), MBN_MAX_LEAD)= is re-read every
    slice, so a =leadUntil= ten minutes out holds every background request for ten minutes.
  SAED now counts a stored =cool= for at most 60 s from the moment the tab first read that value, at the booking
  and in the wait. Every writer sets =max(cool, now + ms)= with =ms ≤ MBN_MAX_HOLD=, so a real hold is never cut.
  I'll do the same for =leadUntil= (at most =MBN_MAX_LEAD=).

  *2. A step of the wall clock.* Everything runs on =Date.now()=, mine included. On WSL I have seen the clock step
  +16.8 s and back every few seconds (Hyper-V's time sync against systemd-timesyncd), and laptops coming out of
  sleep can step too. What a step does today:
  - a booking made inside a forward step stores =tat=, =cool= or =leadUntil= that much ahead, and every script
    waits it out once the clock is back (the first-seen bound in 1 limits that to one hold or one lead);
  - a forward step during a wait ends a 503 hold early;
  - a backward step during =mbnSleep()= stretches even a 250 ms slice by the whole step, because it sleeps until
    =Date.now() >= end=.
  Storing =performance.now()= values would not work across tabs (each tab's =timeOrigin= is its own start), so
  I'd keep the stored format and fix the reading side: =mbnSleep()= sleeps until =performance.now() + ms=, and
  the booked slot becomes a =performance.now()= deadline once, at the booking, moved later only by a newly seen
  =cool=.

  *Not changed, on purpose:* =tat= is not capped on read. A long real queue is normal (one =MBN_GAP= per booking
  waiting in any tab), and a capped =tat= written back would let new bookings overlap the queue.

  *Questions:*
  1. Does this fit how you see the gate, or would you rather put it into =mb-gate.mjs= first, and I port it?
  2. Should the gate also lower a broken =cool= in storage (=cool = now + MBN_MAX_HOLD= under the lock), so a tab
     opened later does not wait its minute again? That is a new write in v1, so I left it out.

** DONE time sync

● I can't fully prove the mechanism from inside WSL, but the evidence narrows it down a lot.

  What's established on petri:
  - The spikes need WSL's own NTP client. With systemd-timesyncd running: 7 jumps in 30 s. Stopped: 0. The system journal recorded the same thing, "Time jumped backwards" every 5 s.
  - WSL's kernel also takes its time from Windows: hv_utils.timesync_implicit=1, Hyper-V's time service, which sends a sample every 5 seconds. That's the spikes' rhythm.
  - Windows itself has never synchronised its clock: w32tm reports "Local CMOS Clock", "not synchronized", "Last Successful Sync Time: unspecified".

  The most likely story:
  1. WSL's clock had two owners fighting over it: Hyper-V's samples from the Windows side every 5 s, and timesyncd steering it to internet time. They disagreed by 16.8 s, so each sample pushed the clock one way and it was pulled straight back.
  2. The 10 days powered off explain the 16.8 s. While a PC is off, only the battery-backed hardware clock keeps time, and those drift by typically 1–2 s a day; 16.8 s over 10 days is 1.7 s a day. With Windows not syncing, nothing corrected that drift after the restart. So one
     side carried the drifted hardware time and the other the correct internet time.
  3. One thing I can't resolve: Windows' displayed time agreed with internet time to within about a second when I compared them. So the drifted value most likely sits in what Hyper-V hands WSL, or in the emulated hardware clock, rather than in Windows' clock display. The exact
     kernel-level interaction would need Windows-side logs.

  Why NB-3641 never showed it: I can't look at that machine, but the candidates are concrete:
  - It runs most days, so its clock never drifts far.
  - Its Windows time service may actually be syncing.
  - Its WSL may not run systemd, and with it timesyncd, at all.

  You can check all three there with systemctl is-active systemd-timesyncd in WSL and w32tm /query /status in Windows.

  General solution: one owner for the clock, and a Windows that syncs.
  1. In WSL, leave the clock to Windows permanently:
     sudo systemctl disable --now systemd-timesyncd
     Today's stop lasts only until the next WSL restart.
  2. In Windows, make the time service actually sync, in an admin PowerShell:
  w32tm /config /manualpeerlist:"pool.ntp.org,0x8" /syncfromflags:manual /update
  Restart-Service w32time
  w32tm /resync /force
     Also check Settings → Time & language → "Set time automatically", then "Sync now". Once Windows syncs, it also corrects the hardware clock, so the next long shutdown starts from a correct clock.
  3. Verify: w32tm /query /status should name an NTP server and a recent sync time. In WSL the clock check should report 0 jumps.
  4. In the code, SAED's own request pacing is already immune since c8e71ba8. The shared gate with majkinetor's scripts still reads the wall clock. He could make the same performance.timeOrigin + performance.now() change on his side; I can draft that for #938 if you want.

  If you like, I'll keep the clock check as a reusable script (scripts/check-clock-jumps.js, with a line in tests/README.org), so a "flaky" run on a freshly booted machine can be checked in 30 seconds.
