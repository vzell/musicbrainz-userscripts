* Ground rules for any new type
** Branching and versions
- Feature branch, never =main=. Userscript: WIP entries in
  =ShowAllEntityData_CHANGELOG.wip.json=, no =@version= bump on the branch.
- The library has no WIP mechanism. Its version is bumped ON THE BRANCH, in
  THREE places that must agree: =// @version=, =LIBRARY_VERSION=, a new top
  entry in =changelog_library=. Minor version for a new type (4.5.0, …).
- This repo's =@require= is the local =file:///V:/…/lib/VZ_MBLibrary.user.js=
  (so a live browser check exercises the working copy); the published copy
  must carry the network URL. =scripts/check-publish-ready.py= before any
  republish.

** Degrade path, decided with =select=
An older library renders any unknown type as a plain text box (the final
=else= of the widget chain). So the userscript NEVER trusts a stored value of a
new type: it reads through a validating helper (=_selectSetting()= is the
model) and puts stored values in canonical form on load
(=_canonicalizeSelectSettings()=, called right after
=_coerceNumericSettings()=). Then the publish order of library and userscript
does not matter, and a user on the old library still gets correct behaviour.

** Every place a new type must be considered
Library (=lib/VZ_MBLibrary.user.js=, inside =settingsInterface=):
- =showModal()= widget chain: the =isCheck= … =isTable=, =isSelect= flags and
  the =if (isCheck) … else= branches. A widget that is not ONE element with a
  =.value= puts a hidden input under =<scriptId>-input-<key>= (the =select= and
  =popup_dialog= pattern), so SAVE, =takeSnapshot=, =hasUnsavedChanges=,
  =rowWidgetValue= (changed marks) and =isSchemaDefault()= need nothing new.
- The Default column: =hasComparableDefault=, =defaultText=, =defaultNote=
  (also feeds =data-vz-default= and the search).
- =widgetTitle()= (the row tooltip; =select= adds a "Choices:" line).
- Post-render wiring: delegated on =settingsBodyEl= (the =select segments=
  block is the model), never per widget.
- The SAVE handler (=<scriptId>-save-btn= onclick): typed values (=select=
  maps the hidden text back to the option's own value).
- =resetSettingWidget()=: any widget whose visible state is not the hidden
  input must be re-synced there (=syncSelectSegments()=); the global RESET and
  the per-section ↺ both go through it.
- =settingsEscHandler=: a focused control of the new widget must BLUR on
  Escape, not close the dialog.
- The per-row widget CSS block (after =/* ── Per-row setting widgets ── */=).
  No backtick in a =GM_addStyle= comment.
- The =showModal= JSDoc list of widget types.
- Every hoverable control needs a =title= (=settings-dialog-header.spec.js=
  "every settings row has a tooltip on the widget you can actually hover"
  caught segments without one).

Userscript (=ShowAllEntityData.user.js=):
- =_applyConfigSettings()= (📂 import): a branch for the type; an invalid value
  counts as =invalid=, never falls into the =String()= catch-all.
- =_buildConfigJson()= (💾 export): export what the code acts on.
- =_coerceNumericSettings()= / =_canonicalizeSelectSettings()=: the on-load
  pass for the type.
- =_settingsValueMatches()=, =_migrateFrozenSettings()= pass 3: string
  compare; check the type does not need its own rule.
- =_maskSecretSettingInputs()= sets =input.type='password'= — only valid on a
  text input; keep =secret= off any other widget.
- The test hooks under =window.__saTest= (=numericSettings()=,
  =selectSettings()=): add one per type that has an on-load pass.

Tooling (no type list anywhere, so a new type is accepted; still run them):
- =scripts/dump-config-defaults.py= (a new count in =_meta.types=),
  =scripts/dump-default-history.py= (=_NON_VALUE_TYPES= = divider, function,
  table), =scripts/audit-config-defaults.py=. A new type must have a =default=.

** Proving it
- Specs: =tests/fixtures/settings-dialog.spec.js= drives the REAL library
  against the real schema (the "type: select" describe is the model:
  RENDER, PICK + SAVE, RESET + SAVE, KEYBOARD, ON LOAD, STORED VALUES);
  =config-import-export.spec.js= for the config file.
- Harness traps met while doing =select=:
  - =settingsOverride= is re-seeded on EVERY load, so a SAVE that reloads
    brings a seeded value back. Seed with =GM_setValue= on load 1, then load
    the shell again (=loadShell()= twice) — never =page.reload()=, which loses
    the =addScriptTag= injection.
  - A SAVE that changed nothing does not reload; one that did, does.
  - Lint forbids =waitForSelector=/=waitForTimeout= beyond the baseline: use
    =expect(...).toHaveCount(0)= and =expect.poll()=.
- Mutations: one JSON per type in =scripts/mutations/= (=settings-select.json=
  is the model). A mutation edits ONE file, so a library guard that the
  userscript's on-load pass already covers can only be recorded
  =expect: pass= — see item 9.
- =npm run test:full= through =scripts/run-test-full.py=, then the user's
  live check, then ask before merging.

* TODO 2. =number=: enforce =min=, =max=, =step=
*Problem.* =min=/=max= are only HTML attributes on =input type=number=;
nothing validates, so SAVE stores 3500 for a max of 3000. Worse, a missing
=max= is rendered as =max="100"= (=cfg.max || 100=), and =min= as
=cfg.min || 0=. There is no =step=, so fractional settings
(=sa_ars_column_max_height_em= 5.6, =sa_annotation_column_max_height_em=)
show the browser's step-mismatch state.

*Verify first* (the survey was by grep, 2026-10-15): which numbers have
=min= but no =max= (=sa_rel_auto_retry_max_failed=, =sa_pop_mb_ttl_hours=,
=sa_pop_ext_ttl_hours= were found) and whether any stored/default value
exceeds 100 — those rows are drawn invalid today.

*Library.*
- Omit the attribute when the schema has no bound (no silent 100). Add =step=
  (default 1; =any= for fractional).
- On input: mark the widget invalid (class + message line in the row, as in
  the mockup) when out of range or not a number.
- On SAVE: refuse an invalid number — keep the last valid value, and say so
  (a note in the dialog, not a silent clamp). Decide: refuse the whole SAVE,
  or save the rest and keep that key? (Mockup says "SAVE keeps the last valid
  value".)
- =resetSettingWidget()= clears the invalid state.

*Userscript.*
- Add bounds to numbers that have none: =sa_max_page=, =sa_auto_expand=,
  =sa_render_threshold=, =sa_render_warning_threshold=,
  =sa_chunked_render_threshold=, =sa_auto_resize_columns_threshold=,
  =sa_event_rg_search_hints=, =sa_rg_window_max_releases=,
  =sa_picard_tagger_default_port= / =sa_picard_tagger_max_port= (1–65535).
- =_coerceNumericSettings()=: also clamp (or fall back to the default for) a
  stored value outside the bounds? Decide; the import already rejects NaN.
- Remember the =|| default= hazard: =0= is falsy (=sa_render_threshold=).

*Tests.* settings-dialog: an out-of-range entry is marked, SAVE does not store
it; a missing =max= renders no =max=; =step= on a fractional row. Import: an
out-of-range number is =invalid=. Mutations for each guard.

* TODO 4. Checkbox pairs/triples → =select= (needs a fold migration)
*Why a separate item.* These are two or three stored keys becoming ONE, and
=_SETTINGS_MIGRATIONS= cannot express that: its shape is ={key, was: [...]}=,
it reads only that key and can only DELETE it (reset to default). There is no
way today to read old key A and B and write new key C.

*Mechanism first (userscript, =_migrateFrozenSettings()= and friends).*
- A new entry kind, e.g. ={fold: 'sa_new', from: ['sa_a', 'sa_b'], map: (a, b) => value}=,
  run once under a raised =_SETTINGS_MIGRATION_LEVEL=, with the old values
  backed up to =sa_settings_migration_backup= first (as the existing pass
  does), the old keys deleted and added to =_SETTINGS_ORPHANED_KEYS=.
- Must run BEFORE =_coerceNumericSettings()= / =_canonicalizeSelectSettings()=.
- A profile where the old keys are absent (defaults) must write nothing.
- Config import of an OLD file still carrying the old keys: map them too, or
  report them as skipped? Decide.

* TODO 5. =showIf= dependent rows
*Problem.* About thirty labels start with "…" and say "needs the setting
above" in prose; the dialog shows them live and editable while the parent is
off. =applyVisibility()= has no notion of one row depending on another.
- Schema: =showIf: 'sa_parent'= (truthy), later maybe
  =showIf: {key: 'sa_x', is: 'info'}= for a select parent.
- Library: greyed and =disabled= (the mockup), NOT hidden — hiding would
  fight search and "Changed only". Re-evaluate from the delegated
  =input/change= listener. Rule from CLAUDE.md: only =applyVisibility()= may
  assign =display= to a row; =disabled= + a class is a different channel, keep
  it that way.
- SAVE still stores a disabled child's value (it is the user's choice for when
  the parent comes back on).
- The "changed" marks and section badges: does a disabled changed child
  count? Decide (probably yes: it is still stored).
- Candidates: every "…" child row, e.g. =sa_sidebar_inline_collapsed=,
  =sa_sidebar_inline_cards_open=, =sa_sidebar_inline_release_facts_open=
  (parent =sa_sidebar_inline_main=), the =*_on_touch= and =*_without_ctrl=
  rows, the findings tint rows. Grep labels starting with "…".

* TODO 8. =key_value= (ordered pairs)

* TODO 9. A library-only test harness
=settings-select.json= records one honest =expect: pass=: breaking the
library's case-insensitive =selectValue()= is invisible because
ShowAllEntityData's =_canonicalizeSelectSettings()= fixes the stored value
first. A consumer without that pass (MB_PageEnhancer) would be exposed, and no
spec can see it. Options:
- a tiny fixture consumer page (a 5-key schema, every type) loaded with the
  real library and the GM stubs, so library guards are tested on their own;
- or let =mutation-check.py= accept edits in two files per mutation.
Either would also make items 2–8 testable without the 438-key schema.
