* The question

For every place the script talks to the network: what happens on a 503 (or
another transient failure), what does the end user SEE, can they retry, at
which level (page, table/sub-table, row, cell), and what could be automated
without being intrusive.

* Findings, most serious first

** DONE F1 — a failed HTML page silently truncates the result, and the status line says it completed  (confirmed by a spec; fixed)

The pagination loop does =pagesProcessed++= /before/ fetching page =p=, and its
catch block is =Lib.error(...); break;=. After the =break= the loop falls
through to render whatever was accumulated, and the final status reads
=Loaded ${pagesProcessed} pages (${totalRows} rows)=. So:

- =pagesProcessed= counts the page that FAILED;
- nothing on screen distinguishes "5 of 5 pages" from "2 of 5 pages, then a 503";
- the Save-to-Disk path takes the same route, so a truncated set may be
  written to disk as if complete (to confirm — not traced to the write).

This is the only finding that can make a user believe wrong DATA is complete,
which is why it outranks the rest. =fetchHtml()= itself has no retry: a single
503 on page 4 of 40 ends the whole run at page 3.

*Fixed on =fix/html-fetch-transient=, together with F2 and F3.* The third
bullet is now CONFIRMED and fixed: the Save-to-Disk path did take the same
route, and a truncated set was written with no marker at all.

- =fetchHtml()= retries a transient status or a thrown request up to
  =_HTML_FETCH_TRIES= (3) times, backing off =_HTML_FETCH_BACKOFF_MS= (2 s then
  5 s) and honouring =Retry-After= as a floor via item 1's helpers. A pressed
  Stop interrupts the backoff (=_sleepInterruptible()=). It throws an Error
  carrying =status=, so callers classify without parsing =message=.
- =pagesProcessed++= moved to AFTER the fetch, so the failed page is no longer
  counted as loaded.
- A =fetchIncomplete= record ({=pageFailure=, =maxPageUnknown=,
  =preFetchIncomplete=}) is filled during the run and rendered by ONE resolver,
  =_fetchIncompleteSummary()=, for every surface: the status line, the
  render-decision dialog, the save-without-rendering line, the disk-load line
  and the saved file's own header. Four places printed "Loaded N pages"
  independently before.
- The saved file gains an optional =incomplete= block. Absent on a clean run
  and in every file written before it existed, so =!incomplete= keeps its old
  meaning and *no format-version bump was needed*. A loaded file's marker is
  carried forward, so re-saving a partial file keeps it partial.

*No shared retry budget across pages, and none is needed* (open question 4,
answered): every caller stops at its first failed page, so exactly one page can
ever pay the retries. A genuinely down site costs three attempts in total, not
three per page.

** DONE F2 — =fetchMaxPageGeneric()= turns a fetch failure into "1 page"  (confirmed by a spec; fixed)

Its catch returned =1=. A 503 on the page-count request made the script fetch
page 1 only and report success. Same silent-truncation class as F1, one step
earlier, and it also had no retry.

*Fixed on =fix/html-fetch-transient=.* It now returns ={maxPage, ok, detail}=.
=maxPage= is still =1= on failure, so a caller that ignores =ok= behaves exactly
as before and nothing silently fetches zero pages; =ok: false= is what lets the
status line say "of an unknown total" instead of "1 of 1 pages". The old JSDoc
said "defaults to 1 on error", which is how this survived — it read as a
decision rather than the bug it was.

Note the *spec had to be rewritten once* because the F1 retry absorbed it:
failing one attempt of the count request is no longer enough, so the test
exhausts all three and lets the loop's own page-1 request (the same URL)
succeed.

** DONE F3 — the artist-releasegroups pre-fetch pass =break=s on error  (traced, confirmed by a spec; fixed)

The pass builds the "official headers" set that the main pass uses. A break
leaves the set incomplete.

*Effect traced (open question 2, answered): it is worse than truncation.* The
consumer walks =h3_all_category_header_array= and treats entries matching the
FRONT of the official array in sequence as official; the first mismatch starts
the non-official section. So a set short by two categories does not shorten the
Official view — it files two genuinely-official categories under
Non-Official, confidently and silently. And =discOfficialCategories= persists
that to disk, so the wrong split outlives the session.

*Fixed on =fix/html-fetch-transient=:* an incomplete pass DISCARDS its partial
set. Every consumer — the view-button builder, the two re-render walks and
=saveTableDataToDisk()= — is gated on =length > 0=, so discarding switches
all of them off at once, including the one that would have persisted the wrong
split. Threading a flag out instead would have missed the save path, which does
not run inside =startFetchingProcess()=.

The rows themselves are untouched (the main pass is independent), so this case
is marked ⚠️ but deliberately NOT called INCOMPLETE — see
=_fetchIncompleteSummary()='s =dataIncomplete=. The spec carries a CONTROL test
asserting a clean run DOES build the buttons, without which the suppression
test would pass on a fixture that never had them.

** DONE F4 — the release-events column gives up silently and uses a weaker path than its siblings  (confirmed by a spec; fixed)

=initReleaseEventsColumn()= called =fetch()= directly rather than
=_ws2GetJson()=, so it got neither the 3-attempt retry nor error
classification, and a failure ended in =_dbg(...)= — gated behind a setting, so
silent by default — then =return=. The column stayed empty with nothing to tell
the user why, and there was no retry short of a reload. It is one request per
page, which is exactly what made it so cheap to lose.

*Fixed on =fix/release-events-transient=.* What shipped:

- Routed through =_ws2GetJson()= (=_RE_WS2_TRIES= 3, =_RE_WS2_BACKOFF_MS=
  1100), so it gains the transient classification and =Retry-After= for free.
  Deliberately NOT on =_relAwaitRateSlot()=: that gate spaces a STREAM of one
  request per entity, and this is one request for the whole page. The old bare
  =fetch()= did not join it either, so nothing regressed.
- A failure leaves the cells UNPOPULATED and un-=reDone=, which is what lets
  the retry — or any later render path — pick every one of them up. Marking
  them done would have looked entirely settled and been permanently wrong.
- *The first column-level retry affordance in the script.* =.mb-re-col-hdr-btn=,
  the eighth member of the =.mb-col-hdr-flex= family: ⏳ while in flight, a
  yellow ⚠ naming the error afterwards, click to ask again. Present ONLY in
  those two states, so a clean render gains no markup and no committed
  =rendered.html= baseline changes except its =<style>= block
  (=tests/snapshots/registry.org='s "Expected drift" has the entry).

Two traps, both of which bit during the work:

- *The control must be destroyed and rebuilt, not reused.* It has to change
  state (⏳ → ⚠), so reuse strands it on whatever it was first painted as;
  and =renderGroupedTable()= rebuilds every =<thead>= from a =cloneNode(true)=,
  which carries classes and attributes but NOT the click listener. One mutation
  covers both, and the spec CLICKS the control after a re-render rather than
  just looking at it.
- *A test must wait on =[data-re-state="error"]=, not the bare class.* The
  control is painted while loading too, so waiting on the class alone proceeds
  mid-retry and sees one request where three are coming — which is what the
  first draft of the spec did, reporting 1 of 3 as though it were a defect.

** DONE F5 — a 503/429/5xx on CAA metadata is recorded as "no artwork", persisted for 7 days, and the retry button may not clear it  (confirmed by a spec; fixed)

In =_artEnrichIcon()= Tier 3, every non-OK status takes one branch:
=countCache.set(path, 0)=, =imagesCache.set(path, [])=,
=_artIdbPutMetadata(path, 0, [])=. The comment says "404 — expected"; the code
does not act on that distinction. Two consequences:

1. A transient failure is stored as a fact about the release, in IDB, for
   =sa_art_idb_metadata_ttl_days= (default 7). Every later page load hits Tier 2
   and shows no artwork with no request and no warning.
2. =_artRetryTable()= purges =countCache=/=imagesCache= (session Maps) and
   =_artMissCache=, but a search of its body finds no IDB metadata delete. If
   that holds, the retry button re-enters =_artEnrichIcon()=, hits the stored
   zero at Tier 2, and does nothing.

This is the same mistake the ⏱ and Relationships features already fixed
("a transport failure is not 'no data'", in CLAUDE.md), left standing in the
oldest network path. The image-bytes path (row 9) already does it correctly;
only the metadata path is wrong. Highest-value, smallest fix, and the only
finding whose damage /outlives the session/.

*Fixed on =fix/caa-metadata-transient=.* Both halves confirmed by
=tests/fixtures/caa-metadata-transient-503.spec.js= — consequence 2 was exactly
as suspected: the retry re-entered Tier 2 and issued *zero* requests for the
whole table, which the "no IDB metadata eviction" mutation reproduces.

What shipped:
- =_artEnrichIcon()= Tier 3 gates the =_artIdbPutMetadata()= call on
  =_ART_MISS_STATUSES= (404/410), an existing constant declared next to
  =_artMissCache= whose sibling =_artGmFetchBlob()= already drew this exact
  distinction for image bytes. The same local also replaces the old bare
  =resp.status === 404= log-severity test, which logged a 410 as a warning
  while treating it as definitive.
- =_artRetryTable()= is now =async= and evicts each entity's =metadata= record
  before step 3, gated on =sa_art_idb_enable= so the IDB-off path stays fully
  synchronous (step 5's =performance.clearResourceTimings()= is order-sensitive).
  Keys come from the *art anchors* via =ref || href.replace(artSuffix)= — the
  writer's own expression — not from =ctx.rowLinkSel=, which drifts on Path-C
  synthetic anchors and would also delete keys never written.
- =sa_art_idb_metadata_ttl_days= 7 → 30, matching every sibling TTL. Safe only
  *because* of the first bullet.

*Deliberately NARROWER than this file's own item 2 below.* Only the IDB write is
gated; =ctx.countCache=/=ctx.imagesCache= still take the zero for every non-OK
status. Gating those too would re-fire one request per failed entity on every
filter keystroke and every sort — hammering the archive precisely while it is
already struggling. The zero that /outlives the session/ was the whole of the
damage. Pinned by the "the in-memory zero is gated on the status too" entry in
=scripts/mutations/caa-metadata-transient.json=, so the decision is a tested one
rather than an unexplained divergence.

** DONE F6 — retry policy is narrower than the failures it meets  (confirmed by a spec; fixed)

=_ws2GetJson()= retried only =status === 503= plus thrown errors. 502 and 504
(what a reverse proxy returns during a MusicBrainz deploy) and 429 broke out at
once and were reported as final. =Retry-After= was ignored everywhere — no
response header was read anywhere in the file — so the script could not back
off by the amount the server asks for. Note that =_relAwaitRateSlot()='s fixed
1100 ms spacing also means all three of a row's attempts land inside a burst
that typically lasts longer than 3.3 s.

*Fixed on =fix/ws2-transient-classifier=*, pinned by
=tests/fixtures/ws2-transient-classifier.spec.js= (9 tests) and
=scripts/mutations/ws2-transient-classifier.json= (12 mutations, all
=expect: "fail"=, all confirmed).

What shipped:
- =_TRANSIENT_HTTP_STATUSES= (429/502/503/504) and =_isTransientHttp(status)=,
  declared immediately above =_ws2GetJson()= so they precede every future
  consumer in file order. Their JSDoc names what is deliberately EXCLUDED — 500
  (a real server-side error), 408, every other 4xx — and records that this is
  *not* the complement of =_ART_MISS_STATUSES= (=[404, 410]=): a 403 is in
  neither set, and expressing either in terms of the other would be wrong.
- =_parseRetryAfterMs(headerValue)= + =_RETRY_AFTER_MAX_MS= (30 s). Both RFC
  9110 forms, clamped to =[0, cap]=, returning =0= rather than =null= so callers
  fold it in with a bare =Math.max()=. Delta-seconds is tested BEFORE the date
  form, because =Date.parse('12')= succeeds on some engines as the year 12 and a
  bare number would otherwise be discarded as two millennia past.
- =_ws2GetJson()= passes the parsed hint on as =beforeRetry(attempt,
  retryAfterMs)=. It applies *no floor of its own* — a =beforeRetry= that
  ignores the argument simply does not honour the header — and that contract is
  in its JSDoc.
- All three call sites fold it in as =Math.max(ownDelay, retryAfterMs)=: the
  server's ask is a FLOOR, never a replacement (or a =Retry-After: 0.5= would
  let us retry faster than MusicBrainz's 1 req/s rule) and never additive. On
  both Relationships sites the extra wait precedes =_relAwaitRateSlot()=, so the
  slot reservation still sits immediately in front of the request and Step 36's
  one-request-per-1100 ms invariant is untouched.

Two things the mutation run taught, worth keeping:
- The three =beforeRetry= bodies are written out separately, so each is its own
  guard and each needed its own test — the ⏱ batch source and the Relationships
  BROWSE source would otherwise have been a fix wired up in one place only.
- *The rate gate MASKS a lost backoff.* Dropping the hint argument entirely
  makes every caller compute =Math.max(delay, undefined)= = =NaN=, i.e. no
  pause at all — and the observed retry gap was still 1100 ms, because
  =_relAwaitRateSlot()= alone held the line. A spec that merely checked "was
  there a pause" would not have seen it; the assertion has to name the number.

** DONE F7 — Relationships retry-table reloads everything, not just what failed  (confirmed by a spec; fixed)

=_relRetryTable()= collected every =td.mb-rel-cell[data-mbid]= in the table and
evicted and re-requested all of them, including the ones that succeeded. On a
2000-row table with three failures that is 2000 requests at 1 per 1.1 s to
recover three cells.

*Fixed on =feat/rel-retry-failed-only=* — the Relationships half. What shipped:

- =#mb-rel-retry-failed= (=⚠⟳ N=), ONE page-wide control, present only when
  something failed. =_relRetryTable()=/=_relRetryAll()= are deliberately left
  alone: "force a genuine refetch of a table I believe is stale" and "recover
  the failures" are different intents, and a mutation covers the future
  simplification that would collapse them.
- =_relFailedMbidsPageWide()= reads the captured SOURCE rows as well as the live
  DOM, so the set survives a filter (trap 2).
- *A real bug found on the way*: =_relRetryMbids()= cleared =data-rel-error= on
  the LIVE DOM only. A failure a filter was hiding therefore kept its marker —
  and the impl's candidate scan and =_relQueueStillWants()= both read a marked
  cell as "leave alone" — so it was stranded permanently, silently. Markers are
  now cleared on the source rows too.
- *A second one*: =_relRetryAnchorFor()= (extracted from an inline arrow) now
  treats an =<h2>= as an anchor on SINGLE-table pages. The walk used to stop
  there and return =null=, so with cover art off the retry buttons were built
  and dropped on the floor — which is every single-table FIXTURE, and why no
  spec had ever seen them.

*Deviations from [[Retry UI: one segmented control per table]], both deliberate:*

1. *Plain sibling button, not a segmented pill* (user decision). The CAA half of
   that design is blocked, so drawing only the Rel pair as a pill would leave
   the header reading inconsistently. The pill gets done once, for both, when
   the CAA blocker clears.
2. *Page-wide, not per table.* Scoping zone 4 to one table needs a table →
   source-rows mapping this file's own code says is unreliable (merged
   discography view folds other groups' rows into the first-occurrence table),
   and it saves nothing — F7 is about not re-requesting the SUCCESSES, which is
   orthogonal to which table they are in. *That mapping is the first problem to
   solve when the per-table pill is built.*

*What is NOT guaranteed, and is worth knowing before promising more:* a
filtered-out failure is not re-FETCHED while it is off screen, because
=initRelationshipsColumn()='s candidate scan is live-DOM-based. It is un-marked,
so it loads as soon as it is back in view. Fixing that properly means teaching
the candidate scan about source rows, which is Step 36 territory.

Two things the mutation run taught:

- *An earlier draft kept the control present but DIMMED at zero* rather than
  absent, believing that answered trap 2. It did not: a filter still dimmed it
  into uselessness. Absent-at-zero is safe only BECAUSE the count is
  filter-proof.
- *The repaint hook in =_relScheduleProgressRefresh()= was redundant AND
  expensive* — =_relCreateRetryButtons()= already runs when the Phase-2 queue
  drains, and =_relFailedMbidsPageWide()= walks every source row, so a per-frame
  call would be thousands of =querySelectorAll()=s per frame on a big page. The
  mutation for it could not be made to fail, which is how the redundancy
  surfaced; it was removed rather than kept as belt and braces.

** F8 — what already works

Relationships is the model to copy: errors are a distinct outcome, never
cached, visible per cell and as a count on the header, filterable in 📊, and
retryable at cell, table and page level. ⏱ has honest button states, and its
partial retry re-requests only the outstanding MBIDs. CAA image bytes
distinguish a definitive absence from a transport failure.

* Visualisation and retry level, summarised

| Level           | Has a visible failure state today?                               | Can retry here today?                 |
|-----------------+------------------------------------------------------------------+---------------------------------------|
| Whole run/page  | *No.* F1, F2, F3: truncation looks like completion               | No — rerun the whole fetch            |
| Table/sub-table | Rel: badge with failed count. ⏱: yellow retry/partial. CAA: none | Rel: yes. CAA: yes but see F5. ⏱: yes |
| Row             | Expand-RG: inline error text                                     | Yes (click ▶ again)                   |
| Cell            | Rel only: ⚠︎, hover ⟳                                             | Rel only: click                       |
| Column          | Release events: none. CAA metadata: none                         | No                                    |

*Every "can retry here" above means retry EVERYTHING at that level.* Nothing
in the script can currently retry just what failed, at any level except a
single Relationships cell. That is F7 as a behaviour and
[[Retry UI: one segmented control per table]] as an affordance.

The gaps sit at the two extremes: the page/run level (least visible, the most
data at stake) and the CAA and release-events columns (nothing visible at all).

* What could be automated, and how intrusive each is

Ordered by value over intrusiveness. "Silent" = the user notices nothing except
things now working.

1. [DONE] *Shared transient classifier* (silent, tiny). One
   =_isTransientHttp(status)= covering 429, 502, 503, 504 and thrown errors,
   used by =_ws2GetJson()= and everything below, and an optional =Retry-After=
   reader capped at, say, 30 s. Removes F6 and is the prerequisite for the rest.
   Shipped on =fix/ws2-transient-classifier= — see F6 above for exactly what
   landed. Scoped to =_ws2GetJson()= as its only consumer: the helpers are
   there for items 3-4 and 6 to pick up, and neither the CAA art path nor the
   ⏱ ='ws2'= source was touched (both would have been behaviour changes, not
   refactors — see [[Open questions]] 5).
2. [DONE] *Stop recording transient failures as "no artwork"* (silent, small).
   Only 404/410 may write the zero and only they may go to IDB (F5). Also delete
   the IDB record in =_artRetryTable()=. Do this first: it is the only finding
   that persists.
   Shipped on =fix/caa-metadata-transient=, with one change: "may write the zero"
   was narrowed to the IDB write alone — see F5 above for why.
3. [DONE] *Retry the HTML page fetch* (silent, small). 3 attempts with widening
   backoff (2 s, 5 s) inside =fetchHtml()= for transient statuses only, applied
   to all three call sites (F1-F3). Most 503s are bursts, so this alone turns
   most of F1 into a non-event. Shipped on =fix/html-fetch-transient=; it also

* Retry UI: one segmented control per table

Raised 2026-09-19. Not yet built; this is the design record, and item 8 / F7 is
the behaviour half of it.

** What exists today

Three separate buttons, all at table / sub-table level:

| Button               | id                            | Does                                                 |
|----------------------+-------------------------------+------------------------------------------------------|
| CAA/EAA strip toggle | =mb-caa-toggle-btn-{i}=       | show/hide the big-image strip; carries thumb + count |
| CAA/EAA retry        | =mb-caa-toggle-btn-retry-{i}= | =_artRetryTable()= — reload EVERYTHING, cache-busted |
| Relationships retry  | =mb-rel-retry-{i}=            | =_relRetryTable()= — reload EVERYTHING, evicts IDB   |

Globals alongside them: =mb-caa-toggle-btn-global=,
=mb-caa-toggle-btn-global-retry=, =mb-rel-retry-global= (note the LAST one
breaks the pattern — it is not =mb-rel-retry-global-retry=).

*The two CAA buttons are already adjacent siblings*:
=_artCreateOrUpdateRetryButton()= ends in =toggleBtn.after(btn)=, and it bails
out entirely if the toggle is absent. So they are already one visual run that
merely looks like two controls. That is what makes this cheap.

** Proposed shape

One segmented pill per table, replacing the run of loose buttons. Zones left to
right, each its own click target:

#+begin_example
  CAA / EAA                                Relationships

  ┌─────┬─────┬─────┬───────┐              ┌────────┬─────┬───────┐
  │ ▶🖼 │  36 │  ⟳  │ ⚠⟳ 3 │              │ 🔗 84/91 │  ⟳  │ ⚠⟳ 7 │
  └─────┴─────┴─────┴───────┘              └────────┴─────┴───────┘
    (1)   (2)   (3)    (4)                    (1)      (3)    (4)

  (1) toggle   strip / column show-hide, carries the thumb (CAA) or done/total (Rel)
  (2) count    CAA only — see the open question below
  (3) all      reload everything, cache-busted (today's ⟳)
  (4) failed   reload ONLY what failed; ABSENT when nothing failed
#+end_example

Zone 4 is the new affordance and the point of the exercise. Zone 3 keeps
today's behaviour so "force a genuine refetch of a table I believe is stale"
does not disappear — it is a different intent from "recover the failures" and
both are legitimate.

** Why this is workable, and cheap

- *No DOM restructuring.* The CAA pair are already siblings; the pill is CSS
  plus one new segment. The Relationships button becomes a run of its own.
- *No wrapper element is needed*, so nothing has to be re-parented. Draw the
  run as one pill with the run-relative selector pair the sort group already
  uses — =:not(.mb-x + .mb-x)= for the first segment,
  =:not(:has(+ .mb-x))= for the last. =:first-of-type=/=:last-of-type= are
  WRONG here for the same reason CLAUDE.md gives for the sort group.
- *Existing ids survive.* =mb-caa-toggle-btn-{i}= and
  =mb-caa-toggle-btn-retry-{i}= stay on zones 1 and 3. This matters more than
  it looks: =#mb-caa-toggle-btn-global= is referenced by *eight live specs*
  plus =tests/support/measure-caa-metadata-404s.js=, and =.mb-caa-toggle-count=
  by two more. Renaming any of them turns a CSS change into a test migration.
- *There is an established visual language to join*, not invent: the
  =.mb-col-hdr-flex= family (six controls, one shared CSS rule) and the sort
  group's segmented pill. CLAUDE.md's "Column-header toggle family" section is
  the spec; a seventh member extends the selector lists rather than copying a
  block.

** Traps, in the order they will bite

1. [SOLVED] *CAA HAD NO FAILURE STATE TO DRIVE ZONE 4. This was a hard
   prerequisite, not a detail.* After F5, =ctx.countCache= holds =0= for *both*
   "the archive says this release has no artwork" (a 404, a fact) and "the
   request failed" (a 503) — F5 deliberately kept the in-memory zero for both,
   and nothing distinguished them afterwards.

   Cleared on =feat/caa-retry-failed-only= by =ctx.failedCache=, exactly as
   predicted here: a session-scoped Set of entity paths, written in
   =_artEnrichIcon()='s Tier 3 where F5 decided not to persist, and cleared by
   =_artRetryTable()=. One correction to the prediction — it is also cleared by
   the SUCCESS path and by =_artRetryFailedAll()=, and only a NON-definitive
   status is recorded: a 404 is the commonest answer the archive gives, so
   recording it too would have put a =⚠⟳= carrying a large number on almost
   every page.

   Being keyed by entity PATH rather than by DOM turned out to matter more than
   expected: the Relationships half had to read the captured source rows to
   survive a filter, and this one gets that property for free.
2. *Do not hide zone 4 on a count taken from the live DOM.*
   =_relTableProgress()= reads =table.querySelectorAll('tbody td.mb-rel-cell[data-mbid]')=
   — the LIVE tbody — and =runFilter()= REMOVES non-matching rows rather than
   hiding them. A zone that disappears at =failed === 0= would therefore vanish
   exactly when a filter excludes the failed rows, removing the only way back
   to them. This is the *identical* bug CLAUDE.md records for
   =_updateLengthMismatchButtons()= / =_updateLiveDateFlagButtons()=, and
   =_countLengthMismatchRows()= walking =_msSourceRows()= is the fix to copy.
   Count source rows, or keep the zone present and merely dimmed.
3. *Nested =<button>= is invalid HTML.* The segments are siblings, never
   nested — which they already are. The sort group uses sibling =<span>=s for
   the same reason.
4. *The sort group's "no wrapper, ever" rule does NOT transfer, and knowing why
   matters.* That rule exists because 19 specs locate sort icons as
   =locator('.sort-icon-btn', {hasText: '▲'})= and =hasText= is a SUBSTRING
   match, so a wrapper whose text is =⇅▲▼= wins =.first()=. These buttons are
   located by *id*, so a wrapper would be harmless here. It is still not needed
   — but do not cite the sort-group rule as a blanket prohibition, and do not
   dismiss it either.
5. *Per-zone CSS deltas must sit AFTER the shared rule*, same specificity, or
   source order silently decides. Three deltas in the existing family are
   load-bearing for exactly this reason; see CLAUDE.md.

*** What the archive actually gives us, and what we already have

Checked against <https://musicbrainz.org/doc/Cover_Art_Archive/API> on
2026-09-19, per the root CLAUDE.md rule. =GET /release/{mbid}= returns
={release, images[]}=, and each image carries *exactly nine* documented fields:

| Field        | Type   | The doc's own words                                             | Used today?  |
|--------------+--------+-----------------------------------------------------------------+--------------|
| =id=         | string | "archive.org's internal file id"                                | yes, 1 site  |
| =image=      | string | full URL to the original                                        | yes          |
| =thumbnails= | object | =250= / =500= / =1200=, plus deprecated =small=/=large=         | yes, 8 sites |
| =types=      | array  | "list of zero or more types for the image"                      | yes, 3 sites |
| =front=      | bool   | "indicates if this is the 'main front'"                         | *no*         |
| =back=       | bool   | "indicates if this is the 'main back'"                          | *no*         |
| =comment=    | string | "a free text comment"                                           | yes, 3 sites |
| =approved=   | bool   | "whether the image was approved by the musicbrainz edit system" | yes, 1 site  |
| =edit=       | int    | "the edit id on musicbrainz (e.g. 123)"                         | *no*         |

=/release-group/{mbid}= returns the same image shape and adds a =release=
field — "the specific release from which the art was sourced".

*Everything above is ALREADY FETCHED AND ALREADY PERSISTED.* Tier 3 does
=images = Array.isArray(json.images) ? json.images : []= and hands that array
verbatim to =_artIdbPutMetadata(entityPath, count, images)=, so the whole
record — every field, every thumbnail size — is sitting in the =metadata= IDB
store right now. *The summary panel therefore costs ZERO new requests and zero
new storage.* It is a pure read of data the script already pays for and then
throws away.

Four things are stored on every image and surfaced nowhere:

- =edit= — a MusicBrainz edit id, i.e. a link to =/edit/{id}=. For an editor
  chasing "who added this cover and when", that is the single most useful field
  in the record, and it is currently dead weight in the cache.
- =front= / =back= — the archive's own "this is THE main front" flags, which are
  not the same thing as ='Front' ∈ types=: an image can be typed Front without
  being the main front. Worth showing exactly because the distinction is
  invisible today.
- The full thumbnail ladder. The script reads whichever size it needs; the
  summary can say which sizes actually exist per image, which is how a missing
  =1200= (common on old uploads) stops being a mystery.
- On a release-group listing, =release= — *which release supplied this cover*.
  Nothing in the script can answer that today.

*** Proposed contents, per table

| Group    | Rows                                                                                           |
|----------+------------------------------------------------------------------------------------------------|
| Entities | total / with artwork / none / *failed* / still pending                                         |
| Images   | icon + inline + strip, as the toast already breaks them down                                   |
| Cache    | the existing four tiers (🟢 memory, 🟡 network, 🔵 IDB, 🗄️ timed), scoped to this table         |
| Types    | Front / Back / Booklet / Medium / Tray / Obi / Matrix-Runout / …, counted from =types[]=       |
| Flags    | main-front present? main-back present? =approved: false= count; images with an empty =types[]= |
| Sizes    | how many images offer =1200= / =500= / =250=                                                   |
| Edits    | =edit= ids, linked to =/edit/{id}=                                                             |
| Sourced  | release-group listings only: which release each cover came from                                |
| Failures | the failing entities by name, each a link, plus a "retry these" action                         |

The Failures group is what ties zone 2 to zone 4: *zone 2 explains, zone 4
acts*. Zone 4 stays as the one-click path — a user who has already seen the
panel should not have to reopen it to retry.

*Do not add a request to enrich this.* The archive publishes no batch or bulk
endpoint (same doc, same date), so anything not in the record above costs one
request per entity — which is the cost this whole file exists to reduce. If a
field is wanted that the archive does not return, the answer is a MusicBrainz
WS/2 lookup, and it needs its own gate and its own measurement.

*As shipped, the panel makes no request at all* — every group reads
=ctx.imagesCache=, which already holds =json.images= verbatim.

*One group is shipped but UNTESTED: "Cover sourced from".* The archive
returns =release= only on a release-GROUP lookup, and the fixture's page
(=releasegroup-releases=) looks up releases. Covering it needs an
=artist-releasegroups= fixture; recorded rather than left to be discovered.

*** Traps specific to this zone

1. *It must work MID-LOAD, which is the whole point.* Do not gate it on the
   queue draining, do not reuse the toast's "has it completed" signal, and do
   not wait on =#mb-info-display-caa=. Read current state when the panel opens.
   A summary that only becomes available once everything succeeded is useless on
   precisely the pages that motivated it.
2. *Do not reuse the toast's accumulators for a per-table count.*
   =_showCaaCompletionToast()='s =s.icon[key]= / =s.inline[key]= are PAGE-WIDE
   tallies. A per-table panel needs its own pass, and that pass must walk the
   SOURCE rows — =runFilter()= removes non-matching rows, so a live-tbody tally
   silently reports "the filtered subset" as if it were the table. Same rule as
   trap 2 above, same fix (=_countLengthMismatchRows()= / =_msSourceRows()=).
3. *Follow =.mb-col-uniq-wrap=, do not invent a panel idiom.* It is the exact
   precedent: the one member of the column-header family that is NOT a toggle
   but a panel opener. Copy its conventions — an "on" state of
   =.mb-col-uniq-active= (two classes, so it wins on specificity regardless of
   source order) rather than =aria-pressed=, and one panel open at a time, which
   =_uniqDropOwner= already manages by clearing the class from the previous
   owner.
4. *Drive it from =ctx=, never from the string "CAA".* EAA shares
   =sa_enable_caa_pics= and the whole pipeline; =ctx.column= is ='CAA'= or
   ='EAA'= and =ctx.key= is the debug channel. A hardcoded panel works on
   release pages and silently mislabels every event page.
5. *The panel's own counts need the uniq-drop cache discipline.* If it is
   opened while artwork is still arriving, its numbers are a snapshot; either
   refresh it on the same coalesced hook the progress badge uses, or state the
   time it was taken. Do not cache it under a key that a later write cannot
   invalidate — CLAUDE.md's "Writing cell text AFTER the render" applies.

*** What this does not change

Zone 2 is a panel opener, so it has no pressed state and never changes what is
loaded. It cannot be the recovery affordance on its own, which is why the
"count carries the failure state inline" variant (=36= → =36 ⚠7=) was NOT
taken: it would have merged an explanation and an action into one target.

** What this does NOT address

The page/run level, which is where the most data is at stake (F1-F3). A
per-table control cannot say "page 4 of 40 failed"; item 4's status line is
still the fix for that.

* Performance and compatibility notes

- Items 1-4 add no work on the success path (a status check that already
  exists). Retry backoff only spends time on a request that was already lost.
- Item 7's follow-up pass adds requests only after failures; the shared rate
  gate must cover it, as Step 36 requires of every Relationships source.
- =fetchHtml()= is used for the current-page shortcut only when the page is the
  current document; retry does not apply there.
- Test-framework impact to check before implementing: =tests/support/gmStubs.js=
  and =realNetworkGmXhr.js= (they stub network calls), any fixture that
  answers =**/ws/2/**= or serves HTML pages (a 503 sequence needs a stateful
  route), and =rel-column-collapse-toggle.spec.js= (it asserts exact request
  counts, which item 7 changes by design).

* Open questions

1. [ANSWERED — yes, and fixed] Save-to-Disk after a truncated fetch DID write
