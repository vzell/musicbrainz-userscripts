I have the code picture now. Before writing the plan, two findings change the shape of the work.

"Is this just a filter performance fix?" — No. Step 23 converts six features' event wiring from per-element addEventListener to delegation. Four of them are user-visible controls (Picard ♪ buttons, ERG ▶ expanders, nested-<h2> collapse, cdtoc toggles) plus two unlisted members the step's own corrections add (sticky-column row hover, barcode cell clicks). The perf win is real, but the risk is "an interactive control silently stops working after a keystroke", not "a number moves". Specifics I verified:

- ERG is the hard part. Its per-button state is a closure toggled flag plus a listener-set-encoded fetch lifecycle (loadOnce detaches itself; retrySetup re-arms it) — none of it on the DOM. initExpandRGsFeature() also injects into live rows only (link.parentNode, #content table.tbl > tbody > tr > td), so in tableMode: 'multi' the master rows never own the button — the same gap that caused the 2026-09-10 Picard bug. Delegation alone would delete the buttons there; it needs a source-row mirror first. - Picard is the easy part. Its button closure holds exactly three data values (guid, entityType, name), host/port are already read at click time, and the visual state already lives in the DOM. A .mb-picard-btn arm added to the already-delegated _picardHdrDelegateHandler on <table> covers it.

Tier 1's order is no longer valid as written, and Step 23 is the item that moved.
