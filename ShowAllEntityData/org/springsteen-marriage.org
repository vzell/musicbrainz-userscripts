** Probe, second pass: the -N chains (same Env as above)

Section 4 of the probe treats every redirect page named =<base>-N=, onstage pages included:
- *Pages and bases:* 56 sibling pages, 28 bases found. The other 25 are =multi:…-1/-2=: "several shows on one date" pages, not overflow, with no base page.
- *Naming rule:* base =[:60 - len("-N")]=, a trailing =-= dropped, then =-N=. It holds for all 31 siblings with a base, with 0 failures. Wikidot page names are at most 60 characters, so a long name is CUT before the suffix:
  - =onstage:2026-06-04-oceanfirst-bank-center-west-long-branch-2= (the =-nj= is gone);
  - =onstage:2004-10-13-continental-airlines-arena-east-rutherf-2=.

  Build the address with this rule, never by appending =-2=.
- *Overflow vs alias:* the base of a real overflow chain is over 400 characters. 19 of the 28 bases are; the rest are renamed pages (=relation:steve-van-zandt-2=, 24 characters) or =multi:= pages.
- *Onstage pages have chains too.* =onstage:2009-05-03-madison-square-garden-new-york-city-ny= (Pete Seeger's 90th) goes on to =-2= and =-3=. The gig itself carries 27 tags, and its three onstage pages 40 + 35 + 18. The reader therefore walks: event page → On stage page → its siblings while each read page is nearly full.
- *A chain can start at -1:* =gig:1990-01-17-waldorf-astoria…= has no base onstage page, only =onstage:…-1= (44 tags) and =-2= (7 tags). So when the onstage page is missing, try =-1= once.
- *Suffixes:* =-2= 24, =-3= 3, =-1= 4.
- *What the trigger costs*, as pages over N characters and how many of them really have a sibling:

  | over | pages | with a sibling |
  |------+-------+----------------|
  |  400 |   828 |             19 |
  |  450 |   253 |             18 |
  |  480 |    94 |             16 |
  |  500 |    35 |             10 |

  Recommendation: use *450*, not 400. It is 3× fewer wasted requests and misses 1 chain. It is one constant, easy to move.

The reader that follows from this:
1. *The show's own tags* come from the event page (no request).
2. *The On stage page:* if the On Stage tab exists, fetch =onstage:<slug>/noredirect/true=. If that page does not exist, fetch =…-1= once.
3. *Siblings:* for each page read so far whose tags are over 450 characters, fetch its =-2= (by the name rule), then =-3=, … until one is missing. That is at most 3 pages deep in the mirror.
4. *The result:* the union of all their tags, each tag knowing which page it came from. The families are classified with the EVENT page's context, because the onstage pages have no =/relation:= links of their own.

Also: =_dpParseBb()= is SYNCHRONOUS (the plan said async). The extra requests belong in the Brucebase loader (=_extDpLoad()= / the =_dpGet()= path) after the parse, and must go through the same rate slot.

Decisions (vzell, 2026-11-13):
- SAED is the home.
- BBP retires once SAED covers all of its checks.
- BruceParser keeps running offline and publishes a compact JSON feed to GitHub raw, which SAED reads.

Generic MusicBrainz behaviour must not change.

*The gap vzell named: tags that spill onto the onstage page.* Wikidot limits how many tags one page can hold. A gig, rehearsal or interview page with an "On Stage" tab can park its overflow tags on =/onstage:<slug>/noredirect/true=. BBP handles this in =fetchOnstageCompanionTags()= (=BruceBaseParser.user.js:6831=, doc =doc/TAGS.md= "Onstage companion page tags"). BruceParser's =efc.sh:331= notes a second form: category pages that reach the limit get =-2=, =-3= … sibling pages that redirect to the main one (=MULTI-title-postfix.txt=). SAED's =_bbPageTags(doc, url)= reads only =div.page-tags= of the page itself. So three places miss the spilled tags:
- the bb-event head and its Tags card;
- every BB preview window, through =_dpParseBb()=, including windows opened on musicbrainz.org;
- the year table's ▶ Pages columns.

** The ideas, ordered by value per byte

1. *Spilled tags (phase 1, below).* One shared reader change fixes all three places.
2. *BBP's checks become FINDINGS entries, not ported code.* SAED already has the registry, the ⚠️/❌ menus, the cell tint and the 📊 sections, and four BB findings already exist (=bb-mbev-link-*=, =bb-date-comma=, =bb-onstage-tab=). BBP's checks fit as entries over data SAED already reads (the =_bbEvp*= year columns read each event's page, as BBP's =processOneYearEvent= does):
   - YEAR vs DETAIL event name (=extractDetailEventName= / =normalizeDetailName=)
   - venue name
   - the year page's anchor date (=checkYearAnchorConsistency=)
   - setlist songs without their tag (=checkSetlistSongTags=)
   - expected vs actual tags: date parts, places, relations, tours and premieres (=computeExpectedTags= and its siblings)
   - spurious tags
   BBP's own UI is not ported. Save/Load, SmartTable, the lightbox and the keyboard shortcuts all already exist in SAED, and some came from SAED in the first place.
3. *BBP's lookup tables move into the feed instead of the script.* Examples: =TOUR_DEFINITIONS=, =SONG_TAG_ALIAS_OVERRIDES=, =VENUE_TAG_ALIAS_OVERRIDES=, =RELATION_TAG_ALIAS_OVERRIDES=. BruceParser generates or curates them, and SAED fetches them once a day and caches them. That keeps them out of the 10 MB file and lets vzell update them without a release.
4. *BruceParser's site-wide reports become findings in the browser.* =bbp.sh= writes =bb-feed.json=, keyed by page path:
   - setlist differences YEAR vs DETAIL
   - titles that differ between YEAR, YEAR-LIST and DETAIL
   - URLs shortened at a different place (=URL-shortening=)
   - pages missing their first-character tag or a date-part tag
   - =files= tag vs images
   - pages with no parent
   SAED stamps these on BB rows and in previews without extra requests. Each finding's card names the report it came from and the feed's date.
5. *Cross-checks on MusicBrainz, gated to entities with a brucebase URL relationship.* On an E with a BB "reviews" link, the feed already holds BruceParser's =search/= comparison (MB event title vs the MB-style title derived from BB), and the same goes for W vs BB song (=esfsl.sh=). Shown as findings only when the row's entity carries a =brucebase.wikidot.com= URL and the feed is loaded. Any other MB page makes zero requests and takes no new code path, and the MB fixture suite proves it.
6. *Retirement matrix.* =org/bbp-parity.org= lists every BBP check and feature with its SAED counterpart (finding id, pageType or feed key) and a state. BBP is frozen when every row is done. Until then, test that SAED and BBP can run on the same page together, since both match the same URLs.

*Size budget.* Port checks as data and findings, never as BBP's code. Target for the whole of Track A: at most about 150 KB (~1.5 %). Record the bytes each phase adds in its changelog entry. Data goes through the feed.

* Track B: volkerzell.de (Ionos shared hosting: PHP + MySQL/MariaDB)

** Context

Today volkerzell.de serves only the SL mirror at =/springsteenlyrics/=. Ground rules (vzell, 2026-11-13):
- *The site is for three audiences:* fans, MB and BB editors, and SAED users.
- *SAED never calls the site*, so the feed stays on GitHub raw. That means no visitor IPs from userscript users and no new =@connect=.

The resulting split:

- *One export step pushes the results up.* A new step at the end of =bbp.sh=, =publish.sh=, exports to JSON or SQL and uploads it over SFTP/SSH.
- *The site reads its own database.* PHP serves pages from MySQL only and never scrapes anything itself.

** One data spine, three outputs

=bbp.sh= already joins BB, SL, KF, JL and MB data. The new =publish.sh= step writes one normalised dataset:
- shows: date, venue, kind, setlist, tour;
- songs, venues and people;
- for each show, its links: BB page and anchor, MB event MBID, setlist.fm, SL, JL, KF, IA;
- the findings from the reports.

That dataset feeds three outputs:
1. =bb-feed.json= on GitHub raw, for SAED (Track A, idea 4).
2. The MySQL import for volkerzell.de.
3. A run record (counts, timings, what changed since the last run) from =docs/timings.tsv= and =run-history.md=.

** 1) The public homepage (fans, editors, SAED users)

** 2) Private and internal use (behind HTTP auth)

- *A dashboard of runs and measurements.* =bbp.sh= timings for each host, =test:full= wall clocks, the perf baselines and the lint counts, as charts across petri, NB-3641 and vzell-lap. Today these sit in =tests/MEASUREMENTS.org= and =docs/timings.tsv=.
- *A place for =debug/= snapshots.* =debug/= is synced between hosts by hand today. A small upload-and-list PHP page (or SFTP to a private folder) holds the snapshots and logs, each with its Env stamp. The NAS stays the home of the full =bb/latest= mirror, which is too big for shared web space.
- *Review queues.* A finding accepted as "known exception" in the browser goes into a DB table. =publish.sh= downloads it as the allowlist that the reports' =-CLEANEDUP= steps now hard-code in the scripts.
- *A public status page for the feed.* The feed's date, the counts and whether the last run failed (from =timings.tsv='s failed-steps column), so it is visible at a glance that =bb-feed.json= is current.

** 3) The database as the shared archive (from [[file:offline.org][offline.org]])

=offline.org= deliberately left one question open: where the "local store" lives, a folder or a local SQLite server (❓ in its Phase 2). It also named the weaknesses of every local option:
- each archive is invisible to the other machines;
- IndexedDB is per browser and per site, and can be evicted;
- replication needs PouchDB and CouchDB.

MariaDB on Ionos fills that gap *as the hub between machines*. The offline view itself stays local, because offline means no Ionos either.

- *Snapshots go into the database.* Format 1.2 (=key=, =text= for each column, absolute URLs, optional =images=) maps onto:
  - =snapshot(id, site, pagetype, button, taken_at, script_version, row_count, incomplete, same_as)=
  - =snapshot_row(snapshot_id, row_key, text_json, html)=
  The row keys are the ones =offline.org= item 4 already defined:
  - SL: path + =item=
  - JL: =YYYYMMDD[_N].htm=
  - BS: =Code=
  - BB: the page link
  BruceParser's feed uses the same keys, so the DB, the feed and SAED all speak one key. A "same as <date>" snapshot stores only a reference, so a weekly run of a frozen site like JL or KF costs a few bytes.
- *Uploads come from home, never from the userscript.* SAED's 📸 Snapshot job writes to the local folder or server, as in =offline.org=. A small =scripts/sync-archive.py= uploads new snapshots and =publish.sh= uploads BruceParser's, over SFTP or a PHP import endpoint with a token.
- *The diff is computed by the server.* The added, changed, removed and moved rows that =offline.org= Phase 3 computes in the browser become an SQL join on =row_key= between two snapshots. That gives three things:
  - "What changed" pages for all four Springsteen sites, not only BB;
  - one row's history (mockup F) as a page;
  - the diff of each run in the run record.
  =applySnapshotDiffToTable()= in SAED stays the in-browser view of the same data.
- *Search.* =offline.org= suggested SQLite FTS5 and Datasette for querying. MariaDB =FULLTEXT= indexes over =snapshot_row.text_json= give that over every snapshot. Full text goes in the private area; the public search covers facts only.
- *Every machine can work offline.* A =scripts/pull-archive.py= turns the MariaDB data into a local =.sqlite= file. petri, NB-3641 and vzell-lap each get the same archive for =offline.org='s local page B (Phase 4) and its local server option. This settles the ❓ in =offline.org= Phase 2: a local server with SQLite, fed from the hub.
- *WARCs.* The raw WARC crawls (the shutdown insurance) stay on the NAS, because they are too big for shared web space. The database keeps only their index:
  - which crawl;
  - when;
  - which URLs;
  - which content hash.
  Ionos can hold an off-site copy of the small ones (JL, KF) if the quota allows.
- *Rights.* =offline.org= item 6 already says it: snapshots and WARCs are for personal use and preservation. They stay in the private area. The public site shows facts and links and credits the owners (below).

** Constraints to settle before building

- *A German site needs an Impressum and a Datenschutzerklärung.* Avoid analytics and third-party fonts and CDNs, and keep the Ionos access logs short.
- *Link and derive, never republish.* Setlists, dates and counts are facts. Lyrics, wiki prose and images belong to BB and SL, so show page links rather than copies. Also check whether the public SL mirror at =/springsteenlyrics/= is allowed; if not, put it behind auth.
- *Shared hosting limits.* Check whether the package includes SSH and cron, and what its PHP and MySQL versions and its space are. Without cron, everything is pushed from petri, which is fine.
