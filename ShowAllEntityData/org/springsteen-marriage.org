* Track A: BruceParser and BruceBaseParser into ShowAllEntityData

** Context

There are three Springsteen tools today:

| Tool                               | Where                                             | What it is                                                                                                                                                                                                               | Size                                        |
|------------------------------------+---------------------------------------------------+--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------+---------------------------------------------|
| ShowAllEntityData (SAED), main one | =~/git/musicbrainz-userscripts/ShowAllEntityData= | Userscript: MusicBrainz table engine plus BB, SL, JL, KF, DI, IA and SFM pageTypes, link previews and FINDINGS                                                                                                           | 10,150,618 bytes, 186,459 lines (9.99.1624) |
| BruceBaseParser (BBP)              | =~/git/userscripts/BruceBaseParser=               | Userscript on brucebase only: the YEAR, LIST, DETAIL, VENUE, RETAIL, SONG, RELATION and Recent changes pages. It checks the wiki against itself (event names, venues, setlists, expected tags compared with actual tags) | 588 KB, 12,263 lines (v3.33)                |
| BruceParser (bbp.sh)               | =~/git/scripts/BruceParser=                       | Offline Bash pipeline that downloads the whole wiki (=bb/latest=) plus SL, KF, JL and MB, and writes site-wide QA reports                                                                                                | 277 KB of =.sh=                             |

Decisions (vzell, 2026-11-13):
- SAED is the home.
- BBP retires once SAED covers all of its checks.
- BruceParser keeps running offline and publishes a compact JSON feed to GitHub raw, which SAED reads.

Generic MusicBrainz behaviour must not change.

*The six ideas, ordered by value per byte* (the numbering is cited elsewhere, keep it):
1. *Tags kept on other pages* (Phase 1). One shared reader change fixes the event head, every BB preview window and
   the year table's ▶ Pages.
2. *BBP's checks become FINDINGS entries, not ported code.* SAED already has the registry, the ⚠️/❌ menus, the cell
   tint and the 📊 sections. BBP's own UI is not ported: Save/Load, SmartTable, the lightbox and the keyboard
   shortcuts all already exist in SAED.
3. *BBP's lookup tables move into the feed instead of the script* (=TOUR_DEFINITIONS=, =SONG_TAG_ALIAS_OVERRIDES=,
   =VENUE_TAG_ALIAS_OVERRIDES=, =RELATION_TAG_ALIAS_OVERRIDES=). BruceParser generates or curates them, SAED fetches
   them once a day and caches them, vzell updates them without a release.
4. *BruceParser's site-wide reports become findings in the browser*, through =bb-feed.json=, keyed by page path. SAED
   stamps them on BB rows and in previews without extra requests; each card names its report and the feed's date.
5. *Cross-checks on MusicBrainz*, gated to entities with a =brucebase.wikidot.com= URL relationship and a loaded feed.
   Any other MB page makes zero requests and takes no new code path; the MB fixture suite proves it.
6. *Retirement matrix* (=org/bbp-parity.org=): every BBP check with its SAED counterpart and a state. BBP is frozen
   when every row is done; until then SAED and BBP must be able to run on one page.

*Size budget.* Port checks as data and findings, never as BBP's code. Target for the whole of Track A: at most about
150 KB (~1.5 %). Each batch records its bytes in its changelog entry (batch 3: +38.6 kB). *Never totalled yet.*

*** The reader as built

1. *The show's own tags* come from the event page (no request).
2. *The On stage page:* if the On Stage tab exists, fetch =onstage:<slug>/noredirect/true=; if it does not exist,
   fetch =…-1= once.
3. *Siblings:* for each page read so far whose tags are over 450 characters, fetch its =-2= (by the name rule), then
   =-3=, … until one is missing.
4. *The result:* the union of all their tags, each knowing its page. The families are classified with the EVENT
   page's context, because the onstage pages have no =/relation:= links of their own.

=_dpParseBb()= is synchronous, so the requests sit in the Brucebase loader after the parse, through the same rate slot.

* Track B: volkerzell.de (Ionos shared hosting: PHP + MySQL/MariaDB)

** Context

Today volkerzell.de serves only the SL mirror at =/springsteenlyrics/=. Ground rules (vzell, 2026-11-13):
- *The site is for three audiences:* fans, MB and BB editors, and SAED users.
- *SAED never calls the site*, so the feed stays on GitHub raw. That means no visitor IPs from userscript users and no new =@connect=.
- *Shared hosting:* PHP, a database and SFTP. Long Bash pipelines don't run there.

The resulting split:
- *The heavy work stays at home.* =bbp.sh= runs on petri.
- *One export step pushes the results up.* A new step at the end of =bbp.sh=, =publish.sh=, exports to JSON or SQL and uploads it over SFTP/SSH.
- *The site reads its own database.* PHP serves pages from MySQL only and never scrapes anything itself.

** One data spine, three outputs

=bbp.sh= already joins BB, SL, KF, JL and MB data. The new =publish.sh= step writes one normalised dataset:
- shows: date, venue, kind, setlist, tour;
- songs, venues and people;
- for each show, its links: BB page and anchor, MB event MBID, setlist.fm, SL, JL, KF, IA;
- the findings from the reports.

That dataset feeds three outputs:
1. =bb-feed.json= on GitHub raw, for SAED (Track A, idea 4).
2. The MySQL import for volkerzell.de.
3. A run record (counts, timings, what changed since the last run) from =docs/timings.tsv= and =run-history.md=.

** 1) The public homepage (fans, editors, SAED users)

It uses the "Liner notes" look: paper ground, serif, small caps labels. Page ideas:

- *Show finder.* Every show is one page: date, venue, setlist, tour. Its "Sources" strip links each site's page for that
  show (BB, MB, setlist.fm, SL, JL, KF, IA). Browse by year, tour, venue or song, with SAED-like filtering through a
  small sortable table in plain JS, no framework.
- *On this day.* Today's date across the years: shows, first and last performances, plus an RSS/Atom feed.
- *Song pages.* Times played, first and last time, the longest gap, a play count by tour (BB stats), and links to SL lyrics and MB works.
- *Data health, for editors.* BruceParser's reports become live, filterable pages instead of =.html= files on disk:
  - MB events without a BB link
  - titles that differ MB vs BB
  - setlists that differ YEAR vs DETAIL
  - tags missing or spilled
  - wrongly shortened URLs
  Each row has a "fix it here" link (MB edit page, BB page) and shows its trend run by run. That gives the community an obvious use for the pipeline.
- *"What changed on Brucebase."* The wiki shows only the latest 1,000 recent changes, and BBP's SmartTable stops there
  too. =publish.sh= uploads each run's diff, so the site keeps a permanent, searchable change history.
- *The userscripts' home.* Install buttons that point at the =vzell/mb-userscripts= raw URLs (GitHub stays the install
  and update source), "What's new" from =ShowAllEntityData_RELEASES.md=, the help, screenshots and the FORUM.org videos,
  and the supported sites from =NON-MB-COVERAGE.html=. The ❓ and 📜 dialogs keep reading GitHub.

** 2) Private and internal use (behind HTTP auth)

- *A dashboard of runs and measurements.* =bbp.sh= timings for each host, =test:full= wall clocks, the perf baselines
  and the lint counts, as charts across petri, NB-3641 and vzell-lap. Today these sit in =tests/MEASUREMENTS.org= and
  =docs/timings.tsv=.
- *A place for =debug/= snapshots.* =debug/= is synced between hosts by hand today. A small upload-and-list PHP page (or
  SFTP to a private folder) holds the snapshots and logs, each with its Env stamp. The NAS stays the home of the full
  =bb/latest= mirror, which is too big for shared web space.
- *Review queues.* A finding accepted as "known exception" in the browser goes into a DB table. =publish.sh= downloads
  it as the allowlist that the reports' =-CLEANEDUP= steps now hard-code in the scripts.
- *A public status page for the feed.* The feed's date, the counts and whether the last run failed (from =timings.tsv='s
  failed-steps column), so it is visible at a glance that =bb-feed.json= is current.

** 3) The database as the shared archive (from [[file:offline.org][offline.org]])

=offline.org= deliberately left one question open: where the "local store" lives, a folder or a local SQLite server (❓ in its Phase 2). It also named the weaknesses of every local option:
- each archive is invisible to the other machines;
- IndexedDB is per browser and per site, and can be evicted;
- replication needs PouchDB and CouchDB.

MariaDB on Ionos fills that gap *as the hub between machines*. The offline view itself stays local, because offline means no Ionos either.

- *Snapshots go into the database.* Format 1.2 (=key=, =text= for each column, absolute URLs, optional =images=) maps onto:
  - =snapshot(id, site, pagetype, button, taken_at, script_version, row_count, incomplete, same_as)=
  - =snapshot_row(snapshot_id, row_key, text_json, html)=
  The row keys are the ones =offline.org= item 4 already defined:
  - SL: path + =item=
  - JL: =YYYYMMDD[_N].htm=
  - BS: =Code=
  - BB: the page link
  BruceParser's feed uses the same keys, so the DB, the feed and SAED all speak one key. A "same as <date>" snapshot
  stores only a reference, so a weekly run of a frozen site like JL or KF costs a few bytes.
- *Uploads come from home, never from the userscript.* SAED's 📸 Snapshot job writes to the local folder or server, as
  in =offline.org=. A small =scripts/sync-archive.py= uploads new snapshots and =publish.sh= uploads BruceParser's, over
  SFTP or a PHP import endpoint with a token.
- *The diff is computed by the server.* The added, changed, removed and moved rows that =offline.org= Phase 3 computes
  in the browser become an SQL join on =row_key= between two snapshots. That gives three things:
  - "What changed" pages for all four Springsteen sites, not only BB;
  - one row's history (mockup F) as a page;
  - the diff of each run in the run record.
  =applySnapshotDiffToTable()= in SAED stays the in-browser view of the same data.
- *Search.* =offline.org= suggested SQLite FTS5 and Datasette for querying. MariaDB =FULLTEXT= indexes over
  =snapshot_row.text_json= give that over every snapshot. Full text goes in the private area; the public search covers
  facts only.
- *Every machine can work offline.* A =scripts/pull-archive.py= turns the MariaDB data into a local =.sqlite=
  file. petri, NB-3641 and vzell-lap each get the same archive for =offline.org='s local page B (Phase 4) and its local
  server option. This settles the ❓ in =offline.org= Phase 2: a local server with SQLite, fed from the hub.
- *WARCs.* The raw WARC crawls (the shutdown insurance) stay on the NAS, because they are too big for shared web space. The database keeps only their index:
  - which crawl;
  - when;
  - which URLs;
  - which content hash.
  Ionos can hold an off-site copy of the small ones (JL, KF) if the quota allows.
- *Rights.* =offline.org= item 6 already says it: snapshots and WARCs are for personal use and preservation. They stay
  in the private area. The public site shows facts and links and credits the owners (below).
