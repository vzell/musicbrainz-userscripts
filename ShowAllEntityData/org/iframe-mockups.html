One popup engine for every link

The detail-page card and its pinned window (9.99.1263) work on four Springsteen sites. These mockups show the same engine on MusicBrainz: a card for the entity behind any link in a table, Space to pin it into a window with an Extracted view and the Live page, the arrows to step through the column. The release-group popup on release tracklists comes first. All data on this page is example data, shaped like the real Web Service answers. Covers are stand-ins, because this page loads no images.

Hold Ctrl and hover a link in any mock table (or rest on it, then press Ctrl). Space pins, Esc closes, ← → step. On a touch screen, tap a link.
What is reused
The whole detail-page engine

Card, delay, Ctrl gate, Space and Esc, the pinned window with Extracted and Live page, ‹ ›, ⟳ and ↗, the cache with its one-request-per-URL rule. Only the four site entries become "sources", and MusicBrainz adds its own.

What is new
Sources, a resolver, one gate

A source per entity kind; a resolver that also takes declared containers, not only links; every MusicBrainz request through the Relationships column's gate, so the script stays at one request a second.

What comes first
The release-group popup

The "#" cell and the subheader link on release tracklists move onto the engine: a card you can pin, every release in a sortable table, the release group's own page beside it.

How a card comes about

Three ways in, one card, one window. The resolver takes the first that matches.

Every MusicBrainz entity kind

A card is about the link's target, so one source serves every pageType that links that kind. Endpoints are candidates, to be checked against the MusicBrainz API documentation and a probe in Phase 0.

Phases

Each phase on feature/popup-engine, a WIP changelog entry each, merged only after a browser check.

Phase 0 · probes
  • inc sets per kind, answer sizes
  • what a page without scripts still shows
  • embedded JSON beyond /release
  • cover-art presence in the browse
Phase 1 · engine + release group
  • _DP_SITES into sources, no visible change
  • both release-group cards on the engine
  • pin, every release, Live page, one gate
Phase 2 · Web Service cards
  • release, recording, work, artist, label, event, place, area, series, instrument
  • arrows step through one column
  • behind one setting, off by default
Phase 3 · page HTML
  • edit and editor cards
  • Live page for every kind
Phase 4 · containers
  • data-mb-pop, popTargets, ISRC and barcode text, UVD entries
  • page-wide scope
  • maybe a wider @include, measured first
Phase 5 · optional
  • drill-down inside the window, with Back
  • a side drawer if the window feels cramped

Decisions

The eight open questions, answered on 2026-10-07 (org/iframe.org, "answers").

  1. MusicBrainz cards are off by default

    opt-in, like every new hover feature.

  2. No new key for the Ctrl gate

    MusicBrainz cards follow the existing detail-preview setting, relabelled "every preview"; the "#" cell keeps its own.

  3. One switch for all MusicBrainz kinds

    no per-kind switches.

  4. MusicBrainz answers are kept 24 hours

    ⟳ always asks again.

  5. Links inside the window drill down, with Back

    Phase 5.

  6. Only the pages the script already runs on

    @include stays as it is for now.

  7. One rate gate for cards and the Relationships column

    its auto-load slows by one slot per card opened.

  8. The subheader link stays on a plain hover

    only the "#" cell is Ctrl-gated.

Containers beyond <a href>

Item 1b. Every form below ends as rule 1 of the resolver, an attribute stamped during pre-processing, so the engine keeps one path and the attribute survives every cloneNode(true) re-render.

i · any element, by attribute

A converter or extractor stamps the element. This is how the release-tracks "#" cell joins the engine.
