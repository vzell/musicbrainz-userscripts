Editing history in the entity window

One new button in the header of every MusicBrainz entity's window opens that entity's /<entity>/<MBID>/edits page inside the same window: a list of edits, the selected one's changes as the Discogs history's OLD | NEW diff, and Back to where you came from.

Every edit shown here is real. The pages were saved on 2026-10-20 and read by the prototype parser that becomes _mbParseEditsPage(); the windows below are drawn by a prototype of its renderer. Click rows, chips, artwork, Edit #… and ← Back.

What is reused
The window, its Back, the Discogs look

The popup window and its Back stack (Backspace, Alt+←), the Discogs history's sections, chips, pills and diff colours, the edit and editor cards that already exist, the one MusicBrainz rate gate and its cache.

What is new
A button, a page kind, a parser

✎ Editing history in the header; an edits kind in _MB_KINDS; _mbParseEditsPage(), which turns each div.edit-header block into a history row and its table.details into the OLD | NEW pane.

What it costs
One request per 50 edits

The list page already carries every edit's full details, so selecting a row costs nothing. Opening costs one page request; each "Load page N" one more. Closed edits are kept for sa_pop_mb_ttl_hours; a page with an open edit stays in memory only.

The path through the window

Each step is what the window does in order; the right column is what it asks of musicbrainz.org.

  1. An entity's window is open (Space on a recording link, as today). Its header now has ✎ Editing history.

    no request

  2. The button pushes the entity onto the Back stack and shows the edits kind: newest 50 edits, newest selected in the lower pane.

    1 page · /recording/…/edits

  3. A row (or ↑ ↓ and Enter) selects an edit: the lower pane shows its changes. Chips filter by Add / Edit / Remove / Merge / Other and by status; the order flips.

    no request

  4. Load page 2 of 7 appends the next 50 rows.

    1 page · ?page=2

  5. Edit #… drills into the existing edit card (votes, every note). An entity link drills into that entity's card. Artwork opens the artwork viewer.

    1 page · /edit/N (cached after)

  6. ← Back returns: edit → history → entity, each from memory.

    no request

Which windows get the button

Every kind with an MBID and an /edits page. The button reads the window's own MusicBrainz URL, so release groups opened by the release-group sources get it too.

Open questions

Answers change the implementation plan in org/mb-edit-history.org.

  1. The button's label

    "✎ Editing history" (MusicBrainz's own sidebar word) or a short "✎ Edits"? It shrinks to ✎ in a narrow window either way.

  2. A keyboard key for it

    H while the window is focused, like ← → step rows? Not in the mockup yet.

  3. Busy entities

    "Found at least 500 edits" is all MusicBrainz says for Bruce Springsteen. The footer then reads "Load page 11 · more than 500 edits" with no last page. Enough?

  4. The editor's own history

    The Editor card could get the same button for /user/<name>/edits. In scope now or later?

  5. Default of "Only what changed"

    On (as Discogs): context rows except the first and unchanged track lengths are hidden until "Everything".

  6. Committed fixtures

    Logged-in pages name other editors and quote their notes (public on musicbrainz.org). The Discogs fixtures already do. Fixtures from these pages, or logged-out pages plus your own edits only?

Logged out, and what can go wrong

The window fetches with the user's own MusicBrainz session. Logged out, MusicBrainz hides who made each edit and shows no notes at all; dates are in UTC instead of the user's zone.

She's a Runaway, logged out

Same 23 edits as tab 2, as the probe got them without a session.

Probe

Every "Edit by" reads "Editor hidden (log in…)"; there is no .edit-notes block. The parser marks editorHidden and notesHidden instead of showing empty values.

Failures and empty states

Each is the window's area; the header is unchanged.

A narrow window

The window at 400 px, as on a phone or a small resized window: the button is ✎ alone, a row stacks its date and pill over the text, OLD and NEW stack too (the existing max-width 760 px rules).

Touch

A tap selects a row; on a phone the pane is below the list, so the selection scrolls the pane into view.
