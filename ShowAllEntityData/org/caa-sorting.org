Confirmed. Here's the technical answer.

There is no negative cache for image bytes

_artFetchCachedImage() has three tiers, and all three only ever record successes:

const blob   = await _artGmFetchBlob(normUrl);   // ← 404 REJECTS here
const objUrl = URL.createObjectURL(blob);
_artIdbBlobUrls.add(objUrl);
_artIdbMemCache.set(normUrl, objUrl);            // ← never reached
_artIdbPut('images', { url: normUrl, blob, … }); // ← never reached

_artGmFetchBlob rejects on any non-2xx (:65919), and that rejection propagates out before any of the caching lines run. Tier 2 (IDB images) is written on the same line, so it's skipped too.

So the two states are, at the cache layer, literally identical:

┌─────────────────────┬─────────┬────────┬────────────────────────────────────────────────────────────┐
│                     │ Tier 1  │ Tier 2 │                    Result on re-render                     │
├─────────────────────┼─────────┼────────┼────────────────────────────────────────────────────────────┤
│ Image exists        │ Map hit │ —      │ synchronous lookup, painted at build time                  │
├─────────────────────┼─────────┼────────┼────────────────────────────────────────────────────────────┤
│ Image doesn't exist │ miss    │ miss   │ falls through to a network request → 404 → wrapper removed │
└─────────────────────┴─────────┴────────┴────────────────────────────────────────────────────────────┘

A missing memory entry means "never successfully fetched" — which covers both "we've never asked" and "we asked and it doesn't exist." Nothing distinguishes them, so the second is retried forever.

The galling part: that information already exists, one layer up

_artEnrichIcon() does cache negatives, at the metadata layer (:68701-68705):

// Cache sentinel (0) to suppress repeated failed requests
// across sort/filter re-renders for the same entity.
ctx.countCache.set(entityPath, 0);
ctx.imagesCache.set(entityPath, []);

— with a comment naming this exact problem, and it persists the zero to IndexedDB as well.

But _artInitBigPics() never reads it. I grepped its whole body: zero references to countCache/imagesCache. Its build loop (:69157) walks every art anchor in the table, derives front-{size} from the href, and builds a wrapper + fetch unconditionally. The metadata layer knows the release has no artwork; the stripe builder never asks.

So on the pilot page, each sort fires 20 requests to coverartarchive.org that are known in advance to 404 — and those 20 are exactly the hourglasses you'd still see.

Two independent fixes, one nearly free

1. Have the stripe consult ctx.countCache before building a wrapper. The data is already in RAM by then (_artEnrichIcon runs on the same render). A count === 0 entity gets no wrapper, no fetch, no hourglass. Narrow and cheap.
2. Give _artFetchCachedImage a negative cache — record 404s (not transport failures) so any caller stops re-asking. Broader, and it'd fix the icon column and inline thumbnails too. The precedent already exists in this codebase: ms-rec-len deliberately caches null for "no sub-second length on record", and _msFetchWs2RecordingLengths is careful to cache a successful-but-empty answer while never caching a transport error — exactly the distinction needed here.

Worth noting these are pre-existing, not something the recent work introduced — it just made them the last visible symptom. Want me to do (1), or both?
