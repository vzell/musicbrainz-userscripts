2. Why jesus2099's ms never survives a fast click

Three properties of SMC-II combine into exactly your symptom:

1. @run-at document-end, one-shot, no MutationObserver. The RECORDING_LENGTH_COLUMN block is straight-line code reached ~line 1496 of 1775, after the script has worked through a dozen other features.
2. It caches the table node before fetching (:1502): relationshipTable = document.querySelector("div#content table.tbl").
3. Its XHR load handler (:1507) writes into relationshipTable.querySelectorAll("tbody > tr") — resolved at completion time, against that cached element.

What happens next depends on our tableMode:

- tableMode: 'single' (work-recordings-filtered, artist-relationships-filtered, place-performances-filtered) —
  renderFinalTable grabs the existing table.tbl tbody and does tbody.innerHTML = '' (:43416). The element survives, so a
  late jesus2099 write lands on our rows. This is precisely why initTreleasesObserver() (:43486) and
  _repairTreleasesTd() exist.
- tableMode: 'multi' (work-recordings, artist-relationships, place-performances) — renderGroupedTable runs
  container.querySelectorAll('h3, table.tbl, …').forEach(el => el.remove()) (:44664). The original table is detached
  from the document. jesus2099's late write goes into a node nobody can see, permanently. The observer at :46042 is
  attached to our new tbodies and correctly never fires — the data never arrives at them.

And the race is trivially easy to win: all three of those multi pageTypes are non_paginated: true, so our render is pure
local DOM work with zero fetches, while jesus2099 is waiting on a WS2 round trip. I timed that exact call three times
just now: 107 ms, 179 ms, 269 ms. You only have to click before it returns.

So "why do some third-party scripts fire on our final page and others don't" isn't a property of the script — it's a property of the hook:

I probed the actual endpoints before writing anything. The spec's premise doesn't survive contact — reporting that first, since it changes the work.

A browse loop is the wrong shape here. Its cost is set by the entity's catalog, not by the page:

┌─────────────────────────┬────────────────────────────────────────────────┬─────────────────────────────────────────────────────┐
│                         │                ?artist= browse                 │                 batched rid: lookup                 │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────┤
│ Springsteen /recordings │ 746 requests ≈ 14 min (recording-count: 74540) │ ceil(rendered rows / 100) — 5 requests for 500 rows │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────┤
│ instrument-recordings   │ no endpoint exists                             │ works                                               │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────────────────┤
│ cache unit              │ per page-entity                                │ per recording — reusable across pages               │
└─────────────────────────┴────────────────────────────────────────────────┴─────────────────────────────────────────────────────┘

I verified rid:(m1 OR m2 …) batches return 100/100 with lengths, values identical to the browse endpoint. Batch 150 is accepted but capped by limit=100; batch 200 is HTTP 414 (URI too long, 8868 chars). So 100 is the exact ceiling.

Two other findings:

- instrument-recordings has no browse or lookup path at all. /ws/2/instrument/<mbid>?inc=recording-rels returns 0 relations while the page lists 100 recordings — MB models those as artist-recording rels carrying an instrument attribute. The browse plan could never have covered this pageType.
- area-recordings needs no loop. /ws/2/area/<mbid>?inc=recording-rels returned 24/24 with lengths, exactly matching the page's 24 rows — so it just needs area added to the existing single-request path's regex.

Also relevant: WS2 is 503ing roughly 1 in 3 requests right now. A 746-request loop is fragile in a way a 5-request one isn't.
