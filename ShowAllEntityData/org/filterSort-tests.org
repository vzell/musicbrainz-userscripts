* TODO findings for future implementations
** I found and fixed the missing piece, but it uncovered something bigger. Let me lay out both findings clearly:

1. Fixed (small, clean, already applied on the branch): runFilter()'s CAA/EAA init block never registered
   _caaQueue.onIdle(_showCaaCompletionToast) — the equivalent registration startFetchingProcess() has. This means the
   completion toast and #mb-info-display-caa never fired after any call to runFilter(), not just disk-restore — that
   includes every ordinary filter/sort action on a live-fetched page too. This part is a genuine, isolated bug and the
   fix is correct and safe (onIdle() already handles "queue already idle" safely via its own setTimeout(cb, 0) path).

2. A separate, bigger issue this exposed: runFilter() intentionally strips each cloned row's "already enriched" CAA/EAA
   markers on every re-render — not a bug, it's needed so _artHighlightImageLi can re-apply the active filter's
   highlights to art cells. But the side effect is that this also forces _artEnrichIcon to treat every cell as
   unenriched, re-triggering a full re-fetch of every image's enrichment data (real network calls) on every single
   filter/sort — including the very first runFilter() call right after a disk-restore, even though that data was already
   fully populated and saved in the fixture. In my test this queued 220 tasks that take real time to drain. Unlike
   Relationships (which correctly skips cells already marked relDone), CAA/EAA has no equivalent "skip re-fetch, just
   re-apply highlights" path — re-enrichment and highlight-reapplication are currently the same step.

That second one is a real architectural gap, not a quick fix — it'd mean separating "re-apply highlights" from "re-fetch
enrichment data," which needs its own careful design and testing, not something to improvise right now.

Live specs are tag-gated (@core/@extended/@perf) via --grep; snapshot regression coverage is separate (node tests/support/capture-snapshots.js [--only=<pageType>] [--headed] [--perf]), not wired into package.json.

The two .org/.html reports

Two npm scripts generate a timestamped .org/.html pair in debug/ (e.g. debug/artist-releases-filterSort-test-report-<ISO-stamp>.org/.html), via the shared engine in tests/support/filtersortReportGenerator.js:

- npm run test:live:report:artist-releases
- npm run test:live:artist-releases:full (same, with TEST_PREFILTER_LOAD=1 TEST_COLVIS=1)
- npm run test:live:report:releasegroup-releases

Mechanism: playwright test ... --reporter=list,json with PLAYWRIGHT_JSON_OUTPUT_NAME=<file> writes the JSON results to a file (list still prints to the console); the exit code is captured (e=$?); then node tests/support/generate-*-report.js < <file> reads that JSON via stdin redirection and writes the .org/.html pair; the script re-exits with the saved playwright exit code. debug/ is gitignored, so reports accumulate with no cleanup needed.

package.json: main vs. perf-steps-1-4

perf-steps-1-4 fixed the three test:live:report:*/test:live:artist-releases:full scripts — main still uses the older, fragile form: playwright test ... --reporter=json | node .... That's broken two ways main doesn't have fixed: mixing list+json reporters would interleave both on stdout if you also wanted console output, and piping loses playwright test's own exit code (the pipe's exit status is the last command's, i.e. the report generator, which always exits 0). No other differences in package.json between the branches.
