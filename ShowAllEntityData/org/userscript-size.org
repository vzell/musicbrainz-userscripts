What the numbers say:
- *Every matched page: ≈260 ms at full speed, ≈1.1 s with the CPU slowed four times*, before
  anything useful happens, and also on pages with no pageType. The script runs at document-idle,
  so the page is already visible, but the main thread is blocked for that long, on every
  navigation (MusicBrainz is a multi-page site).
- *The time grows faster than the file.* 9.99.1167 → today: 1.58× the bytes, ≈1.8× the time
  (both throttle rates). 9.99.1316 → today: 1.18× the bytes, ≈1.25× the time. More of the new
  code runs at load instead of only being parsed.
- *Never-called code costs ≈43 ms per MB, comments ≈10 ms per MB* (×1; the 10 MB and 15 MB code
  pads agree on the first). 10-10 measured 20 and 4.5 on the same host in its faster state: the
  ratio of the two (≈4.4) is the same. *Pre-parsing alone* (the never-run copy) is ≈45 % of
  today's cost.
- *A stripped copy saves ≈18 %, a stripped one-byte copy ≈22 %* (×1; 16 % and 20 % at ×4).
  Comments are cheap to scan; the one-byte form is another ≈5 % faster to parse.
- *At 15 MB of code — the end of the year at October's pace — a page pays 2.15× today's cost*:
  ≈0.57 s at full speed, ≈2.4 s at ×4.
- *The cached changelog* does not slow the script's own synchronous part (the library parses it
  after the script), but the page settles ≈9 ms later at full speed and ≈34 ms later at ×4.
- *Supported pages* (each its own run; compare within a table only): today's file costs ≈1.9×
  what 9.99.1167 costs there (≈1.8× on the bare page), stripping saves 17–19 %, and what the
  script defers until the page settles adds 12–17 ms at full speed, 45–60 ms at ×4 — without
  MusicBrainz's own stylesheet, so the real style work is likely larger.

Tampermonkey makes ~GM_getValue~ synchronous by handing a script's WHOLE store to the page at
injection. Its own issue tracker shows it: issue #2045 asked to stop "preloading all storage data
at script start" for scripts that do NOT use the legacy ~GM_getValue~/~GM_setValue~; that was
done in 5.3.6207, and the maintainer decided against changing the old API. This script grants
the legacy API, so it still gets the whole store up front. Issue #1787 shows the limit: a 23 MB
store broke with "message length exceeded". So every value this script ever stored travels to
every matched page, before a line of the script runs.

What is stored that is big (startup sweep, 2026-10-22). The cached texts come from the MIRROR
(~REMOTE_BASE~, still 9.99.1167); the next publish makes them the dev repository's sizes.

  the new value to every other open tab of the script (it supports value-change listeners) is

** 2.4 CSS, listeners and observers on a supported page

From the startup sweep (code reading; the timings in 2.1 include all of it):
- *About 207 kB of CSS* is injected at load on a supported page, in about 12 ~<style>~ elements:
  the global block (141 KiB, much of it CSS comments inside the template literal) and the popup

* 5. Libraries (question 3)

** 5.1 What a Tampermonkey ~@require~ library is — and what it is not

- A required file is downloaded at install and stored by Tampermonkey; on every matched page it
  runs before the script, in the same sandbox, with the script's grants, and its top-level names
  are visible to the script (that is how ~VZ_MBLibrary~ works today). The script's own code
  stays inside its IIFE, so a library sees none of it unless the script hands it over.
- *It is not lazy.* Every ~@require~ is injected and parsed on every page the script matches. A
  library cannot be loaded only on discogs.com, or only when somebody hovers a link. Moving code
  into a library changes WHERE the bytes live, not how many each page parses (2.1: the cost
  scales with the code a page parses). Two routes would change what a page parses:
  - a separate userscript with its own ~@include~ list — rejected in 10-10 §3b, and the previews
    sweep adds reasons (5.2);
  - lazy loading: ~@resource~ text read with ~GM_getResourceText~ and evaluated only when needed.
    Not recommended. ~GM_getResourceText~ is synchronous, so Tampermonkey very likely hands the
    resource text to every page anyway, as it does the GM values (not verified). It needs ~eval~
    in the sandbox. And it costs readable stack traces.
- *Since Tampermonkey 4.16 externals refresh only when the script itself updates*, and a
  library has no entry of its own in the dashboard. This project has already lived through both
  failure modes with its one library: SAED 9.99.1138 ran against library 4.0.0 and behaved
  differently with nothing saying so (the library's 4.3.0 changelog), and
  ~CustomizableMultiSelector.user.js~ shipped with a ~file://~ ~@require~ from 2026-02-02 to
  2026-09-25 — which fails silently for every user. Every new library multiplies the publish
  rewrite that ~check-publish-ready.py~ exists to catch.
- New failure modes a library would bring: a missing library throws a ~ReferenceError~ (only
  ~VZ_MBLibrary~ has the ~Lib~ stub fallback); a script declaration silently shadows a library
  name; ~__saTest~ exposes ≈20 parsers through the script's closure and would have to be
  re-pointed.
- Done right, each library needs an immutable URL per release (a tag or commit plus
  ~#sha256=~ SRI, which Tampermonkey checks at install), a version handshake at startup (the
  script refuses an older library loudly), and its own entry in the publish check.

** 5.3 Answer

*Feasible for some parts, but a library is the wrong primary tool.* It does not make a single
page cheaper (5.1), it adds the publish and version-skew hazards this project has already paid
for once, and the parts that are cleanly separable today (extractors, AR helpers, title case,
the settings schema) are exactly the parts whose separation buys least — they are edited
together with the code around them.

The order that gets each benefit where it is cheapest:
1. *Per-page cost first, no split needed* (4: the changelog, the orphaned GM values, the
   publish copy, ~.meta.js~). That is where the users' milliseconds and megabytes are.
2. *Manageability: the byte-identical fragment split* (10-10 §2.4). ~src/NN-name.js~ joined back
   into the same IIFE, so no scope, TDZ or behaviour changes, proven by SHA-256 equality on the
   first cut. It gives one file per subsystem of 1.2 — 20 to 40 files of 100–800 KB — which is
   what "relocate the popup code / the non-MB code / the extractors" is really asking for, without
   a single new URL for users.
3. *Libraries only where there is a second consumer*, starting with the smallest pure piece: the
   title-case engine (your Springsteen scripts), then WS/2 client plus rate gate and the escapers
   if MB_PageEnhancer wants them (that is a "VZ_MBCore" or an extension of ~VZ_MBLibrary~), then
   the popup engine behind ~_popSources()~ if a second script wants link previews. Each with an
   immutable URL, SRI, a version handshake and a publish-check entry (5.1).
