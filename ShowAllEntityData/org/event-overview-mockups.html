The event overview page

A new pageType for /event/<mbid>. Its button turns the relationship lists and the setlist into filterable, sortable tables, and puts the 15 Event Art Archive images above them. Every part is a setting of its own. All mockups run on the real data of one concert. Type in a table's filter, click a column header to sort, hover a thumbnail for its card, click it for the viewer.

Today

reference

The native overview. Relationships are nine small two-column lists, one target per line. The setlist is a single paragraph of lines. Nothing can be filtered or sorted, and the event art sits behind the “Event art (15)” tab.

Requests
0. Seeing the art means opening a second page.
No pageType today
Only event-tags exists; nothing matches the bare /event/<mbid> path.
C

Every part is a setting

recommended

A new “🎫 EVENT PAGE” group in the settings dialog. The first box adds the button at all; each part under it can be turned off on its own, and the two layout choices make T1/T2 and S1/S2 user choices instead of ours. Change any of them: the page on the right is rebuilt the way the script would render it.

Defaults
Everything on, with T2 and S1 as the layouts. Each setting is read once per render.
Owed per setting
A configSchema entry, the defaults dump, and its fixture/off state in a spec.
T1

Relationships as one table

alternative

Every target of every list becomes one row: the relationship, the target, its entity type, whatever followed it on the line, and which heading it came from. One filter searches everything, which is handy for a quick “is X credited anywhere”, but most columns are half empty because a recording, a place and a URL have little in common.

Rows
Render
tableMode: 'single', one table.tbl
T2

One sub-table per target type

recommended

The script's normal multi-table view: an h3 per target type, each with the columns that fit it, its own count and filter. Recordings name where the setlist played them; the related series' own relationships (its tour artists, its parent series, its links) keep their own table, so they are never mistaken for the event's.

Tables
Render
tableMode: 'multi'; native anchors kept, so flags and entity links survive
Cross-check
“In setlist” matches a recording's title to the setlist's work names; no request
S1

Setlist: one sub-table per part

recommended

The line-up, then one table per setlist part (“Soundcheck”, “Concert”), each under its own h3 with its count. A part's note line (“Scheduled: …”) sits under its h3 instead of becoming a row. A medley line stays one row with every work it names; a song played in two parts is marked in both; a song with a recording made at this event shows 🎙.

Tables
Source
p.setlist line by line; everything after the paragraph (another script's “Event Schedule” block) is left alone
S2

Setlist: every song in one table

alternative

All songs in one table with a “Part” column, the line-up beside it. Better for filtering across parts (“every song from The River era”), but the per-part counts move out of the headings.

Tables
Sorting
“Part” then “#” restores the running order after any other sort
E1

“Event art (15)” section

recommended

The release page's Cover art section, fed from the Event Art Archive. The type chips are the archive's event types; an image with two types (“Schedule / Poster”) counts for both. Grid and By type only: Spreads and the medium thumbnails are release packaging and stay on the release page.

Requests
0 before the button; then 1 JSON to eventartarchive.org (or 0 from the shared cache) + 15 lazy 250 px thumbs
Where it lives
Before h2.relationships; the end of #content when an event has no relationships
Record shape
As a cover art record plus an event key, and no back flag
E2

The tab opens the viewer

recommended

A plain click on “Event art (15)” opens the viewer on a grid of every image instead of leaving the page. Ctrl-click, middle click and Shift-click still open the archive page. Keys as on the release page: ← → step, Z zoom, G grid, I info, Esc close.

Try: click the outlined tab, or a thumbnail in E1.
Requests
1200 px only for the image in view, ±1 preloaded
Shared
The same _artViewer* component as the release page, driven by EAA_CTX
✓

Recommendation

Ship the pageType with C (every part a setting), T2 and S1 as the default layouts, and E1 + E2 for the art. Whether T1 and S2 ship as the alternative values of the two layout settings is your call: each costs one extra render path and its specs.
