Which other sites get tables and previews

Every non-MusicBrainz site the script supports, what pageTypes (PT) it has, where the link previews (POH: card on hover, window on Space) work, and which links inside a preview window open there or in a new tab. The same data is shown two ways, so you can pick the report's format.

Both render from the same data object, the proposed registry.

Gaps and stale docs

What NON-MB-COVERAGE.org would hold, as Emacs shows it. 1a, 1b and 2a are ordinary org tables. 2b has a third dimension (the site you are on), so it becomes one table per site; only the musicbrainz.org one is shown in full, the other five have the same shape.

Comparison
Org tables
  • Lives with the other org docs; greppable; diffable line by line.
  • 1a, 1b and 2a read well: one row per PT or reader.
  • 2b turns into six 14×10 tables of single letters. You read one by matching a row label to a column number.
  • No colour, so a gap looks like any other "T".
Rich HTML
  • 2b is one matrix with a site switch; gaps stand out in colour.
  • Evidence and "why" sit in the cell, not in a footnote.
  • Needs a browser or the published Artifact to read.
  • Diffs are only readable in the JSON it is built from.
Recommendation
  • One JSON registry as the source, checked against the userscript by build-coverage-report.py --check.
  • HTML as the report people read.
  • Optionally the org file generated from the same JSON, for grep.
Keeping it current

Both mockups are drawn from one data object with the shape proposed for docs/non-mb-coverage.json: sites → pageTypes (IP/FRP state, evidence, why), readers, windows, link families, and per-site routing. scripts/build-coverage-report.py --check reads pageDefinitions (host:), _DP_SITES, _EXT_READERS and the _DP_WIN_* sets from the userscript and fails when a host, PT or reader exists on one side only. A new site then cannot ship without its rows.
