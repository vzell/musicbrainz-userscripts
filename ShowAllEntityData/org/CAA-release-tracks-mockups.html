Cover art on the release page

Eight ways to show all 16 Cover Art Archive images of a release on its overview page, so nobody has to open the separate “Cover art (16)” tab. Each mockup runs on the real data of one release. Hover a thumbnail for its card, click it for the viewer.

Today

reference

The sidebar shows the main front at 250 px. The other 15 images are one click away, on a page that leaves the tracklist and everything the script built on it. ShowAllEntityData does nothing with cover art on this page.

Requests
0 (MusicBrainz renders the sidebar image)
What it costs the user
A page change, then the back button, which reloads the release page and its consolidated tracklist
R1

“Cover art” section above the tracklist

recommended

A new collapsible h2, built like every other h2 on the page. Collapsed, it reads its count from the tab text and costs nothing. Expanded, it loads the archive JSON once and shows a contact sheet. The type chips filter the sheet; the second switch groups it by type. ★ marks the archive's main front, which is not the same thing as “has the Front type”.

Try: Click a chip to filter, a thumbnail to open the viewer.
Requests
Collapsed: 0. Expanded: 1 JSON (or 0 from the shared cache) + 16 lazy 250 px thumbs
Where it lives
Inserted before h2.tracklist, so makeH2sCollapsible() wraps it and stops at “Tracklist”
Risk
Must stay outside the tracklist's global filter, row counts and master toggle
R2

Filmstrip under the tabs

not recommended

A single scrolling row of 72 px thumbnails between the tabs and the page. Compact and always in view, but it needs the JSON and every thumbnail on each page load, it pushes the tracklist down on every release, and the 72 px tiles are too small to tell Liner pages apart.

Requests
1 JSON + 16 thumbs on every page load
Verdict
R1 shows the same images at a useful size and only when asked
R3

Sidebar gallery

optional

The native sidebar image gets a 4-column grid underneath. Hovering a small tile swaps the big image and its caption in place; clicking opens the viewer. It leaves the main column alone, but the 50 px tiles are small and the grid becomes four rows tall for this release.

Requests
1 JSON + 16 thumbs on page load, or on the first hover of the sidebar image
Risk
Touches native MusicBrainz markup (div.cover-art), which other userscripts also decorate
R4

The “Cover art (16)” tab opens in place

recommended, as an add-on

A plain click on the tab opens the viewer in grid mode over the page instead of navigating. Ctrl/Cmd-click, middle-click and “open in new tab” keep working, because the link stays a link. The small marker on the tab tells the user the click behaves differently. Click the tab below.

Requests
0 until clicked; then as R1 expanded
Why add-on
Costs one delegated click handler and reuses R5 entirely
R5

Viewer

recommended, shared

The lightbox from the CAA/EAA column study (D1 there), with one release as its whole scope. It shows the 250 px thumbnail at once and swaps in the 1200 px image when it arrives. The info panel is the house liner card. Build it once: whichever branch lands first owns the viewer, the other reuses it.

Open at:
KeyAction
← →, swipePrevious / next image; wraps at the ends
Home EndFirst / last image
click, ZToggle 2× zoom; the zoomed image follows the mouse
GGrid of all images, grouped by type
IShow / hide the info panel
OOpen the original image in a new tab
EscClose (from grid: back to the image); focus returns to the opener
Requests
0 JSON (reads the same cache as R1); 1200 px per image viewed, ±1 neighbour preloaded
Out of scope
Editing, reordering, removing art. The script reads; it does not edit
R6

Spreads and booklet

later, optional

A third layout for the R1 section. Images whose comments end in “left” and “right” and share the rest are shown as one opened spread; Liner (and Booklet) pages are paged two at a time in archive order. Pairing is a heuristic on free-text comments, so anything unpaired stays a single page and the layout never hides an image.

Requests
0 beyond R1
Heuristic
/^(.*?)\s*\b(left|right)$/i on comment, same prefix, same type
R7

Medium art beside each medium

later, only with explicit comments

A small thumbnail of the label or disc in each medium's h3. The archive has no link from an image to a medium, so this can only guess. The proposed rule assigns an image only when its comment names the medium (“disc 2”, “LP 3”, “side C”) or when Medium images and media are equal in number. This release has 4 Medium images, 3 media and no comments, so the rule refuses and says so. The second button shows the matched look.

State:
Requests
1 JSON at page load (types are needed before anything shows)
Risk
A wrong guess puts disc 2's label on disc 1. Refusing is the safe default
✓

Recommendation

Ship R1 + R5, with R4 as a small add-on. Nothing loads until the user asks, the archive JSON is shared with the CAA column's cache, and the viewer is the same component the CAA/EAA column study already plans. R3, R6 and R7 can follow once that settles. R2 stays out.
