*** 1a. Credentials: how logged-in content gets in without the script holding them

The script never asks for, stores or uses a user name or password, and never
logs in by itself. You log in on the site in your browser, and the script
rides on that session.

What already happens today (code reading):
- List fetches on SL and BB go through =fetchHtml()=, which is
  =fetch(url, {credentials: 'same-origin'})=. They send your cookies, so a
  logged-in tab already fetches logged-in pages. The BB recent-changes POST
  does too: its token is the =wikidot_token7= cookie (=_bbWikidotToken()=).
- Detail cards opened ON the site use =_dpFetchText()=, also same-origin with
  cookies.
- Cards opened from MusicBrainz or another site use =_extFetch()=, a
  =GM_xmlhttpRequest= with =anonymous: true=. That is on purpose: the card
  shows what everyone sees. =org/iframe.org= X9 measured Brucebase at 120,699 B
  anonymous vs 123,822 B with your cookies.
- So the converters already receive the extra content and simply ignore what
  they don't know.

What has to change in the implementation phase:
1. Login detection from the page: =_slLoggedIn(doc)= (SL renders the
   =hTxtPassword= log-in form to visitors) and =_bbLoggedIn(doc)= (Wikidot
   renders "Sign in" in =#login-status= to visitors). The probe confirms
   which markers the logged-in pages carry.
2. *Cache collision.* The detail-card cache (IndexedDB
   =vz-saed-detail-pages=, =_dpMem=, =_dpRawMem=) is keyed by URL only. A
   public parse and a logged-in parse of one page replace each other for 30
   days (=_DP_TTL_MS=). Fix: store the login state in each record, treat a
   mismatch as a miss, and bump =_DP_PARSER_VERSION=.
3. Converters add logged-in-only columns only when the pages have them, with
   headers decided per run, so a logged-out run looks exactly as today.
4. A login chip on the toolbar h1 ("● Logged in · your view" / "○ Public
   view"), and a mixed run (session expired halfway) reported with the page
   where it changed.
5. Optional, per host: =sa_pop_ext_with_session= (default false) to drop
   =anonymous= for SL/BB cards opened from MusicBrainz. Only after a probe
   shows such a request passes Cloudflare.

Rules: no =sa_*= setting for user or password; no cookie read except
=wikidot_token7= (as now); a committed fixture made from a logged-in page
goes through a scrub step first. MusicBrainz is untouched: all of this sits
behind =_isSlHost= / =_isBbHost= and the sites' opt-in settings.

*** 1b. Cloudflare on SL

- *Where it does not bite:* in your tab. Same-origin requests carry the
  clearance cookie and come from the real browser
  (=docs/claude/springsteenlyrics.md=, "fetchHtml() is a same-origin
  fetch()"). Logging in changes nothing here.
- *Where it does:* cross-origin anonymous =GM_xmlhttpRequest= (no clearance
  cookie; =_extFetch()= already recognises =cf-mitigated=), Python probes
  (403; see the memory note on Python probe refusals), and later Playwright.
  The clearance is tied to the browser and IP, so you solve it once in the
  headed login window and the live specs must use the same user agent.
- Today a challenged list page reads as "0 cards". Proposal: a
  =_slIsChallenge(doc)= check, so =_fetchIncompleteSummary()= says "the site
  sent its Cloudflare check instead of page N; open the site in this tab,
  then Resume".
- The probe records the Cloudflare outcome of its cookie-less requests. That
  is the first real data point on how often it fires.

*** 2. How we find out what logging in adds

=scripts/probe-logged-in-diff.user.js= is a throwaway Tampermonkey script,
never published.
1. Install it, log in on the site, open any page of that site.
2. In the Tampermonkey menu, run "Probe: what logging in adds (all pages)", or
   "(this page)" for one page.
3. When asked, type the terms to redact (your user name, real name). They
   stay in the browser.
4. Wait about 25 s per site: two requests per page, 1.1 s apart, 10–11 pages.
5. Review the JSON in the box, press Download and put the file into
   =debug/= (=logged-in-diff-sl-YYYYMMDD.json=, =…-bb-…=).

Each page is fetched with =credentials: 'omit'= and with
=credentials: 'include'=, parsed with DOMParser and compared. The report holds:
- status, size, Cloudflare mark and login marker of both answers;
- headings, tabs, table headers and forms only the logged-in page has;
- link kinds and image counts that differ;
- for each new block: its path, heading, link kinds, image count, form field
  NAMES and a redacted excerpt of at most 120 characters.

What is never read or reported:
- cookies and input values (a textarea's content counts as a value);
- the user name the page shows, plus your typed terms → =«USER»=;
- e-mail addresses, long token-like strings, session-like URL parameters;
- link URLs other than their kind.

Checked with =node scripts/check-probe-logged-in-diff.js= (Playwright
Chromium, no network). It plants a logged-in block in
=debug/detail-sl-collection-7431.html= and asserts the block is found and no
planted secret reaches the report. Mutation-checked: with =redact()= off, three
checks fail; with the textarea guard off, one fails. The check found two real
