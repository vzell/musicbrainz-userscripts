    Credits) is pinned as one block.
  - 2. Wikipedia licence note covering the link: fixed. The "Continue reading" link and the licence note were pinned separately at the same left edge, so one was drawn over the other.
  - 3a. "Add a new alias": removed on artist and all other entity Aliases pages.
  - 3c. Credits: fixed. Its only column fills the whole 906 px table, so it had no room to dock. A table that fits in the window is now pinned whole.
  - 3b. Aliases table docking: not reproduced. On fddfe5b, logged in, at 2000 and 2034 px with real scrollbars, the table docks at 20 px every time. Your snapshot has no trace of the docking stylesheet at all, so please re-check it on the new build.
  - 4f. Other page types: a new live sweep covered all reported pages plus every registered page type, and finally left nothing behind. It found one more case, edit/notes-received's alert checkbox, which is fixed too.
  - 5. Re-measure on petri: done; the harness is now committed in tests/support/.

  Found along the way:
  - A real bug in fddfe5b: after a refresh while scrolled right (e.g. a window resize), the sticky column lost its docked state and the strip to its left stopped being masked. fddfe5b's own docking test fails on petri every time with fddfe5b's own code; vzell-lap just never hit
    the timing. Fixed, with a test that forces the case.
  - Two millisecond-length tests only passed because a layout shift moved the button out from under the mouse. They now read the tooltip text correctly.

  Tests: the full fixture suite passes (1015). All 40 planted defects in the sticky mutation list behave as recorded, and lint is within the baseline. I ran npm test, not the test:full merge gate.

  Performance (petri, everything in one session):
  - On the big artist-events table, today's changes are indistinguishable from fddfe5b.
  - Decision for you: pinning a table whole costs about +60 ms per sort on the 521-row Credits table (+17–20%). It appeared in every round of three sessions and disappears when only that part is switched off. I didn't measure how it grows with more rows. Options: accept it, cap
    whole-table pinning at some row count, or drop it, in which case narrow tables scroll away again.
  - Separate flag from fddfe5b itself: after a sort finishes, the browser stays busy longer before going idle: +1.1 s in 7 of 9 rounds this session, +0.5 s in the first. Not traced to a cause yet.

  Known limit (documented in DEBUG-NOTES.md): a pinned block is capped to the window width. If unbreakable content inside one were the only thing making a page too wide, the feature could switch on and off repeatedly. No MusicBrainz page is known to do that.

  Should I commit, after you've reviewed git diff? I'd also like your call on the pinning cost.
