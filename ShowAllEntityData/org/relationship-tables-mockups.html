Relationships as tables, everywhere

The event overview already turns its relationship lists into filterable, sortable tables. This study applies the same converter to every other entity page that carries those lists: Place, Area and Instrument (no pageType yet), and Series, Work, Release group, Label, Artist, Recording and Release (which already have a main table). Every table below runs on real data from ten pages captured today. Type in a filter, click a column header to sort.

Can several h2 sections each have their own filter?

NOThe script handles one dataset per page. One h2 carries the global filter, the row-count stats, the status line, the Clear button and the master toggle. All of that is shared, page-wide state: the merged page definition, the row arrays, the filter cache and the filter's fixed element ids. What it does support:

  • Many h3 sub-tables under that one h2, each with its own filter, count and collapse.
  • Several native h2 sections that can be collapsed, without filter or stats.
  • Either/or buttons on pages with two data sections (area-releases, artist-aliases). Pressing one removes the other section; pressing again reloads.

So every page in this study gets a second button. Its main button works exactly as today. Specimen Q shows this on the recording page.

R1

Recording: one table per kind, then “Via” each work

recommended

One sub-table per kind of target, in MusicBrainz's order, each with only the columns it fills. Each related work gets a “Via Badlands” table with a Type column, exactly like the event's “Via <series>”. Those rows describe the work, not this recording, and the heading says so.
