0 · Overview

How the parts fit

When the network is down the browser cannot load musicbrainz.org or the Springsteen sites, so Tampermonkey never starts the script there. A fully offline start therefore needs a page that comes from this machine. The four parts below build on each other; each is useful on its own.

1 · Live page phase 0

  • Notices the network is gone (failed requests, not just navigator.onLine).
  • Stops waiting on timeouts and serves expired cache entries instead of deleting them.
  • Offers the last snapshot of this page.

2 · Browser storage phase 1

  • Kept forever for the Springsteen sites (per site, opt-in).
  • Site images stored like cover art.
  • Asks the browser not to evict it (navigator.storage.persist()).

3 · Snapshots phases 2–3

  • 📸 runs every button of a site and stores keyed rows.
  • Written to a local archive outside the browser.
  • Two snapshots compare row by row, shown as an ordinary table.

4 · Local archive page phase 4

  • A page on 127.0.0.1 (or file://, if the probe shows Tampermonkey runs there).
  • The script runs on it like on any site and loads snapshots.
  • Works with the network unplugged.

Separate from all of this, a raw copy of each site (WARC, made by a crawler on a schedule) is the insurance against a shutdown: it keeps everything, including the parts the script does not read.

Behaviour

  • When it fires: two or three requests fail with status 0 or a timeout within a short time, or the browser sends its offline event. navigator.onLine alone is not trusted: it stays true on a LAN without internet.
  • Cached data only means every fetcher answers at once from IndexedDB, including expired entries (marked stale), and no expiry sweep runs.
  • It goes away on the online event plus one successful request; queued retries then run once.
  • On MusicBrainz the same banner appears, and the menu lists Save-to-disk files only if the user points the script at a folder (phase 2).

Why a local page

  • Offline, the real sites never load, so no @include line can match.
  • A localhost page needs only a new @include and a host: 'local' pageType; its loader is _hydrateAndRenderFromSnapshotData(), unchanged.
  • Its own origin can hold a merged image cache for all four sites, which per-site IndexedDB cannot.
  • The probe answers whether Tampermonkey runs on file:// in your browser. If it does, no server is needed for viewing.

What a snapshot is

  • One record per row: a key (the row's own link, e.g. /gig:2026-04-16-…), the visible cell text per column, and the cell HTML for display.
  • Filled dot: rows plus detail pages. Hollow: rows only. Grey: incomplete, kept for the record but never compared, because a missing page would read as hundreds of removed rows.
  • A userscript cannot start on its own. Due runs show as a reminder on the next visit ("Brucebase: last snapshot 9 days ago"), or a scheduled Playwright job takes them.

How rows are matched

  • By key, never by position: SL path plus item, lyrics song=; JL artwork link; KF Code; BB the page link (two BB headings have none, so date plus anchor is the fallback).
  • A row whose key changed reads as one removed plus one added. A second pass pairs them when the title and date match, and shows them as moved.
  • Text is compared after the same clean-up the filter uses (getCleanColumnText()), so markup-only changes on the site do not flood the diff.

Why per site

  • Browser storage belongs to one site address, so each of the four sites has its own quota, its own persist grant and its own toggles.
  • "Forever" is a separate switch, not a huge number of days, so a TTL setting read with || can never turn it back into 30.
  • MusicBrainz keeps its current TTLs; nothing here changes them.
