## 9.99.554 — 2026-04-29

**🐛 Fix**

- Fix sub-table filter (STF) silently failing to match rows after any previous filter pass has left fragmented text nodes in the live DOM: when applySubFilter step 2 clears mb-subtable-filter-highlight spans it does `n.replaceWith(document.createTextNode(n.textContent))`, which leaves the replacement text node as a sibling of the surrounding text nodes WITHOUT merging them. The browser does not automatically call normalize() on parent elements after replaceWith(). Consequently getCleanColumnText() sees e.g. three sibling text nodes '"U"', '"nited States"', '"(US)"' instead of one contiguous '"United States (US)"'. Because getCleanColumnText joins all collected text nodes with a space (textParts.join(' ')), the result is '"U nited States (US)"', and '"Un"' no longer matches (example 1). The same fragmentation breaks any query token that straddles a previously-highlighted boundary: '"(Pi"' fails to match '"(Pitman pressing)"' because the '"("' and '"Pi..."' fragments get a space inserted between them (example 2); '"-01-"' fails to match '"1973-01-05"' for the same reason (example 3). Fix: add root.normalize() in getCleanColumnText() immediately after the clone-and-strip step and before the TreeWalker. normalize() merges all adjacent sibling text nodes in the subtree, restoring contiguous text so join(' ') only inserts spaces at genuine inter-element boundaries. Calling normalize() on root (the clone when stripping was needed, or the live element otherwise) is safe — it never alters visible content, only the internal text-node structure.

Falls back to `true` (highlight ON) when the button element cannot be found.

## 9.99.549 — 2026-04-28

**🐛 Fix**

- Fix false-positive filter matches caused by the invisible sentinel text 'caa-inline-yes' / 'caa-inline-no' in `.mb-inline-art-sort-key` spans leaking into general filtering: e.g. filtering for 'nl' matched rows solely because 'caa-i\*\*nl\*\*ine-yes' was present in a cell's hidden sort-key span. Root cause: `.mb-inline-art-sort-key` was deliberately absent from `_CLEAN_STRIP_SEL` (by design, so that `applyUniqVal('caa-inline-yes')` column-filter clicks could drive filtering through the normal `getCleanColumnText` text pipeline without a special bypass). This meant the sentinel text was included in every `getCleanColumnText` call — global regexp filter, global plain-text rel-cell fallback, STF row-match (since 9.99.548), sort keys, and unique-values dropdown counts. Fix: added `.mb-inline-art-sort-key` to `_CLEAN_STRIP_SEL` so it is stripped from all general text-extraction paths. The `applyUniqVal` / column-filter path is preserved via a direct bypass in `testRowMatch`: before the normal `getCleanColumnText` text comparison, the column-filter code now queries `cell.querySelector('.mb-inline-art-sort-key')` directly and performs an exact (case-insensitive or case-sensitive) string equality check against `f.val`; a `match = true` from this check short-circuits the subsequent text comparison. The bypass is intentionally skipped for regexp column filters (regexp matching against sentinel values would be unusual and unreliable). Also added `.mb-inline-art-sort-key` to the element-level `FILTER_REJECT` list in `highlightCrossTag` so that the sentinel text is never wrapped in a highlight span.

## 9.99.545 — 2026-04-27

**🐛 Fix**

- Fix permanent Relationships (and Release-events) column-header destruction on multi-table pages when a global filter removes ALL rows from any sub-table, followed by clearing (or changing) the filter: root cause was that both `_suppressRelationshipsIfNoReleaseOrReleaseGroupLinks(table)` and `_suppressReleaseEventsIfNoReleaseLinks(table)` are called inside `renderGroupedTable()` after rows are appended to each group's `<tbody>`. When `runFilter()` passes a filter that matches zero rows, `tbody.innerHTML = ''` is executed first and then the empty group's rows (none) are appended — leaving the tbody with no `<tr>` elements. The two suppression helpers then find no `/release/` or `/release-group/` links (false negative due to empty tbody) and unconditionally delete the `Relationships` / Release-events `<th>` from the thead. On the next `renderGroupedTable` call (`query = 're-run'`, also truthy so existing tables are reused), the real rows are reinserted but the suppression guards now return early because links ARE found — leaving the thead permanently missing the already-deleted `<th>`. The browser then shifts every subsequent column left by one: `.mb-rel-cell` (Relationships data) appears under the Picard column header, and the Picard `<td>` has no header at all. Fix: added an empty-tbody guard at the top of both suppression functions — `if (!_tbodyForCheck || !_tbodyForCheck.querySelector('tr')) return;` — so that suppression is never triggered when the tbody has zero rows (state that is inherently indeterminate and is always due to a filter pass, not to the absence of release links in the data).


## 9.99.544 — 2026-04-27

**🐛 Fix**

- Fix regexp highlighting not applying for `^…` (start-of-string) patterns in cells whose first DOM content is a decorative/UI element rather than plain text: (1) cells on series pages whose Release column combines a `[data-erg-btn]` `▶` toggle span and a `.mb-caa-inline-ph` inline-thumbnail span before the actual text — the `▶` glyph and the `🗄️` cache-hint emoji inside the inline-ph span both inflated the highlight walker's `fullText` at position 0, so `^` referred to before those characters; (2) the extracted Country column on release-group pages whose cells contain a flag `<img>` followed by a formatting-whitespace text node (` `) before the `<a>` country text — the space shifted the `^` anchor by one character. Root cause: `highlightCrossTag` used a `NodeFilter.SHOW_TEXT`-only TreeWalker, which cannot issue element-level `FILTER_REJECT` to prune entire subtrees; every text node (including those inside `[data-erg-btn]`, `.mb-caa-inline-ph`, and whitespace-only inter-element nodes) was included verbatim in `fullText`. The filter path uses `getCleanColumnText()` which clones-and-strips those same elements and skips whitespace-only / decorative-icon text nodes, so the filter matched but the highlighter did not. Fix: switch `highlightCrossTag` to `NodeFilter.SHOW_TEXT | NodeFilter.SHOW_ELEMENT`, add element-level `FILTER_REJECT` for the same exclusion set as `_CLEAN_STRIP_SEL` / `getCleanColumnText` (`script`, `style`, `[data-erg-btn]`, `.mb-caa-inline-ph`, `.mb-eaa-inline-ph`, all `.mb-art-cache-hint-*`, `.mb-caa-count-badge`, `.mb-eaa-count-badge`, `.mb-caa-art-li-image`, `.artwork-icon`, `.caa-icon`, `.icon`), and add text-node `FILTER_REJECT` for whitespace-only nodes and decorative-icon glyphs (mirroring the `isDecorativeIcon()` guard in `getCleanColumnText`). All other element nodes receive `FILTER_SKIP` so their children are still visited. The resulting `fullText` is now positionally equivalent to the string `runFilter()` tested the regexp against, making `^` anchors highlight the correct character in the first real data text node.

## 9.99.541 — 2026-04-23

**✨ Enhancement**

- Add `_suppressReleaseEventsIfNoReleaseLinks(table)` helper that applies the same data-driven release-link guard used by `initPicardTaggerColumn` to the Release events injected column and all ICE synthetic columns derived from it (`Release country`, `Release date`, `R-DD`, `R-MM`, `R-YYYY`, `R-Day`, `R-Month`). When a rendered sub-table or single table contains no `a[href*="/release/"]:not([href*="/release-group/"])` anchor in its tbody data cells (excluding `.mb-sticky-col` and `.mb-rel-cell`), the helper removes the Release events `<th>`, all `mb-ice-th` synthetic `<th>`s, their corresponding `<td>` cells from every body row, and the matching cells from every secondary thead row (filter row etc.). This prevents the Release events column from appearing on non-release relationship sub-tables on `place-performances` and `label-relationships` multi-table pages (e.g. "Held concert at", "Member of") and on `place-performances-filtered` / `label-relationships-filtered` single-table pages when the filtered relationship type is not a release relationship. The helper is hooked into the multi-table group loop immediately after each sub-table's tbody rows are appended, and into the single-table pipeline immediately after `renderFinalTable` + `cleanupHeaders`. It runs before `initReleaseEventsColumn()` in both pipelines so that `mb-re-cell` placeholder `<td>`s are never created for suppressed tables.
- Fix sticky column hover highlight: `applyStickyColumn` sets an explicit inline `style.background` on each body sticky cell (snapshotted from the zebra-stripe CSS class so the cell remains opaque while scrolling horizontally). Inline styles have unconditional cascade priority — they win over every author-sheet rule including `!important`, so MusicBrainz's native `tr:hover > td` rule cannot override the sticky cell's background. Fix: `applyStickyColumn` now stores the rest-state colour in `cell.dataset.mbStickyBg` (refreshed on every `_apply()` call so re-runs after zebra re-striping always have the current value), and attaches `mouseenter`/`mouseleave` handlers on each `<tr>`. On `mouseenter` the handler reads the hover background from the first non-sticky sibling `<td>` via `getComputedStyle` — at that moment the browser has already applied its `:hover` rules to siblings, so the value is the actual live hover colour — and writes it directly to `c.style.background`. A fallback of `#e2e2e2` (MusicBrainz's known hover tint) is used when the sibling's computed background is still transparent, matches the rest colour, or is otherwise unavailable. On `mouseleave` the handler restores `c.style.background` from `c.dataset.mbStickyBg`.
