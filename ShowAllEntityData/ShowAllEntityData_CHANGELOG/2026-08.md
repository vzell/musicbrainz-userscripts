## 9.99.976 — 2026-08-31

**🐛 Fix**

- Unique-values dropdown: the panel no longer closes itself the instant it opens when the 📊 button had to be scrolled into view first. Scroll events are dispatched asynchronously (at the next rendering opportunity), so a scroll that happened BEFORE the panel opened was still delivered AFTER it opened, and the close-on-scroll listener acted on it. Because `.mb-col-uniq-wrap` is focusable, this was reachable in normal use: clicking — or tabbing to — a 📊 button that is only partially in view makes the browser scroll it into view on focus, and that scroll event lands one tick later, right after the click handler already built and positioned the panel. The panel flashed open and vanished, with focus bounced back to the previously-focused column filter input.
- The close-on-scroll listener now compares the owning 📊 button's CURRENT viewport rect against the rect the panel was positioned against at open time, instead of closing on any scroll event unconditionally. An unchanged rect means nothing actually moved (a stale, pre-open scroll event) and the panel stays open; a changed rect means the page really has scrolled since, the fixed-position panel is no longer anchored to its button, and it closes as before. As a side benefit this also stops an unrelated inner scroll container — one that doesn't move the column header at all — from dismissing an open panel.


## 9.99.975 — 2026-08-31

**🐛 Fix**

- Unique-values dropdown (📊) cache: also invalidate it when a CAA/EAA artwork cell finishes loading. `_artBuildMultiRowArtCell()` rebuilds a cell's image `<li>`s, its per-image type/comment badges and its `ul.dataset.mbArtSearch` search text asynchronously, long after the initial render and with no row show/hide — invisible to the cache's visible-row-set signature. The dropdown reads all three: `valueCounts` picks up the search text via `getCleanColumnText()`, and `artTypeValueCounts`/`artCommentValueCounts` read the badges. Without this, a dropdown opened for a CAA/EAA column before its artwork resolved kept serving pre-enrichment counts on every reopen. Invalidation added to both the REBUILD and FIRST-BUILD branches, so it covers single-table and multi-table pages alike (unlike the neighbouring `_artSyncSearchTextToSourceRow()`, which is multi-table-only by design). Same class as the 9.99.974 sites; this one surfaced after rebasing onto main's v9.99.971/v9.99.972 CAA/EAA multi-table filter fix, which introduced the search-text sync and its own `_rowTextCache` invalidation alongside it.


## 9.99.974 — 2026-08-31

**🐛 Fix**

- Unique-values dropdown (📊) cache: invalidate it for columns whose cells are populated asynchronously, after the initial render. The 9.99.973 cache keys off which rows are currently visible, which cannot see a column that fills previously-empty cells in place with no row show/hide — so a dropdown opened while such a column was still loading would cache a near-empty bundle that nothing ever refreshed (until an unrelated filter or sort happened to change the visible-row signature). New table-wide `_invalidateUniqDropDataCacheForTable(table)` is now called from `initReleaseEventsColumn()` (both post-population re-scan sites), `initRelationshipsColumn()`'s completion handler, and `initPicardTaggerColumn()`; `_artSetInlineSortKey()` additionally invalidates just its own column, since it stamps the `.mb-inline-art-sort-key` sentinel that the dropdown's inline-artwork scan reads, from \~8 CAA/EAA fetch-completion callbacks. Affects the Release events / Release country / Release date, Relationships, Picard tagger and inline CAA/EAA columns.


## 9.99.973 — 2026-08-31

**🔧 Refactor**

- PERFORMANCE.org Step 4 (`openUniqDrop()` per-open caching): the unique-values dropdown's 5 full `tbody.rows` scan passes (whole-cell value counts, flag-icon segment map, relationship-cell detection, relationship icon counts, inline CAA/EAA-thumbnail counts) are now cached per (table, column) in a `WeakMap`, keyed by a cheap O(rows) signature of the currently visible rows' `data-mb-row-idx` values. Reopening the same column's dropdown with no filter/sort change in between skips straight past all 5 passes. Measured on `artist-events` (4174 rows, 21 columns, median of 5, script 9.99.970 both sides, captured back-to-back on one machine): warm dropdown open 31 347 ms → 581 ms (\*\*54x faster\*\*), with global filter (1242→1292 ms), column filter (1201→1239 ms) and sort (2995→2906 ms) all unchanged within noise. Cold (first) open is unchanged within noise too — 30 649 → 32 985 ms, against an observed \~20% run-to-run spread for that same 30-second 5-pass scan; a cache miss adds only one O(rows) signature build plus one `Map.set`. Each Map/counter declaration became a `_uniqCacheHit ? … : <original>` ternary in place and each scan loop got a `!_uniqCacheHit` guard, so none of the hundreds of `.set()`/`.get()`/`++` call sites inside the loop bodies changed. Keying by the live `<table>` element means a brand-new table (new fetch, disk-load, multi-table sub-table) is always a cache miss, with no manual reset needed.
- Landed WITHOUT PERFORMANCE.org Step 3, which it was originally written alongside: `_updateAllColHeaderCounts()` — the function Step 3 caches — is never reached from `openUniqDrop()`, so it contributes nothing to the win above. The one thing Step 4 genuinely needed from Step 3, the shared `_visibleRowSetSignature(table)` helper, is carried here standalone; a later Step 3 can key off the same primitive unchanged.
- Found and fixed one correctness gap while implementing: the "Cell structure" section's collapsed/expanded split is read from `expandedCells` (individually-toggled cells), not derivable from the visible-row signature, so a lone cell expand/collapse click would otherwise leave a reopened dropdown showing a stale split. Added `_invalidateUniqDropDataCache(table, colIndex)` and wired it into all 5 places `expandedCells` is mutated by user interaction (`_applyCollapseState()`'s two branches, `ensureCollapseDelegate()`'s three inline toggle branches).
- Found and fixed a second gap that the earlier `perf-steps-1-4` / `perf-steps-3-4` versions of this change still carry: 10 further symbols populated inside the (now skipped) first scan pass were neither defaulted from the cache nor stored into it — `editorDeletedValueCounts`, `editorAnyDeletedCount`, `editorRecordedNameValueCounts`, `editorMembershipValueCounts`, `editorCommentValueCounts`, `changelogHasMessageCount`, `changelogNoMessageCount`, `releaseQualityHighCount`, `releaseQualityLowCount`, `releaseQualityNormalCount`. Left as-is they read 0/empty on every warm reopen, silently dropping the "🗑️ any deleted editor", "📜 has changelog message", "🚫 no changelog specified" and "🟢/🟠/⚪ data quality" entries plus every Editor-info value entry — and, since those same counters gate their sections' visibility conditions, potentially collapsing a whole section to empty. Affects the `annotations` pageType (Editor / Version history columns) and every page carrying a "Release" column. Same failure mode as the previously-recorded `roleTokenValueCounts` miss.
