## 9.99.674 — 2026-06-18

**🐛 Fix**

- Fixed sticky column header cell remaining see-through when sort value-change shading is active (follow-up to v9.99.673 which fixed the body rows). The `mb-mscol-hdr-*` header tint classes also use `rgba() !important` (at alpha 0.60), which overrides the inline `background` shorthand set by `applyStickyColumn`'s header loop, making the sticky column header see-through on horizontal scroll. Fix: added module-level `_MSCOL_HDR_TINT_RGBA` lookup (alpha 0.60 for each of the 8 hues). In `applyStickyColumn`'s header-row loop, store `dataset.mbStickyBg = headerBg` and apply the same detect-remove-read-restore pattern as the body-row fix: if a hdr-tint class is already active, temporarily remove it, set the true header background, restore the class, compute an opaque blended colour via `_blendSortTint`, apply it with `setProperty('background-color', …, 'important')`, and record `dataset.mbStickyRestBg`. In `applyMultiSortColumnTints`, after adding `hdrCls` to the main header `<th>`, if the cell is `mb-sticky-col`, blend the header tint onto `mbStickyBg` and apply the opaque result the same way. `clearMultiSortColumnTints` already queries `thead tr:first-child th` and restores from `mbStickyRestBg`, so no change there.


## 9.99.673 — 2026-06-18

**🐛 Fix**

- Fixed sticky column remaining see-through after sort tints are applied (complete rewrite of v9.99.672 fix). Root cause: `renderFinalTable` calls `applyTints()` on freshly cloned rows before `runFilter()` calls `applyStickyColumn`. When `applyStickyColumn` then reads `getComputedStyle(cell).backgroundColor`, the sort-tint class's `rgba() !important` rule is already winning the cascade — the browser returns the semi-transparent tint colour as the computed background, which `applyStickyColumn` stores as `mbStickyBg`. When the sort handler later calls `applyMultiSortColumnTints()`, it blends the tint onto the already-tinted rgba value, producing a doubly-wrong result, and the sticky cell stays see-through. Additionally, the `mouseleave` handler set `cell.style.background = mbStickyBg` (non-important shorthand), which cleared the cascade-winning `!important` flag previously set by `applyMultiSortColumnTints`, allowing the tint class to win again and make the cell see-through on every hover-out. Fix: (1) Move the tint RGBA lookup table to module scope as `_MSCOL_TINT_RGBA` and add a shared `_blendSortTint(tint, restBg)` helper so both `applyStickyColumn` and `applyMultiSortColumnTints` use the same data. (2) In `applyStickyColumn`'s body-row loop, detect any active tint class, temporarily remove it and any inline `background-color !important`, read the true opaque zebra background via `getComputedStyle`, then restore the tint class; if a tint was present, apply the opaque blended colour via `setProperty` and record `mbStickyRestBg`. (3) In the `mouseleave` handler, when `mbStickyRestBg` is set (tint is active), re-apply the blended colour via `setProperty('background-color', …, 'important')` after setting the background shorthand so the opaque value wins over the tint class. (4) In `mouseenter`, same treatment for the hover colour on tinted sticky cells. (5) `applyMultiSortColumnTints` now uses the shared `_MSCOL_TINT_RGBA` / `_blendSortTint` instead of its former local copies.


## 9.99.672 — 2026-06-18

**🐛 Fix**

- Fixed sticky column becoming see-through when sort value-change shading is active. The `mb-mscol-*` tint classes use `background-color: rgba(…) !important`, which overrides the inline opaque `background` applied by `applyStickyColumn`. On a `position:sticky` cell, the browser composites that semi-transparent background against the scrolled content behind the cell (not against the DOM parent), making columns behind the sticky one visible through it. Fix: in `applyMultiSortColumnTints`, when adding a tint class to a `mb-sticky-col` cell, alpha-blend the tint's RGBA values (from a new precomputed `_tintRGBA` lookup table matching the CSS definitions) onto the cell's current opaque rest background, and apply the resulting opaque `rgb()` colour via `cell.style.setProperty('background-color', …, 'important')`. An inline `!important` declaration wins over class `!important` at the same specificity level, ensuring the sticky cell always paints opaquely. The original rest background is preserved in `dataset.mbStickyRestBg`; `dataset.mbStickyBg` is updated to the blended colour so the `mouseleave` handler continues to restore the correct tinted colour on hover-out. `clearMultiSortColumnTints` is extended to remove the inline important `background-color` and restore the original rest background for sticky cells when tints are cleared.


## 9.99.671 — 2026-06-18

**🐛 Fix**

- Fixed collapse-toggle extra-space over-estimation in `toggleAutoResizeColumns` PASS 2. The formula `extra = max(0, toggleWidth + 16 − thPaddingRight)` subtracted the `<th>` right padding as the baseline, but since v9.99.668 `columnWidths[colIndex]` is set to `th.offsetWidth` from the live-table nowrap pass — which already includes the actual `<td>` right padding (≈22px), not the `<th>` right padding (≈5px). Subtracting the smaller `thPaddingRight` over-estimated `extra` by roughly `tdPaddingRight − thPaddingRight ≈ 17px`, making columns with collapse-toggle widgets unnecessarily wider. Fix: read `getComputedStyle(cell).paddingRight` from the sampled `<td>` cell (already available in `_colToggleSample`) and use that as the baseline (`tdPaddingRight`) instead.

## 9.99.669 — 2026-06-17

**🐛 Fix**

- Fixed auto-resize not applying to initially-collapsed sub-tables in multi-table mode. The v9.99.668 live-table measurement reads `th.offsetWidth` directly from the live table, but a table with `style.display = 'none'` returns `offsetWidth = 0` for all cells — giving every column a 20px minimum instead of the true content width. The symptom: after the initial auto-resize, the resize button showed 'Restore' (resize appeared to succeed) but collapsed sub-tables had useless 20px column widths; expanding them produced mis-sized columns, and toggling Restore/Resize while they remained collapsed could not fix them. Fix: in the measurement loop, if `table.style.display === 'none'`, temporarily set it to `''` before adding `mb-measure-nowrap`, read `th.offsetWidth`, then restore `display: none` immediately after removing `mb-measure-nowrap`. Both mutations are synchronous with no `await` between them, so the browser never paints the intermediate visible state. This applies both to the initial `sa_auto_resize_columns` auto-trigger and to subsequent manual Resize button clicks.


## 9.99.668 — 2026-06-17

**🐛 Fix**

- Fixed persistent line break before the last word of disambiguation comments in auto-resize mode (Bug 1) — final root cause. The v9.99.667 NBSP-outside-anchor approach correctly eliminated the `overflow-wrap:anywhere` interaction, but the bug persisted because the column minimum-width computed by the old offscreen-div measurement was too narrow. The old PASS 1 applied `getComputedStyle(th).padding` to the measurement div so that `div.offsetWidth = th_pad_left + content + th_pad_right`; it then set `th.style.minWidth` to that value. In the live table, however, `<td>` padding is larger than `<th>` padding, so `td_available_content = th.minWidth - td_pad_left - td_pad_right` was narrower than the measured content width, leaving insufficient room and forcing a wrap. Fix: replace the offscreen-div PASS 1 entirely with a live-table measurement — add class `mb-measure-nowrap` (`white-space:nowrap !important; overflow-wrap:normal !important; word-break:normal !important`) to the table itself so the browser expands every column to its single-line natural width, then read `th.offsetWidth` (border-box, includes actual TD padding from the widest cell in each column). Because `th.offsetWidth` in nowrap mode equals the max border-box width across all cells in the column, the resulting `minWidth` is always sufficient to hold the widest cell without wrapping. All mutations are synchronous (no `await` between `classList.add` and `classList.remove`), so the browser never paints the intermediate full-width state. The unused `colStyleCache` variable (a relic of the offscreen approach) was removed.


## 9.99.667 — 2026-06-17

**🐛 Fix**

- Fixed persistent line break before the last word of disambiguation comments in auto-resize mode (Bug 1). Previous fix (v9.99.666) placed U+00A0 (NBSP) inside the anchor's `<bdi>` to prevent the soft-wrap between anchor text and comment. However, `<a class="wrap-anywhere">` carries `overflow-wrap:anywhere`, which Chrome can use to allow a break at any code-point boundary inside the element — including at a NBSP inside `<bdi>` at a bidi-run boundary. The root fix: move the NBSP outside `<a>` entirely. `normalizeCommentSpans` now REPLACES the whitespace text node between `</a>` and `<span class="comment">` with a single U+00A0 text node (or INSERTS one if none exists, covering Variant A). Because this NBSP is a sibling of `<a>` in the `<td>` — not inside any `overflow-wrap:anywhere` element — only the standard Unicode GL rule applies: no break before or after U+00A0. The GL SP-exception ("no break before GL unless preceded by SP") is neutralised by the companion trimEnd on the anchor `<bdi>`, which removes any trailing U+0020 SPACE so the character directly before the NBSP is always a letter or punctuation. Together these two operations guarantee that anchor text and comment remain on the same line at the auto-resize minimum width.


## 9.99.666 — 2026-06-17

**🐛 Fix**

- Fixed column resize minimum creeping upward after each drag (Bug 2). The drag-minimum width (`_minWidth`) was previously recomputed on every `mousedown` from `_hdrFlex.scrollWidth + 8`. After the user dragged a column wider, `_hdrFlex` had stretched to fill the enlarged column, so `scrollWidth` returned the CURRENT (wider) column width instead of the original header-content minimum — making it impossible to drag the column narrower again. The fix moves the computation to `makeColumnsResizable` initialisation time (before any drag has occurred), when the column is still at its natural layout width and `scrollWidth` correctly reflects the intrinsic minimum of the header widget (colName + sort icons + unique-values button + optional extras). The value is cached in `th.dataset.mbResizeMin` so that subsequent `makeColumnsResizable` calls (e.g. the re-call inside `toggleAutoResizeColumns` after auto-resize has already modified column widths, and the re-call after the Restore button removes and re-adds handles) reuse the pre-resize minimum rather than recomputing from a stretched layout.
- Fixed line break before the last word of disambiguation comments in auto-resize mode (Bug 1) and residual anchor→comment line break (Bug 3). After v9.99.665 removed the whitespace text node between `</a>` and `<span class="comment">`, the visual gap between title and comment was still provided by the trailing `\n  ` whitespace at the end of the `<bdi>` element inside `<a class="wrap-anywhere">`. That trailing whitespace collapsed to a regular space, which — being inside the anchor's `<bdi>` boundary with `overflow-wrap:anywhere` active — was still a soft-wrap opportunity. The browser could break there, pushing the comment to a new line and potentially causing the comment text to wrap internally. The fix: `normalizeCommentSpans` now replaces any trailing whitespace in the last text node of such `<bdi>` elements with a single U+00A0 (NON-BREAKING SPACE). U+00A0 has Unicode line-break class GL (Glue) — it is prohibited as a break point even under `overflow-wrap:anywhere` — so the anchor text and immediately-following comment are guaranteed to remain on the same line at the auto-resize minimum width. The visual gap is preserved (U+00A0 renders with the same metrics as a regular space). Only `<a>` elements whose next element sibling is `<span class="comment">` are affected. The operation is idempotent because ECMAScript `trimEnd()` treats U+00A0 as whitespace and strips it, so a second pass re-applies exactly one U+00A0.


## 9.99.665 — 2026-06-17

**🐛 Fix**

- Fixed two remaining soft-wrap break points in `normalizeCommentSpans` that were exposed after the nowrap-style removal in v9.99.664. (1) Trailing whitespace inside `<bdi>` content: MusicBrainz emits a `\n      ` sequence before `</bdi>` (Variant B), which collapses to a single space in rendering and creates a wrap opportunity at the end of the bdi text — causing the last word of a disambiguation comment (e.g. `reissue)`) to break to a new line in narrower columns. The fix trims trailing whitespace from the last text node inside `<bdi>` after all other normalization steps. (2) Whitespace between `</a>` and `<span class="comment">`: MusicBrainz emits a `\n    ` text node as a sibling between the closing `</a>` and the opening `<span class="comment">` at the `<td>` level. That text node collapses to a space and, combined with `overflow-wrap:anywhere` on `.wrap-anywhere` anchors, created a break opportunity between the anchor text and the leading `(` of the comment — the "magic minimum column width" that prevented resize below the anchor-plus-first-word width. The fix removes that inter-element whitespace text node from every `<td>` as a second pass in `normalizeCommentSpans`. Both fixes are pure DOM mutations with no style mutations on live elements.


## 9.99.664 — 2026-06-17

**🐛 Fix**

- Removed all `white-space: nowrap` style mutations from `normalizeCommentSpans`. Previous versions (introduced progressively in v9.99.639–9.99.651) applied `white-space: nowrap` as inline styles to live DOM elements — `span.comment`, `<bdi>`, and the containing `<td>` or `<li>` — to prevent disambiguation text from breaking away from its anchor. This forced the min-content width of every affected cell to the full single-line text width of the longest comment, making columns such as Release and Label unexpectedly wide in `table-layout:auto` even without auto-resize, and also made it impossible to drag those columns narrower than their longest single-line content (text overflowed instead of wrapping). The function now performs only the interior DOM normalisation it originally set out to do: removing pure-whitespace text nodes around `<bdi>`, consolidating Variant-A `(` / `)` orphans into `<bdi>`, and moving any trailing text node after `</bdi>` into `<bdi>` to eliminate the bidi-boundary soft-wrap point. No style properties are mutated on any live element. The auto-resize measurement sandbox is unaffected (it uses `white-space:nowrap !important` via `.mb-measure-nowrap`). At the auto-resize minimum width the full content fits on one line so the browser inserts no unnecessary breaks; if the user drags a column narrower, the browser's natural line-breaking applies — which is the intended behaviour.

## 9.99.662 — 2026-06-16

**🐛 Fix**

- Fixed manual column resize breaking all column widths on mousedown. Switching to `table-layout:fixed` without first locking every `<col>` to its current rendered width caused the browser to redistribute all column widths equally, making all columns jump to the same size at the moment of click. The fix snapshots every `th.offsetWidth` before any style mutation, writes those values to all `<col>` elements, clears `th.style.minWidth` (set by auto-resize) so cell constraints cannot override the explicit col widths, and removes the fixed `table.style.width`/`table.style.minWidth` set by auto-resize so the table is free to grow when a column is widened. This eliminates both the sudden jump-on-click and the zero-sum behavior where widening one column compressed all others. The fix applies equally whether auto-resize is active or not.
- Replaced the hardcoded 30 px minimum drag width with a per-column header content minimum. At `mousedown`, `hdrFlex.scrollWidth + 8` is measured from the live `.mb-col-hdr-flex` element (colName + ⇅▲▼ sort icons + unique-values widget + optional collapse-toggle + optional CAA/EAA column-header button). The +8 accounts for the 8 px resizer handle. A column can no longer be dragged narrower than its own header requires. For columns without `.mb-col-hdr-flex` (e.g. the Picard tagger column, which is injected after the sort UI is built and carries only plain text), `th.scrollWidth` is used as the floor instead, ensuring the column name remains fully visible.

## 9.99.660 — 2026-06-16

**🐛 Fix**

- On `releasegroup-releases` pages, inline cover art thumbnails in the first (sticky) column were absent after loading data from disk. Root cause: the disk-load path unconditionally set `group.colName = category` (e.g. `"Official release"`) for every multi-table group, but the network fetch path only sets `colName` for `listToTable`/`groupByH3` page types. For standard multi-table pages (`releasegroup-releases` uses the generic `else` fetch branch), `group.colName` is left `undefined`. When `colName` was incorrectly set on disk-load, `renderGroupedTable` patched the first `<th>` of each sub-table from `"Release"` to `"Official release"`, causing `caaFindColumnByName('Release')` to return `-1` and `_artInitInlinePics` to skip all sub-tables. Fixed by guarding the `colName` derivation behind a check for `activeDefinition.features.listToTable || activeDefinition.features.groupByH3`, mirroring the network-path condition exactly.


## 9.99.659 — 2026-06-16

## 9.99.654 — 2026-06-01

**🐛 Fix**

- `applyRenderMultiRowCells` did not split the 'Relationship types' column on instrument-\* pages (instrument-releases, instrument-artists, instrument-recordings). Root cause: the splitting loop only recognised standalone comma text nodes (`/^\s*,\s*$/`) as separators — correct for element-separated columns like Catalog\# whose HTML has `<span>…</span>,<span>…</span>` — but MusicBrainz renders Relationship types as a single plain text node (`instrument (as "lead guitar"), instrument (as "rhythm guitar")`), so no standalone comma node exists. Fixed by replacing the simple `if`/`else` check with a depth-aware top-level-comma finder: for every text node the loop now finds all comma positions at parenthesis depth 0 and splits there, creating one synthetic text node per part. Commas inside parentheses (e.g. `vocal (as "soprano, alto")`) are left intact.
