## 9.99.1174 — 2026-09-30

**🐛 Fix**

- Multi-table pages: ticking a sub-table filter's Cc, Rx or Ex box (in the 🔍 panel) now re-runs that sub-table's column filters straight away. Those boxes also govern the column filters, but only the sub-table text used to be re-applied, so e.g. a column filter "^Tun" stayed literal after ticking Rx until the next keystroke. Applying a pinned/recent sub-table history entry, which restores the boxes, takes the same path.
- Multi-table pages: a sub-table's status line no longer contradicts itself. It used to label the global query with the sub-table's own Cc (`GLOBAL:(case) "e"` with the global Cc off), never showed the global Ex, and after any re-filter counted the rows before the sub-table filter hid any. Both code paths that write it now share one builder.
- Multi-table pages with cover art: the image rows of a CAA/EAA cell highlight a global query with the GLOBAL Cc/Rx again, not the sub-table's. A global regexp such as "Back\|Nothing" kept the right rows but was highlighted as literal text whenever the sub-table's Rx was off.
- A plain (non-Rx) global filter no longer matches across two cells. "Rest Bruce" (the end of the Release cell and the start of the Artist cell) matched every row, with nothing highlighted, while the same text with Rx on matched none. Plain text is now matched cell by cell, like a regexp; several words inside one cell, including a name and its disambiguation comment, still match.
- Filter status lines now show the modifiers that apply to each part and the global query as typed: e.g. `✓ Filtered 52 rows in 70ms [1 COLUMN FILTER ['Release':(ex) "live"]]` when the global Ex inverts a column filter on a single-table page, `'Release':(rx) "^Tun"` when a closed 🔍 panel's Rx governs a column on a multi-table page, and `GLOBAL:"BoDeans"` instead of `GLOBAL:"bodeans"`. Before, column filters were listed without modifiers, so an inverted or regexp column filter looked exactly like a plain one.
- Filter status lines name a column by its real name again: a column whose header carries a control glyph was printed with it, e.g. `'▌█Barcode'` instead of `'Barcode'`.

## 9.99.1155 — 2026-09-26

## 9.99.1146 — 2026-09-24

**🚀 Feature**

- A release tracklist now has columns for the relationships of the WORK each track records — publisher, lyricist, composer, arranger, sub-publisher, "is based on", and whatever else a given release uses. MusicBrainz nests those inside the track's "recording of:" relationship, one level below everything that was being extracted, so until now they appeared nowhere but the raw "ARs" column. They are auto-discovered, so a relationship type this script has never heard of gets a column without an update.
- Work columns are named with a "Work " prefix — "Work lyricist", "Work publisher label" — so a relationship the recording itself also has (an "arranger:" on both) stays a separate column instead of the two being mixed into one.
- A relationship naming several roles at once ("lyricist and composer:") becomes one column per role, so it lines up with tracks that credit the roles separately. On Born to Run that turns three part-filled columns into a full "Work lyricist" and "Work composer".
- A work relationship crediting more than one kind of entity across the release splits into one column per kind, the way "Phonographic copyright (℗) by artist"/"…by label" already does — Born to Run credits both an artist publisher and label publishers under the one "publisher:" phrase.
- Cells with several credits render as multi-row lists with the usual ▶/▼ per-cell toggle: Thunder Road's three separate "is based on:" relationships are three rows, not just the first one.
- Each column's header carries the entity icon MusicBrainz shows beside the names in that relationship — artist, label or work — and the shared "extracted column" header tint.
- The columns sit between "Recorded in area" and "Performer", so a track reads left to right as the recording, then the work it records, then who played on it, then the full raw "ARs".
- New setting "Add columns for the recorded WORK's own relationships" (on by default) under RELEASE TRACKS. Independent of the other relationship-column settings, and of whether "Recording of work" itself is shown. "ARs" is left completely unchanged either way — every extracted link still appears there too.

**📝 Docs**

- ❓ Help's release-tracklist section now describes the "Work …" columns, and its "auto-discovered column" example no longer uses "Publisher" — on a release that is the work's relationship, and it now has its own "Work publisher" column rather than an unprefixed one.
- The "Enable collapsible ARs column" setting no longer calls everything in that column a recording-level relationship: it holds both the recording's own relationships and the recorded work's.

## 9.99.1144 — 2026-09-24

- Typing into a filter no longer re-counts the whole table for the ⏳ pending-edits and LENGTH ⚠️/❌ summary buttons on every keystroke. ## 9.99.1143 — 2026-09-23

**🐛 Fix**

- The ⏳ pending-edits filter no longer erases the thing it filtered on. Pressing it — or checking "⏳ has pending edits" / a "» pending edit:" entry in the 📊 dropdown — used to paint each matching entity with the ordinary column-filter background, which covered MusicBrainz's own orange "modification pending" marker completely. ## 9.99.1037 — 2026-09-06

**✨ Improve**

- Artwork that does not exist is no longer re-requested on every sort. A sort of a page with cover-art now issues ZERO requests to the archive: images that exist come from the session memory cache, absences are remembered, and the JSON metadata is already in `ctx.countCache`. Previously each re-render fired one doomed request per art-less entity — 20 of them per sort on the pilot page — each with a ⌛ the user watched until it failed.
- Root cause: every tier of `_artFetchCachedImage()` recorded successes ONLY. - New per-session negative cache (`_artMissCache`), the Tier-1 sibling of `_artIdbMemCache`, consulted immediately after it. Only a DEFINITIVE absence is recorded (HTTP 404/410, per `_ART_MISS_STATUSES`): a 5xx, network error or timeout is deliberately left uncached, because the Cover Art Archive fails in bursts and treating a bad minute as "this artwork does not exist" would hide real images for the rest of the session. This is the same distinction `_msFetchWs2RecordingLengths()` already draws between a successful-but-empty answer and a transport failure. `_artGmFetchBlob()` now carries the HTTP status on its rejection so the two can be told apart at all.

The URL-level miss cache catches an entity that HAS images but no front cover — its count is non-zero, so the metadata check would pass it through. The metadata check catches an art-less entity whose image URL answers 5xx rather than 404, which the miss cache must never record. Verified by mutation: with only the metadata check, one hourglass survives; with only the miss cache, the 5xx case rebuilds its wrapper on every render.

## 9.99.977 — 2026-09-01

**🐛 Fix**

- Column headers on large single-table pages no longer report counts taken from a fraction of the table. On a page like an artist's Events tab (4177 rows), clearing a column filter left the 📊 unique-value badge stuck at a bare multiple of 500 — 1000, 1500, 2000, 2500 depending on the machine — instead of the real 4161, and the ▶N▤ multi-row badge equally wrong (1 instead of 5 for 'Location'). A Load-from-disk hydration showed the wrong number immediately, without any filtering at all. The row-count stat next to the heading was always right, which is what made the mismatch so visible.
- Root cause: `runFilter()` is synchronous and so could not await its own `renderFinalTable()` call. Above the chunked-render threshold (`sa_chunked_render_threshold`, default 1000 rows) that render appends rows 500 at a time, yielding to the browser between chunks — so when `runFilter()` continued, only the FIRST 500 rows were in the table. Its entire post-render pass then ran against that fragment, and the deferred header-count scan it schedules measured whatever multiple of 500 had arrived by the time it fired. Nothing recomputed the counts once the remaining chunks landed.
- The badges were only the visible tip. The same 500-row window starved every other post-render pass on those pages, so after a filter-clear or a sort the rows past the first chunk kept no per-cell ▶ collapse toggles, no release-group ▶ expand buttons, no CD-TOC tracklist toggles, no re-enabled annotation compare radios, no re-wired Picard tagger cells, no nested-heading toggles, no CAA/EAA artwork enrichment, and no zebra striping, sticky-column or barcode-highlight repaint. All of that now runs against the finished table.
- The sticky first column is the clearest example, and was the most visible of these in daily use: re-capturing the committed artist-events sort baseline shows the sticky-column marker going from 502 cells to 4176 — so on a 4174-row table, scrolling past roughly row 500 after a sort or a filter-clear left no sticky column at all.
- `renderFinalTable()` gained an optional completion hook, invoked once every row is actually in the table, and `runFilter()`'s single-table post-render work moved into it. Tables below the chunked-render threshold are unaffected down to the last detail: that path executes no `await` at all, so the hook still fires synchronously, in the same call stack, exactly where the code used to run. A render superseded by a newer one (fast typing) never fires its hook — the winning render fires its own.
- Load-from-disk had a second instance of the same race: its own \~200-line tail ran immediately after the synchronous `runFilter()` call, i.e. also against 500 rows. It now waits for the render to finish first, so the Release-events, Relationships, Picard, expand-RG, annotation-radio, CD-TOC, barcode and sticky-column passes it drives all see the whole table.
- The header-count scan is now scheduled through one entry point that holds it back until any in-flight render has settled and collapses repeat requests into a single pass — `initReleaseEventsColumn()` alone triggers it three times in a row. Two callers that never went through `runFilter()` (the Release-events column population and the column-visibility toggle) were exposed to the same partial-table race and are covered by this too.

**✨ Improve**

- The per-column header-count scan no longer runs as one unbroken task. Now that it covers the whole table rather than a 500-row prefix, a full pass over a page like artist-events is roughly 88,000 cell-text extractions (4174 rows × 21 columns); it is now sliced one column per event-loop turn and abandons itself as soon as a newer scan is queued, so the tab stays responsive while the counts fill in. A scan interrupted this way leaves the columns it already reached updated and the rest showing the previous numbers until the newer scan catches up.
