* Performance improvement plan

Tracking doc for filter/render/dropdown performance work on ShowAllEntityData.

Each implementation step below is its own top-level heading with a TODO/DONE
keyword. Flip TODO -> DONE (and add a short note: what changed, which commit
range / branch) as each step lands. Do not delete completed steps — the
history of what was tried and why is the point of this file.

*The keyword tracks* ~main~, *not effort.* A step reads DONE only when its code
is on ~main~. Several steps below were implemented and measured on a branch
that was never merged; those stay TODO and say so in their own text, so that
"what is true of the script people actually run" is readable straight off the
keywords. As of this revision the DONE set is exactly Steps 4, 18 and 19.

*One canonical numbering.* Three copies of this file drifted into three
incompatible schemes — ~main~, ~perf-steps-1-4~ and

** Context

~runFilter()~ currently clones every matching row with ~cloneNode(true)~ on
every keystroke, replaces the tbody, and re-runs the full post-render hook
chain (CAA/EAA artwork, ~initExpandRGsFeature~, ~initCollapsableColumns~,
CDtoc, Picard tagger, nested-~<h2>~ rewiring). The abandoned
~filter-performance-fix~ branch ("Fix C") replaced this with in-place
~display:none~/~display:''~ toggling on live DOM rows, so the hook chain
runs once at initial load instead of once per keystroke, plus
IntersectionObserver-based lazy CAA/EAA loading for large tables
("Pattern 5").

That branch diverged from ~main~ at commit ~0683c23~ and was never merged;
~main~ has since moved ~347 commits ahead (~23k lines changed in the
userscript alone). It cannot be merged cleanly (4 real conflicts, one
~740 lines) and the surrounding systems it touches (CAA/EAA pipeline,
collapsable-columns, disk-load restore) have all changed since. It has been
archived (not deleted) as ~archive/filter-performance-fix-v1-single-table~
for reference — the ideas need a fresh reimplementation against current
~main~, not a merge.

** Findings: is the underlying problem still real?

Yes — re-confirmed against ~main~ at *9.99.1045+2026-09-07*, which is also the
version every line reference in this section was read at:

- ~runFilter()~ (~:42225~) still clones every matching row and fully rebuilds
  the tbody on every keystroke, in both branches.
- The multi-table branch does the same per group, *except for a sort*, which
  since Step 18 touches only the sub-table it re-ordered: ~runFilter()~
  (~:42450~) pushes an empty ~_mbSkipRender~ group for every undisturbed
  index and ~renderGroupedTable()~ (~:49379~) leaves those ~<tbody>~ elements
  alone. Filters still re-render everything.
- No ~IntersectionObserver~ exists anywhere in the file — zero occurrences —
  so lazy CAA/EAA loading (Step 5) was never independently reimplemented.
- The "Show single-table" button (~openSubtableAsSingleTableTab()~) now lets
  any non-overflowing multi-table sub-table be viewed as its own single-table
  snapshot tab, which makes a single-table-only fix cover *more* ground than
  when the old branch was written. Performance work should keep targeting
  single-table mode first, same as the old branch already did (its own WIP
  changelog scoped Fix C to single-table mode only).

*** The dominant, previously-underweighted cost: ~_updateAllColHeaderCounts~

The file's own comments (~:56886-56888~, ~:57587~) document that this
O(rows x columns) per-column unique-value + multi-row-count scan can take
"30–120 s synchronously" for 8 k+ rows — enough to trigger Chrome's "Page
Unresponsive" dialog, which is why it's already deferred rather than fixed at
the root. ~:56694~ puts the same cost concretely for the harness page:
~artist-events~ at 4174 rows × 21 columns is *~88 000 ~getCleanColumnText()~
calls* per full pass.

It runs at the tail of ~initCollapsableColumns()~ (~:56878~), reached from
~_scheduleColHeaderCounts()~ (~:56650~), which today fires from:

| Call site | Function | Frequency |
|-----------+----------+-----------|
| ~:42747~ | ~runFilter()~, single-table branch | *every keystroke and every sort* |
| ~:49738~ | ~renderGroupedTable()~, reuse branch, per sub-table | every multi-table render — *except undisturbed groups on a sort, since Step 18* |
| ~:50271~ | ~renderGroupedTable()~, new-table branch, per sub-table | every multi-table render |
| ~:19699~ | ~syncCollapseButtonsWithColumnVisibility()~ | every column show/hide, page-wide |
| ~:61362~, ~:61377~ | ~initReleaseEventsColumn()~ | up to 3x in a row post-fetch (what the coalescing token exists for) |
| ~:46421~ | ~startFetchingProcess()~ | once per fetch |
| ~:73505~ | ~initPicardTaggerColumn()~ | post-render |

Scaled to 5,000 rows that is roughly 19-75 s of background work re-triggered
on most of those actions — larger than the cloneNode/DOM-rebuild cost the old
branch was framed around. Step 3 is the remedy and is still TODO; Step 18
removed one slice of it (see that step, and Step 3's own note).

** Implementation steps

*** TODO Step 1: Filter re-render (Fix C) — single-table mode only

In-place ~display:none~/~display:''~ toggling on live DOM rows instead of
~cloneNode(true)~ + tbody rebuild on every keystroke. Hoist
~initCollapsableColumns()~ (and the CAA/EAA/ERG/CDtoc/nested-~<h2>~ hook
chain it drives) to run once at initial render instead of once per filter
pass. Reference: ~archive/filter-performance-fix-v1-single-table~'s WIP.1
entry — reuse the approach, not the diff (too much of the surrounding code
has changed to apply it directly). Branch: ~filter-performance-fix~.

Scope: single-table mode only (~runFilter()~'s non-multi branch). Multi-table
mode is out of scope for this step — see the "Show single-table" button
note above for why single-table-first still covers the important case.

*** TODO Step 2: Extend the Fix-C approach to Sort

Sort currently still calls ~renderFinalTable(allRows)~ after
~sortLargeArray()~ completes, which triggers the same full tbody rebuild +
~initCollapsableColumns()~ re-run as the old filter path. Not covered by the
old branch (its WIP.1 only touched ~runFilter()~). Apply the same
"rows are live DOM nodes, reorder in place, don't re-run the hook chain
unless something actually changed" treatment to the sort-apply path.

*** TODO Step 3: Cache ~_updateAllColHeaderCounts~

Memoize per-column unique-value/multi-row counts, invalidated only when the
visible row set actually changes (not on every trigger). Needed even after
Steps 1-2, since global expand/collapse-all clicks and multi-table renders
still call it unconditionally.

*Still entirely unlanded as of 9.99.1045.* ~_updateAllColHeaderCounts()~
(~:56710~) has exactly two mitigations and neither is a cache: a coalescing
token (~_colHeaderCountsToken~, ~:56606~) so back-to-back schedules cost one
scan instead of three, and one ~await _yieldToEventLoop()~ per column so the
pass is never a single unbroken task. It still performs two full ~tbody.rows~
walks per column on every filter apply and every filter clear.
~_visibleRowSetSignature(table)~ (~:56589~) — the intended cache key — exists
and is used, but only by Step 4's ~_uniqDropDataCache~.

**** Partially mitigated by Step 18 — multi-table sorts only

Step 18 (scoped sub-table sort) skips the whole per-group decorate pass,
~initCollapsableColumns()~ → ~_scheduleColHeaderCounts()~ included, for every
sub-table a sort did not disturb. That is a real reduction in this step's
cost, and it is *correct* rather than merely cheaper: a sort changes a group's
row ORDER, never its row SET, so the counts it would recompute are the ones
already displayed. Filters, which DO change row sets, never take the scoped
path.

Two limits on how much of Step 3 that covers, both important:

- *Multi-table pages only, and only on a sort.* Single-table mode has no
  equivalent narrowing by design (~allRows~ is one array under one cache
  key), and no filter keystroke on any page takes the scoped path.
- *Therefore invisible in the numbers below.* They were captured on
  ~artist-events~, which is ~tableMode: 'single'~. Step 18 cannot move them,
  and did not.

A user-visible side effect worth recording: the 📊 unique-value count badges
now SURVIVE a sort of an unrelated sub-section instead of blanking back to a
placeholder and being re-scheduled. Measured on a saved payload, 19 of 22
badges populated afterwards against 0 of 22 before.

**** Re-costed after the chunked-render fix (branch ~fix-chunked-render-header-counts~)

The estimates above were made while this function was accidentally cheap on
the interactive path. ~runFilter()~ did not ~await~ its own
~renderFinalTable()~, so on a large single table the deferred scan ran against
whatever prefix of the tbody had been appended — a multiple of
~renderRowsChunked()~'s 500-row ~chunkSize~ — and produced visibly wrong
badges (~artist-events~: "Event" showing 984-2500 instead of 4158, "Location"
~.mb-col-collapse-count~ showing 1 instead of 5). That is now fixed: the scan
runs after the render completes, so it genuinely covers all 4174 rows × 21
columns (~88 000 ~getCleanColumnText()~ calls) on every filter apply and every
filter clear, not ~25% of that.

Two mitigations landed with the fix, both of which Step 3 can build on:
- ~_scheduleColHeaderCounts(table)~ — the single entry point. Waits out any
  in-flight render (so a scan can never see a partial tbody again) and
  coalesces repeat schedules via ~_colHeaderCountsToken~;
  ~initReleaseEventsColumn()~ alone fires ~initCollapsableColumns()~ three
  times in a row and now costs one scan instead of three.
- ~_updateAllColHeaderCounts()~ is ~async~ and yields one turn per column,
  aborting at the next column boundary once its token is stale — so the full
  scan is never one unbroken multi-second task.

Read these as a *correctness cost, not a regression in the work being done*:
the scan they are paying for used to cover a 500-row prefix and produce wrong

needs two stable reads, so it is sensitive to main-thread pressure. The
status text and the visible row set still update at exactly the same point in
~runFilter()~ as before (that path stayed synchronous and untouched); what
grew is the background work running after it, which delays the poll. So the
deltas above overstate the change in perceived filter latency, but they do
represent real extra main-thread work.

  is (cell content can change with no row show/hide). Step 6 must land with or

*** DONE Step 4: ~openUniqDrop()~ per-open caching

~openUniqDrop()~ does exactly 5 full ~tbody.rows~ passes from scratch on
every dropdown open with zero caching (the whole-cell value scan, the
flag-icon segment map, the relationship-cell detector, the relationship
icon counts, and the inline-CAA/EAA-thumbnail scan).

Originally written as "same caching primitive as Step 3 — build alongside
it", and that is how it first landed (branch ~filter-performance-fix~, later
~perf-steps-1-4~; also cherry-picked as the pair ~perf-steps-3-4~). It does
NOT actually need Step 3, though — see below.

*Landed*: branch ~worktree-perf-step-4~, standalone, WITHOUT Step 3. See
~ShowAllEntityData_CHANGELOG.json~ v9.99.973 (the port), v9.99.974 (the
async-column cache invalidations) and v9.99.975 (the CAA/EAA-cell one added
while rebasing onto ~main~).

- *Why Step 4 alone.* The earlier 2026-08-24 session had already shown this
  on ~perf-steps-3-4~ (= ~main~ + Steps 3 and 4 only): warm uniq-dropdown
  open 29 700 ms -> 739 ms, filter/sort unchanged within noise, and
  ~post-filter.html~/~post-sort.html~ byte-for-byte identical to ~main~'s
  baselines. That entire win is Step 4's:
  ~_updateAllColHeaderCounts()~ — the function Step 3 caches — has only two
  call sites, both ~setTimeout(…, 0)~ at the tail of the collapse-column
  init path, and neither is reachable from ~openUniqDrop()~. Steps 1-2, by
  contrast, measured as a real tradeoff (+53-68% on narrow filters, +23% on
  sort), so this branch deliberately carries neither.
- *The one thing Step 4 needed from Step 3* is the helper
  ~_visibleRowSetSignature(table)~ — a cheap O(rows) join of the visible
  rows' ~data-mb-row-idx~ values, which is the cache key. It is carried here
  standalone (9-line function); Step 3, if it lands later, keys off the same
  primitive with no change.
- *Implementation shape*, deliberately minimal: a per-(table, column)
  ~WeakMap~ (~_uniqDropDataCache~) whose entries are tagged with the
  signature they were computed against. All 5 passes are gated behind a
  single ~_uniqCacheHit~ check computed once at the top of the function.
  Each Map/counter *declaration* became a
  ~_uniqCacheHit ? _uniqCacheHit.name : <original initial value>~ ternary in
  place and each scan loop got an ~if (!_uniqCacheHit)~ guard — zero changes
  to the hundreds of ~.set()~/~.get()~/~++~ call sites inside the loop
  bodies. Keying by the live ~<table>~ element means a brand-new table (new
  fetch, disk-load, multi-table sub-table) is always a cache miss with no
  manual reset needed.
- *Correctness hazard 1 — ~expandedCells~.* The "Cell structure" section's
  collapsed/expanded split is read from ~expandedCells~ (a Map of
  individually toggled cells), NOT re-derived from the visible-row
  signature — so one cell's expand/collapse click changes those counts
  WITHOUT changing which rows are visible. Fixed with
  ~_invalidateUniqDropDataCache(table, colIndex)~ at all 5 places
  ~expandedCells~ is mutated by user interaction (both branches of
  ~_applyCollapseState()~, all 3 branches of ~ensureCollapseDelegate()~'s
  inline per-cell click handling). A 6th mutation site
  (~initCollapsableColumns()~'s one-time "start expanded by default"
  pre-population) needs none — it runs before any dropdown cache for that
  table could exist.
- *Correctness hazard 2 — async-populated columns* (this is
  PERFORMANCE.org's own Step 8 for the uniq-drop cache, folded in here
  rather than left as a known-shipped bug). Several columns fill
  previously-empty cells long after the initial render with no row
  show/hide at all, which the signature cannot see. Added a table-wide
  ~_invalidateUniqDropDataCacheForTable(table)~ and called it from
  ~initReleaseEventsColumn()~ (both post-population re-scan sites),
  ~initRelationshipsColumn()~ (completion handler) and
  ~initPicardTaggerColumn()~; plus a per-cell
  ~_invalidateUniqDropDataCache()~ in ~_artSetInlineSortKey()~, which stamps
  the ~.mb-inline-art-sort-key~ sentinel the inline-art pass reads from ~8
  CAA/EAA fetch-completion callbacks.

  Added after rebasing onto ~main~'s v9.99.971/v9.99.972 (the CAA/EAA
  multi-table type/comment filter fix): a sixth site,
  ~_artBuildMultiRowArtCell()~ — both its REBUILD and FIRST-BUILD branches.
  It rebuilds a cell's image ~<li>~s, per-image type/comment badges and
  ~ul.dataset.mbArtSearch~ asynchronously with no row show/hide, and the
  dropdown reads all three (~valueCounts~ via ~getCleanColumnText()~,
  ~artTypeValueCounts~/~artCommentValueCounts~ via the badges). That commit
  independently added a ~_rowTextCache~ invalidation at the same spot —
  confirmation that this call site needs one; it just didn't know about
  ~_uniqDropDataCache~. This is the CAA/EAA-column counterpart of the
  inline-art column's ~_artSetInlineSortKey()~ case, and unlike the adjacent
  ~_artSyncSearchTextToSourceRow()~ (multi-table only by design) it covers
  single-table pages too.
- *Port-specific fix — 10 symbols the earlier branches missed.* The Step 4
  code as it stands on ~perf-steps-1-4~ gates and stores 53 names but leaves
  10 more that are ALSO populated inside the (now skipped) pass-1 loop
  ungated and unstored: ~editorDeletedValueCounts~, ~editorAnyDeletedCount~,
  ~editorRecordedNameValueCounts~, ~editorMembershipValueCounts~,
  ~editorCommentValueCounts~, ~changelogHasMessageCount~,
  ~changelogNoMessageCount~, ~releaseQualityHighCount~,
  ~releaseQualityLowCount~, ~releaseQualityNormalCount~. On a warm reopen
  they all read 0/empty, so the dropdown silently loses "🗑️ any deleted
  editor", "📜 has changelog message", "🚫 no changelog specified",
  "🟢/🟠/⚪ data quality" and every ~editordeleted~/~editorrecordedname~/
  ~editormembership~/~editorcomment~ value entry — and because those same
  counters gate the section-visibility conditions, a whole section can
  collapse to empty. Identical failure mode to the ~roleTokenValueCounts~
  miss recorded on the earlier branches. Fixed here; *still open on
  ~perf-steps-1-4~* — see "Follow-ups" below.
- *Not included*: making ~_visibleRowSetSignature~ order-independent. It
  concatenates in DOM order, so a sort produces a different string and
  forces a recompute. On ~main~ (no Step 1) a sort rebuilds the tbody
  anyway, so this is a missed extra win, not a regression versus ~main~.
  Doing it properly has to account for several cached values that are
  themselves first-seen-in-row-order (~entityNameGlyphMap~,
  ~entityNameTypeMap~, ~entityNameFlagMap~, ~valueItemSequence~), so it
  belongs in its own step — that is Step 6, harvested below. Note Step 6's
  own text (written on ~perf-steps-1-4~, where Steps 1, 3 and 4 are all
  landed) calls this "the highest-impact regression"; the sentence above is
  the accurate reading for ~main~, and Step 6 carries a note saying so.

nowhere near the viewport, so a fast scroll never has a large batch of
never-yet-rasterized heavy rows to catch up on — a fix at the actual
mechanism (browser rendering), not a workaround in our JS (there is no
practical way to "lazy load" a ~data:~ URI's decode cost the way Step 5
lazy-loads a network request — the bytes are already inline in the DOM;
the only lever is whether the browser bothers to lay out/paint them yet).

**** Proposed approach

~content-visibility: auto~ + ~contain-intrinsic-size: auto <estimate>px~ on
every ~<tr>~ in ~table.tbl tbody~ (single-table mode first, matching every
prior step's scoping precedent). Semantics that matter for this codebase
specifically:

- While a ~<tr>~ is off-screen (outside an internal "near viewport" margin,
  conceptually similar to ~IntersectionObserver~), the browser skips layout,
  style recalc for layout purposes, paint, and hit-testing for its entire
  subtree — but does NOT remove or hide the DOM. ~textContent~, attributes,
  ~querySelectorAll~, ~cloneNode~, and non-geometric ~getComputedStyle~
  reads (colours, etc.) all keep working normally on a skipped row.
- What DOES break: any read of *layout geometry* on a skipped row or its
  descendants — ~getBoundingClientRect()~, ~offsetWidth~/~offsetHeight~,
  ~scrollWidth~/~scrollHeight~, ~clientWidth~/~clientHeight~ — reports
  placeholder/zero values while skipped, not the row's real laid-out size.
- ~contain-intrinsic-size~ is the row's OWN placeholder height (so total
  ~scrollHeight~/scrollbar-thumb size stay stable while rows skip in and
  out) — it does not, by itself, fix geometry reads on a skipped row's
  *descendants*, which is the actual audit concern below.

**** Audit checklist

Preliminary pass already done (grepped every ~getBoundingClientRect~/
~offsetWidth~/~offsetHeight~/~scrollWidth~/~scrollHeight~ call site — 83
total hits, most on dialogs/tooltips/dropdowns unrelated to table rows):

~main~'s cost scales *linearly* with match count (cloneNode+insert+rescan

roughly *constant* regardless of match rate (dominated by a fixed
forced-reflow cost across the full 4174-row table, whether 158 or 3380 rows
end up visible). Real interactive typing is progressive — early keystrokes
are wide, later ones narrow — so Steps 1-2 likely net out closer to a wash
in practice than the single-query headline table above suggests on its own.

*** Root cause of the narrow-filter regression (traced via temporary instrumentation)

~performance.now()~ marks added directly inside each branch's
~runFilter()~ single-table branch (profiled, then reverted — not committed;
see ~debug/NOTES.md~'s 2026-08-24 entry for the full trace and how to
reproduce), for the narrow ("United Kingdom", 158/4174) case:

| Sub-step                          |    ~main~ | ~perf-steps-1-4~ |
|------------------------------------+----------+------------------|
| Filter-test scan (all 4174 rows)   |   39.6 ms |          37.3 ms |
| Row mutation (clone vs. style-toggle) | 18.0 ms |       23.5 ms |
| DOM insert/replace                 |  121.4 ms |               — |
| *Forced reflow*                    |   34.8 ms |         219.3 ms |
| ~initCollapsableColumns()~ rescan  |    7.4 ms |             0 ms |
| ~_syncCollapseHasMatchInTable()~   |         — |          38.8 ms |
| *Total (self-reported)*            |  ~230 ms |          ~321-348 ms |

~main~ pays ~139ms more for cloning/inserting rows; ~perf-steps-1-4~ pays
~184ms more in forced-reflow cost alone, which dominates. Root cause:
~main~'s rebuild only ever lays out a table containing the MATCHES (158
rows); Step 1 keeps all 4174 rows permanently in the live DOM, so the next
forced reflow (here, ~window.scrollTo()~, called unconditionally at the end
of every ~runFilter()~ pass to restore scroll position) must lay out the
FULL row set, including the ~4016 now-hidden ones. Interestingly,
~initCollapsableColumns()~'s documented "30-120s for 8k+ rows" cost — the
ORIGINAL dominant-cost target behind Steps 1-4 — turns out to be cheap here
specifically BECAUSE ~main~'s rebuild already shrinks the table to just the
matches before that rescan runs; it may still dominate for a filter that
narrows only slightly (not verified).

**** Attempted mitigation: CSS containment — did not work

Tried both ~content-visibility: auto~ on every ~<tr>~ (see this file's own
"Known limitations" section below for why that's a considered, deferred
technique for a related cost) and ~table-layout: fixed~ with locked
~<col>~ widths (the exact technique this codebase's own manual-resize
handler already uses, with the comment "so subsequent width writes are
cheap" — see ~ShowAllEntityData.user.js~ around ~:25860~). Measured against
the same forced-reflow probe, isolated to the table (~table.offsetHeight~,
not ~document.body.offsetHeight~, to rule out unrelated page content):

| Technique                          | forced reflow (2 runs) |
|--------------------------------------+------------------------|
| Baseline (table-layout: auto)        | 200.0 ms / 199.8 ms   |
| ~content-visibility: auto~ on all ~<tr>~ | 250.8 ms / 198.7 ms (no improvement; sometimes worse) |
| ~table-layout: fixed~ + locked ~<col>~   | 211.5 ms / 177.7 ms (within noise, no real win) |

Neither technique meaningfully reduces the cost — it isn't the
auto-table-layout column-width algorithm that dominates, it's the sheer
per-row layout bookkeeping for the table's 4174 ~<tr>~ elements, which neither
technique eliminates. A real fix would need actual DOM virtualization
(rendering only the rows near the viewport), a materially bigger change
than either of these. Not implemented.

*** Sort-skip fix (landed, commit ~e6aa959~): internal vs. external gap

Sort always called ~runFilter()~ internally after reordering, even with no
filter active — pure no-op work once the DOM is already correctly
reordered. Gated behind a new ~_hasAnyActiveSingleTableFilter()~ check.

| Measurement                          | before fix | after fix | Δ            |
|----------------------------------------+-----------+-----------+---------------|
| Internal (self-reported) sort duration | 2842 ms   |    995 ms | -65%          |
| External (wall-clock) sort duration    | ~4388 ms  |   3669 ms | -16%          |

*Methodology lesson*: internal ~performance.now()~ deltas alone are NOT a
reliable proxy for perceived latency when a forced-reflow call is what's
being removed — the layout cost doesn't disappear, it's deferred to
whenever the browser (or a later DOM read, e.g. Playwright's own status-
text polling) next needs it. Always cross-check against external wall-clock
for this class of change. Even after this fix, sort remains ~23% slower
than ~main~ (see headline table above) — the fix mitigates the Step 1-2
regression, it does not close it.

*** Step 5 (lazy CAA/EAA): dramatic, unambiguous win

~artist-events~ normally seeds ~sa_enable_caa_pics: false~ for every other
measurement in this session (the EAA queue doesn't complete in reasonable
time at this row count) — but the pageType's own ~addEAA: 'Event'~ feature
makes CAA/EAA a real, relevant cost to measure once, with CAA force-enabled
and ~GM_xmlhttpRequest~ still stubbed (always a fast 404, so this isolates
queue/DOM-update overhead, not real network latency):

| Branch                         | Time to CAA/EAA queue completion |
|----------------------------------+-----------------------------------|
| ~main~ (no Step 5, eager loading) | *did not complete within 180s*   |
| ~perf-steps-1-4~ (Step 5, lazy)   | 42.2 s                           |

Matches PERFORMANCE.org's own ~99% estimate for this step. Unambiguous win,
no caveats found.

*** Cross-check: Steps 3-4 alone (branch ~perf-steps-3-4~, main + only these 2 commits)

Cherry-picked Steps 3-4 directly onto ~main~ (skipping 1-2-5) to isolate
their effect, confirming they have no dependency on Steps 1-2's DOM-mutation
approach — both only wrap ~_updateAllColHeaderCounts()~/~openUniqDrop()~,

*** Takeaways

- *Steps 3-4 (header-count + uniq-dropdown caching): ship these.* Clean,
  large win (~37-40x on uniq-dropdown warm-open), zero measured downside,
  verified independent of Steps 1-2. Live on ~perf-steps-3-4~.
- *Step 5 (lazy CAA/EAA): ship this too*, independently — dramatic,
  unambiguous win for any CAA/EAA-relevant page over the lazy-load
  threshold, no regression surface found.
- *Steps 1-2 (filter/sort in-place re-render): real tradeoff, not a clean
  win.* Loses on narrow/completed-query filters and (even after the
  sort-skip mitigation) on sort; wins substantially on wide filters. The
  original premise — that ~initCollapsableColumns()~'s "30-120s for 8k+
  rows" rescan is the dominant unaddressed cost — doesn't hold for a narrow
  filter on this page: that rescan turns out to already be cheap on ~main~,
  because its own rebuild shrinks the table to just the matches *before*
  the rescan runs. Worth keeping and iterating on (real, if partial, wins
  exist — sort-skip is proof), but should not be presented as a strict
  improvement over ~main~ without the caveats in this section.

** Findings from performance code-review (2026-08-25)

/Harvested from/ ~perf-steps-1-4~ (branch tip 2026-08-31). These findings were
raised against *that branch's* Steps 1-5, so the "regressions" listed are
regressions in unmerged code, not in ~main~. They became this file's Steps
6-14; read them as the rationale behind those steps. Two exceptions apply to
~main~ directly and are noted inline: the ~_visibleRowSetSignature~
order-dependence (Step 6, which affects ~main~'s shipped Step 4) and the
async-column invalidation gaps (Step 8, whose uniq-drop half landed on ~main~
with Step 4).

Local ~/code-review~ pass (forked agent, ~12 min / 55 tool calls — not the
cloud ultra review, no ultra credit spent), scoped to two questions:
correctness regressions in already-landed Steps 1-5, and further
performance opportunities not yet covered by them. Ranked most severe/
highest-impact first within each group; each item below becomes its own
Step 6+ heading in "Implementation steps".

*** Correctness regressions in Steps 1-5

1. ~_visibleRowSetSignature()~ (~:49412~) is documented as order-independent
   ("regardless of row order") but is actually an order-DEPENDENT string
   concat over ~tbody.rows~ in DOM iteration order. Sort (Step 2) reorders
   rows in place without hiding/showing any of them, so the row SET is
   unchanged but the signature STRING changes — every cache keyed on this
   signature (both Step 3's header-counts cache and Step 4's uniq-drop
   cache) spuriously misses after any sort, forcing the full O(rows x
   columns) recompute both steps were built to skip. This silently negates
   the "37-40x faster warm uniq-dropdown open" win documented above the
   moment a sort has happened first — far and away the highest-impact
   regression found, since it undoes two already-shipped, already-measured
   steps at once.
2. Step 5's lazy-load gate (~_useIO~, ~:63104~) computes
   ~allRows.length >= sa_caa_io_threshold~, but ~allRows~ is only populated
   in single-table mode — it stays empty for every ~tableMode: 'multi'~
   page (e.g. ~user-ratings~' "Release groups"/"Events" sub-tables, which
   declare ~addCAA~/~addEAA~). ~_useIO~ is therefore always ~false~ on
   multi-table CAA/EAA pages regardless of row count, so lazy loading never
   activates there — reproducing the exact "did not complete within 180s"
   eager-load queue-saturation failure Step 5 was built to fix, for every
   multi-table art page.
3. ~initReleaseEventsColumn()~'s post-population re-init (~:53971~) calls
   Step 3's ~_invalidateColHeaderCountsCache(t)~ but never Step 4's
   ~_invalidateUniqDropDataCache~ — a uniq-drop dropdown opened for
   Release events/Country/Date while that column is still populating can
   cache a near-empty bundle that then never refreshes (nothing invalidates
   it afterward) until an unrelated filter/sort happens to change the
   row-set signature.
4. ~initRelationshipsColumn()~/~initPicardTaggerColumn()~ (~:54689~) never
   re-trigger ~initCollapsableColumns()~/the recount pass at all — Step 3's
   own implementation notes already flagged this as a pre-existing gap for
   header counts; Step 4 adds a second, equally uninvalidated cache
   (~relIconCounts~ and friends) on top of it with no new invalidation path
   either.
5. ~_rowTextCache~ (~:30460~, filter-match text memoization) is never
   invalidated anywhere in the file. A filter run before an async column
   (Release events/Relationships/Picard) finishes populating permanently
   caches that row's pre-population (often empty) text; a later filter
   query that should match the now-arrived data silently won't, for the
   rest of that render's lifetime. Pre-existing, not introduced by this
   branch — but Step 1 (rows now persist live across far more filter passes
   than before) makes it bite more often.

*** New performance opportunities (candidate Step 6+, not yet in the plan above)

1. ~sortLargeArray~'s comparator (~createSortComparator~/
   ~createMultiColumnComparator~, ~:15508~) calls ~getCleanVisibleText()~
   (clone + ~TreeWalker~ text extraction) fresh on every pairwise
   comparison instead of once per row before sorting — for a 5,000-row
   merge sort (~n log n~ ~ 60,000+ comparisons), that's 100,000+ redundant
   DOM-text extractions instead of the 5,000 actually needed.
   ~createMultiColumnComparator~ additionally re-derives each column's
   ~isNumeric~ from the header text on every single comparison, even though
   it's invariant per column for the whole sort. Likely the single largest
   un-investigated contributor to the "Sort (unfiltered): 2994ms main /
   3669ms perf-steps-1-4" numbers above — the root-cause trace in this file
   only examined reflow/rebuild cost, never the comparator itself. Fix:
   precompute each row's sort-key text (and each column's ~isNumeric~) once
   before calling ~sortLargeArray~ (decorate-sort-undecorate).
2. ~applyExtractTrackTitleData()~'s ~_anyTitleCellMatches()~ helper
   (~:7748~) runs one independent full-table DOM scan per "does any track
   need column X" presence check (video/recArtist/disambig/streaming/
   recOf/recordedAtEvent/recordedAtPlace/recordedInArea/mixedAtPlace/
   recOfDate, ...) — ~10-15 sequential full re-walks of every row for what
   is logically one combined page-wide characterization pass, on every
   ~release-tracks~ fetch/re-render.

*** Flag-image rasterization cost on flag-heavy tables

Reported symptom, distinct from the Step 5 scroll-jank fix above: on tables
whose rows carry inline flag imagery from the "More Flags Everywhere"/
"Canadian Province Flags Everywhere" companion userscripts (custom/
subdivision-level flags, e.g. a venue's city rendered as its own icon — see
~debug/flags-rendering.html~), a fast scrollbar-drag shows the sticky column
(entity name) painting immediately while the rest of the row stays blank for
a noticeable moment. Confirmed NOT the same mechanism as the CAA/EAA fix
above (that's the "Location"/area column's flags, an entirely different
column and a different, third-party-injected DOM subtree — CAA/EAA's
~IntersectionObserver~ never touches it) and NOT a regression from this
branch: ~debug/flags-rendering.html~'s single sampled ~<td>~ is 305KB,
carrying two inline ~data:image/svg+xml;base64,…~ images (~84KB and ~221KB
of base64 text — up to ~230KB of raw SVG vector art combined) for one row's
venue location. A single-table render has always fully materialized every
row's DOM at once (true on unmodified ~main~ too, long before this work) —
what's new here is just that this particular kind of page makes that
already-large DOM dramatically larger per row.

Mechanism (browser compositing, not our JS): ~applyStickyColumn~ sets
~position: sticky~ on the sticky column's cells, which Chromium typically
promotes to its own compositor layer — a thin, text-only layer that paints
independently and cheaply. The rest of a flag-heavy row sits in the table's
main content layer alongside hundreds of KB of embedded vector art; that
layer's raster tile takes real, measurable time to decode/paint the first
time it scrolls into view. A fast scrollbar-drag jump exposes a large batch
of never-yet-rasterized rows in one step, so the (already fully built,
already in the DOM) main-layer content stays visually blank until the raster
catches up — while the sticky layer, having nothing expensive to paint,
shows immediately.

Not implemented — deliberately deferred rather than folded into Step 5,
since a real fix (the standards mechanism for "skip layout/paint of
off-screen content until it's about to be needed" is CSS
~content-visibility: auto~ + ~contain-intrinsic-size~ on ~<tr>~) is a
structural change with real risk: every place that reads a row/cell's
dimensions while it *could* be off-screen — auto-resize column-width
measurement, the sticky-column left-offset calculation, anything using
~getBoundingClientRect~/~offsetWidth~/~offsetHeight~ on a row not currently
in the viewport — would need auditing, since ~content-visibility: auto~
makes an element report placeholder (contain-intrinsic-size) dimensions
while off-screen rather than its real laid-out size. Candidate for its own
dedicated, independently-verifiable step if picked up later. Not pursued on
this branch — CAA/EAA request-throughput tuning (Steps 6-8 on the source
branches) is out of scope for this port; see this file's git history on
~filter-performance-fix-caa-throughput~ if that work is wanted later.
