* Performance improvement plan

Tracking doc for filter/render/dropdown performance work on ShowAllEntityData.

Each implementation step below is its own top-level heading with a TODO/DONE
keyword. Flip TODO -> DONE (and add a short note: what changed, which commit
range / branch) as each step lands. Do not delete completed steps — the
history of what was tried and why is the point of this file.

** Context

~runFilter()~ currently clones every matching row with ~cloneNode(true)~ on
every keystroke, replaces the tbody, and re-runs the full post-render hook
chain (CAA/EAA artwork, ~initExpandRGsFeature~, ~initCollapsableColumns~,
CDtoc, Picard tagger, nested-~<h2>~ rewiring). The abandoned
~filter-performance-fix~ branch ("Fix C") replaced this with in-place
~display:none~/~display:''~ toggling on live DOM rows, so the hook chain
runs once at initial load instead of once per keystroke, plus
IntersectionObserver-based lazy CAA/EAA loading for large tables
("Pattern 5").

That branch diverged from ~main~ at commit ~0683c23~ and was never merged;
~main~ has since moved ~347 commits ahead (~23k lines changed in the
userscript alone). It cannot be merged cleanly (4 real conflicts, one
~740 lines) and the surrounding systems it touches (CAA/EAA pipeline,
collapsable-columns, disk-load restore) have all changed since. It has been
archived (not deleted) as ~archive/filter-performance-fix-v1-single-table~
for reference — the ideas need a fresh reimplementation against current
~main~, not a merge.

** Findings: is the underlying problem still real?

Yes, confirmed directly against current ~main~ (~ShowAllEntityData.user.js~):

- ~runFilter()~'s single-table branch (~:36407-36434~) still clones every
  matching row and fully rebuilds the tbody on every keystroke.
- The multi-table branch (~:36240-36280~) does the same per group.
- No ~IntersectionObserver~ exists anywhere in the file — lazy CAA/EAA
  loading was never independently reimplemented.
- The "Show single-table" button (~:1070-1626~) now lets any non-overflowing
  multi-table sub-table be viewed as its own single-table snapshot tab, which
  makes a single-table-only fix cover *more* ground than when the old branch
  was written. Performance work should keep targeting single-table mode
  first, same as the old branch already did (its own WIP changelog scoped
  Fix C to single-table mode only).

*** The dominant, previously-underweighted cost: ~_updateAllColHeaderCounts~

The file's own comments (~:48541-48543~, ~:49212-49216~) document that this
O(rows x columns) per-column unique-value + multi-row-count scan can take
"30-120s synchronously" for 8k+ rows — enough to trigger Chrome's "Page
Unresponsive" dialog, which is why it's already deferred via
~setTimeout(0)~ rather than fixed at the root. It runs at the tail of
~initCollapsableColumns()~, which today fires on *every* single-table filter
keystroke (~:36480~), every sort (~:40029~, ~:54785~), every global
expand/collapse-all click (~:16555~, ~:52626~, ~:52637~), and every
multi-table render (~:42703~, ~:43249~). Scaled to 5,000 rows that's roughly
19-75s of background work re-triggered on every one of those actions —
larger than the cloneNode/DOM-rebuild cost the old branch was framed around.

** Ranked areas + estimated impact (5,000-row, ~20-column table)

Estimates are engineering estimates from operation-count analysis (Big-O
comparison, anchored to the one concrete empirical number in the codebase:
the documented 30-120s/8k-rows cost above), not measured browser profiles.
Real DevTools Performance-tab profiling before/after is the actual
acceptance check for each step.

| # | Area                                             | Est. improvement                                |
|---+---------------------------------------------------+--------------------------------------------------|
| 1 | Filter re-render (Fix C)                         | ~95-99% per-keystroke latency (wide tables)      |
| 2 | Same fix extended to Sort                        | ~90-99% per-sort-click latency                   |
| 3 | Cache ~_updateAllColHeaderCounts~                | ~90%+ on toggle / multi-table triggers           |

** Implementation steps

*** DONE Step 1: Filter re-render (Fix C) — single-table mode only

In-place ~display:none~/~display:''~ toggling on live DOM rows instead of
~cloneNode(true)~ + tbody rebuild on every keystroke. Hoist
~initCollapsableColumns()~ (and the CAA/EAA/ERG/CDtoc/nested-~<h2>~ hook
chain it drives) to run once at initial render instead of once per filter
pass. Reference: ~archive/filter-performance-fix-v1-single-table~'s WIP.1
entry — reuse the approach, not the diff (too much of the surrounding code
has changed to apply it directly). Branch: ~filter-performance-fix~.

Scope: single-table mode only (~runFilter()~'s non-multi branch). Multi-table
mode is out of scope for this step — see the "Show single-table" button
note above for why single-table-first still covers the important case.

*Landed*: branch ~filter-performance-fix~, see
~ShowAllEntityData_CHANGELOG.wip.json~ WIP.1. Findings while implementing,
beyond the archived branch's own approach:

- The live fetch pipeline (~startFetchingProcess~) already called the whole
  post-render hook chain (~initCollapsableColumns~, ERG, Picard, CAA/EAA)
  exactly once, independent of this fix — it had evolved that way across
  main's 347 commits since the archived branch diverged. Only the disk-load/
  hydration path still relied on ~runFilter()~'s old per-keystroke behaviour
  for the *first* post-hydration hook-chain run; that path now calls
  ~initCollapsableColumns()~ and the CAA/EAA init functions directly, moved
  to after ~updateH2Count()~ so ~initCollapsableColumns~'s global toggle
  button can find ~filterContainer~ already attached to the h2.
- ~applyZebraStriping~, the CSV/JSON/org/HTML export functions, and the
  sub-table-filter (STF) CAA/EAA bigbox sync were already
  ~display:none~-aware (skip hidden rows/cells) before this change — this
  significantly de-risked the show/hide approach; no changes needed there.
- New regression this approach would otherwise introduce, now fixed: cdtoc
  pages' tracklist sub-rows are a synthetic sibling ~<tr>~ inserted by
  ~_cdtocInitTracklistToggles()~, not part of ~allRows~. The filter show/hide
  pass now hides a row's tracklist sub-row alongside it, and the sort
  reorder pass now moves it along with its parent (both keyed on
  ~.mb-cdtoc-tracklist-row~) — otherwise a hidden/reordered row would leave
  its sub-row orphaned.
- ~_updateAllColHeaderCounts~ (the dominant cost per the Findings above) and
  ~openUniqDrop()~'s unique-values scan are NOT visibility-aware — after this
  step they reflect counts as of the last full hook-chain run (initial
  render or disk-load), not the currently-filtered row set, since they're no
  longer re-triggered per keystroke. This is the accepted, intended effect
  of hoisting described above; making them reflect the live filtered set
  again is Steps 3/4's job (caching with proper invalidation), not this
  step's.

     elements to match the new row order via ~box.appendChild~ — no rebuild,
     so none of ~_artInitBigPics~'s badge/generation-counter double-count
     risk. Called once per sort (not per filter keystroke, since filtering
     alone never changes row order) from the sort handler, right after it
     reorders the live tbody rows.

*** DONE Step 3: Cache ~_updateAllColHeaderCounts~

Memoize per-column unique-value/multi-row counts, invalidated only when the
visible row set actually changes (not on every trigger). Needed even after
Steps 1-2, since global expand/collapse-all clicks and multi-table renders
still call it unconditionally.

*Landed*: branch ~filter-performance-fix~, see
~ShowAllEntityData_CHANGELOG.wip.json~ WIP.3.

- Added ~_colHeaderCountsSigCache~, a ~WeakMap<table, signature>~. The
  signature is a cheap O(rows) join of the visible rows' ~data-mb-row-idx~
  values (an existing per-row identity, already stamped on every ~<tr>~ at
  extraction time and preserved through ~cloneNode(true)~ — see the
  ~_mbRowIdxCounter~ comment near ~:29997~). ~_updateAllColHeaderCounts~ now
  computes this signature first and returns early when it matches the last
  one computed for that table, skipping the O(rows x columns) scan.
  Keying by the live ~<table>~ element means a brand-new table (new fetch,
  disk-load, or multi-table sub-table) is always a cache miss — no manual
  reset needed.
- This correctly turns into a no-op skip for the call sites the "Findings"
  section above flagged as redundant:
  ~syncCollapseButtonsWithColumnVisibility~'s column show/hide re-init, and
  multi-table's per-sub-table re-render/reuse branches (row content there is
  always freshly cloned from the same source rows, so the signature is
  stable across a rebuild that reproduces the same filtered set). The global
  expand/collapse-all button was checked and does NOT call
  ~initCollapsableColumns~/this function at all (it drives
  ~_applyCollapseState~ directly), and ~getCleanColumnText~/
  ~_classifyCollapseCell~ were confirmed to read full DOM content
  independent of collapse/expand toggle state — so cached counts stay
  correct across expand/collapse-all clicks even though nothing re-triggers
  them.
- One real correctness hazard found and fixed while implementing: the
  signature only tracks WHICH rows are visible, not what their cells
  contain. ~initReleaseEventsColumn()~ mutates cell content in place (fills
  previously-empty Release events/country/date cells) with no row
  show/hide, then deliberately re-runs ~initCollapsableColumns()~ twice to
  pick up that new content (its own pre-existing comments: "it ran before
  cells were populated so found 0 ul>li items"). Naively caching purely on
  row visibility would have made those re-runs silently skip and leave the
  header counts frozen at their pre-population (mostly empty) values. Fixed
  by adding ~_invalidateColHeaderCountsCache(table)~ and calling it at both
  of that function's re-scan sites, right before ~initCollapsableColumns~.
  Any FUTURE call site that mutates cell content post-render without a row
  visibility change needs the same explicit invalidation — checked
  ~initRelationshipsColumn~ and ~initPicardTaggerColumn~ (both populate
  cells asynchronously) and confirmed neither one re-triggers
  ~initCollapsableColumns~/this function at all today, so their header
  counts were already not kept fresh before this change either — no new
  regression, but a pre-existing gap outside this step's scope if that ever
  changes.

*** DONE Step 4: ~openUniqDrop()~ per-open caching

~openUniqDrop()~ (~ShowAllEntityData.user.js:45002-47611~) does >=5 full
~tbody.rows~ passes from scratch on every dropdown open with zero caching.
Same caching primitive as Step 3 — build alongside it.

*Landed*: branch ~filter-performance-fix~, see
~ShowAllEntityData_CHANGELOG.wip.json~ WIP.4.

- Reused Step 3's exact primitive: a `WeakMap`-based per-(table, column)
  cache keyed by a signature of the currently visible rows'
  ~data-mb-row-idx~ values, factored out of ~_updateAllColHeaderCounts~'s
  own inline loop into a new shared ~_visibleRowSetSignature(table)~ (both
  it and the equivalent ~_updateAllColHeaderCounts~ change now call the
  same function, rather than duplicating the loop).
- All 5 of the function's ~tbody.rows~ passes (the big value-scan loop, the
  flag-icon segment map, the relationship-cell detector, the relationship
  icon counts, and the inline-CAA/EAA-thumbnail scan) are gated behind a
  single cache-hit check computed once at the top of the function. Deliberately
  did NOT restructure the ~40+ Maps/counters into a bundled accumulator
  object or move any code — each declaration's default value became a
  `_uniqCacheHit ? _uniqCacheHit.name : <original initial value>` ternary
  in place, and each scan loop got an `if (!_uniqCacheHit)` guard around its
  existing body, unchanged. This kept the diff to declaration lines and loop
  guards only, with zero changes to the hundreds of `.set()`/`.get()`/`++`
  call sites inside the loop bodies.
- Correctness hazard found and fixed while implementing, same shape as
  Step 3's release-events case but with a different root cause here: the
  "Cell structure" section's collapsed/expanded split
  (~multiRowCollapsedCount~/~multiRowExpandedCount~) is read from
  ~expandedCells~ (a Map of individually toggled cells), NOT re-derived from
  the visible-row signature — so a single cell's expand/collapse click
  changes these counts WITHOUT changing which rows are visible, and would
  otherwise leave a re-opened dropdown showing a stale split forever (until
  some unrelated filter/sort happened to invalidate it). Fixed by adding
  ~_invalidateUniqDropDataCache(table, colIndex)~ and calling it at all 5
  places ~expandedCells~ is mutated by user interaction: both branches of
  ~_applyCollapseState()~ (header/global-button-driven toggles) and all 3
  branches of ~ensureCollapseDelegate()~'s own inline per-cell click
  handling (CAA/EAA inline expand, prose clamp toggle, list-cell toggle). A
  6th mutation site (~initCollapsableColumns~'s one-time "start expanded by
  default" pre-population for Edit details/notes columns) was checked and
  needs no invalidation call — it only ever runs on the first pass over a
  column for a given fetch, before any dropdown cache for that render could
  exist.

**** Fix: batch the IntersectionObserver callback across animation frames

Reported symptom (large ~series/events~ page, 800 rows, ~sa_caa_io_threshold~
default 500 so lazy-loading is active): dragging the scrollbar quickly to a
distant part of the table showed only the header row — the already-rendered
~<tr>~ content stayed blank/unpainted for a noticeable moment before
appearing all at once. Not a row-data problem (all rows are fully built at
initial render, same as before Step 5) — a scroll-jank/checkerboard symptom:
the browser had already-painted-content-eligible DOM but couldn't composite
it because the main thread was busy.

Root cause: a fast scrollbar-drag jump brings dozens/hundreds of
previously-off-screen icons within the observer's 200px root margin at once,
and the callback's ~entries.forEach~ ran the whole batch's ~unobserve~ +
~enqueue~ calls synchronously in a single task, right as the browser needed
the main thread free to paint the just-scrolled-to rows. Before Step 5, all
of this work happened once at initial render, before the user had started
interacting — Step 5 moved it to run exactly when the user scrolls, which is
what turned it into a visible stall.

Fix: new ~_artProcessIoEntriesBatched()~ splits the callback's intersecting
entries into ~_ART_IO_BATCH_SIZE~ (20) -sized chunks and processes one chunk
per ~requestAnimationFrame~ instead of the whole batch in one tick.
~_artInitLazyPics~'s observer callback now just delegates to it. Doesn't
change the request-concurrency queues (Step 6) at all — only spreads out the
DOM-mutation cost of *starting* observer-triggered loads/enrichment across
frames, so no single frame does more than 20 icons' worth of
unobserve+enqueue work.

*** DONE Step 6: CAA/EAA request-throughput tuning

Split the single shared ~_caaQueue~ (concurrency 4, ~sa_caa_fetch_concurrency~)
into two independent queues — ~_caaImgQueue~ for image loads and
~_caaMetaQueue~ for ~_artEnrichIcon~'s JSON count-lookup ~fetch()~ calls.
Independent of Steps 1-5 (different dimension of the same CAA/EAA subsystem
Step 5 touches: this fixes *how fast* an already-fired request completes,
not *when* it fires).

Trigger: comparing against ~debug/jesus-coverart.js~ (jesus2099's
~mb_FUNKEY-ILLUSTRATED-RECORDS~, the script this feature was originally
modeled on) — its inline cover-art icons load dramatically faster and never
seem to hit the Cover Art Archive's request limit, despite firing every
request completely unthrottled.

*Landed*: branch ~filter-performance-fix-caa-throughput~ (branched from
~filter-performance-fix~, not ~main~ — Step 5's ~IntersectionObserver~/
~_caaQueue~ code only exists on ~filter-performance-fix~), see
~ShowAllEntityData_CHANGELOG.wip.json~ ~WIP.6~.

- Root cause: jesus2099's script never needs manual throttling because
  neither of its request kinds is actually CORS-bound — native
  ~<img src>~ loads are never subject to CORS (CORS only gates script code
  *reading* response bytes via ~fetch()~/XHR/canvas, not the browser
  displaying an image), and its RG-count lookups are unthrottled ~XHR~ calls
  that simply never got flagged in practice. Our own two CAA/EAA request
  kinds have asymmetric CORS exposure: ~_artLoadIcon~'s image loads (IDB
  path via ~GM_xmlhttpRequest~, which explicitly bypasses CORS; native
  fallback via plain ~<img src>~) are equally CORS-free, but
  ~_artEnrichIcon~'s JSON count lookups use a page-context ~fetch()~, which
  *is* subject to CORS. Both kinds were nonetheless sharing one 4-slot
  queue, so on any table with more than a handful of rows nearly everything
  serialized behind a cap that was only ever necessary for the JSON path.
- New settings ~sa_caa_img_concurrency~ (default 12, was 4) and
  ~sa_caa_meta_concurrency~ (default 6) replace ~sa_caa_fetch_concurrency~.
  ~_artInitQueue()~ now creates/cancels both queues every render pass; a new
  ~_caaQueuesOnIdle()~ helper fires the completion toast once both queues
  (not one shared queue) have drained.
- All 10 former ~_caaQueue.enqueue()~ call sites were reclassified by what
  they enqueue: 8 image-load sites (~ergInjectCaaInlineThumbnails~,
  ~_artLoadIcon~'s retry handler, ~_artInitLazyPics~'s icon branch,
  ~_artInitSmallPics~, ~_loadBigImgIdb~/~_loadBigImg~, the inline-pics
  refetch task, ~init{CAA,EAA}InlinePics~'s ~loadTask~) now enqueue on
  ~_caaImgQueue~; the 2 ~_artEnrichIcon~ sites (~_artInitLazyPics~'s
  enrichment branch, ~_artEnrichTable~) now enqueue on ~_caaMetaQueue~.
- No change to *when* requests fire — Step 5's ~sa_caa_io_threshold~/
  ~IntersectionObserver~ lazy-loading is untouched; only how many of each
  request kind can run concurrently changed.

*** TODO Step 7: Decouple IDB caching from the icon-render hot path

Found alongside Step 6 but deliberately not implemented there — bigger risk
profile (changes ~_artLoadIcon~'s IDB-path/native-fallback branching and the
cache-hint telemetry semantics), so it gets its own independently-verifiable
step, same pattern as every prior step in this file.

Today, when IDB caching is enabled (~sa_art_idb_enable~, the default) and an
icon is a cache miss, ~_artLoadIcon~ gates the *visible* render on a full
~GM_xmlhttpRequest → Blob → URL.createObjectURL~ round-trip before the
background-image is ever assigned — jesus2099's script, by contrast, just
assigns ~img.src~ to the plain URL immediately and lets the browser's own
(streaming, off-main-thread-decoding) image pipeline take over, which is a
meaningful part of why it *feels* faster even independent of Step 6's
concurrency fix.

Proposed approach: assign the plain remote URL immediately for display (no
~GM_xmlhttpRequest~, no blob, minimal/no queue wait) — matching jesus2099's
~<img src>~ exactly — then, in the background and without blocking the
visible render, fetch the same URL via ~GM_xmlhttpRequest~ and write the
blob into IndexedDB purely so a *future* page load (or "Load from Disk")
can skip the network. IDB becomes a background accelerator for next-session
speed rather than something the current page's first paint waits on. Needs
its own before/after telemetry check on the cache-hint reporting (a
cold-cache load would report as "browser" instead of "network" even with
IDB enabled, since the blob fetch would no longer be what puts pixels on
screen).

*** TODO Step 8: ~content-visibility: auto~ for off-screen rows

Trigger: on tables whose rows carry inline flag imagery from the "More
Flags Everywhere"/"Canadian Province Flags Everywhere" companion userscripts
(custom/subdivision-level flags, e.g. a venue's city rendered as its own
icon — see ~debug/flags-rendering.html~), a fast scrollbar-drag shows the
sticky column (entity name) painting immediately while the rest of the row
stays blank for a noticeable moment. Confirmed NOT the same mechanism as
Step 5's fix (that's the "Location"/area column's flags, an entirely
different column and a different, third-party-injected DOM subtree — CAA/EAA's
~IntersectionObserver~ never touches it) and NOT a regression from this
branch: ~debug/flags-rendering.html~'s single sampled ~<td>~ is 305KB,
carrying two inline ~data:image/svg+xml;base64,…~ images (~84KB and ~221KB
of base64 text — up to ~230KB of raw SVG vector art combined) for one row's
venue location. A single-table render has always fully materialized every
row's DOM at once (true on unmodified ~main~ too, long before Steps 1-6) —
what's new here is just that this particular kind of page makes that
already-large DOM dramatically larger per row.

Mechanism (browser compositing, not our JS): ~applyStickyColumn~ sets
~position: sticky~ on the sticky column's cells, which Chromium typically
promotes to its own compositor layer — a thin, text-only layer that paints
independently and cheaply. The rest of a flag-heavy row sits in the table's
main content layer alongside hundreds of KB of embedded vector art; that
layer's raster tile takes real, measurable time to decode/paint the first
time it scrolls into view. A fast scrollbar-drag jump exposes a large batch
of never-yet-rasterized rows in one step, so the (already fully built,
already in the DOM) main-layer content stays visually blank until the raster
catches up — while the sticky layer, having nothing expensive to paint,
shows immediately.

Goal: stop the browser from doing ANY layout/paint work for rows that are
nowhere near the viewport, so a fast scroll never has a large batch of
never-yet-rasterized heavy rows to catch up on — a fix at the actual
mechanism (browser rendering), not a workaround in our JS (there is no
practical way to "lazy load" a ~data:~ URI's decode cost the way Step 5
lazy-loads a network request — the bytes are already inline in the DOM;
the only lever is whether the browser bothers to lay out/paint them yet).

**** Proposed approach

~content-visibility: auto~ + ~contain-intrinsic-size: auto <estimate>px~ on
every ~<tr>~ in ~table.tbl tbody~ (single-table mode first, matching every
prior step's scoping precedent). Semantics that matter for this codebase
specifically:

- While a ~<tr>~ is off-screen (outside an internal "near viewport" margin,
  conceptually similar to ~IntersectionObserver~), the browser skips layout,
  style recalc for layout purposes, paint, and hit-testing for its entire
  subtree — but does NOT remove or hide the DOM. ~textContent~, attributes,
  ~querySelectorAll~, ~cloneNode~, and non-geometric ~getComputedStyle~
  reads (colours, etc.) all keep working normally on a skipped row.
- What DOES break: any read of *layout geometry* on a skipped row or its
  descendants — ~getBoundingClientRect()~, ~offsetWidth~/~offsetHeight~,
  ~scrollWidth~/~scrollHeight~, ~clientWidth~/~clientHeight~ — reports
  placeholder/zero values while skipped, not the row's real laid-out size.
- ~contain-intrinsic-size~ is the row's OWN placeholder height (so total
  ~scrollHeight~/scrollbar-thumb size stay stable while rows skip in and
  out) — it does not, by itself, fix geometry reads on a skipped row's
  *descendants*, which is the actual audit concern below.

**** Browser support

Chromium ~85+ and Firefox 125+; not yet in Safari as of this writing. Needs

behaviour needed since it's purely a rendering hint with no functional
dependency elsewhere in the script.
