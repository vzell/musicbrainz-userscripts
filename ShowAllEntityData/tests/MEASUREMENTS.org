#+TITLE: Measurement log
#+STARTUP: showall

Every timing, wall clock and count this project has measured, with the machine
it was measured on.

*Why this file exists.* Timings were previously scattered across
=PERFORMANCE.org=, =DEBUG-NOTES.md=, commit messages and the
=interaction-perf-*.json= arms, and none of them recorded the HOST. That gap
cost real work: two =main= captures three script versions apart came out 1.5-2x
different, and because nothing said which machine either ran on, the difference
was attributed first to machine state and then to concurrent load — both
guesses, and the second was disproved. A number with no machine attached cannot
be compared to a later one, so it is not evidence, it is decoration.

*Rules for adding a row.*

- *Record the hostname AND the time*, from the run itself and not from memory.
  =capture-interaction-perf.js= and =capture-snapshots.js= write a =machine=
  block plus =startedAt=/=finishedAt= (UTC) into their JSON; copy from there.
  The time is not ceremony — "was MusicBrainz busy at that hour" is a real
  hypothesis about any live-page number, and it can only be tested against runs
  that recorded when they happened. It has been tested once, below, and came
  back negative; that answer is only available because the times were
  recoverable from commit timestamps.
- *Say what the measurement was PROBING*, not just which command produced it.
  "Sort click to settled status text" is a measurement; "sort" is a label.
- *Name the page*: pageType, its =tableMode= (single/multi) and its human page
  title, the same four columns =tests/snapshots/registry.org= uses. A bare URL
  or a bare =rendered.html= is unreadable a month later.
- *Mark an unknown host as unknown.* Do not infer it. Rows below that predate
  machine recording say so, and one of them is known to be from a DIFFERENT
  machine.

** What each metric probes

| Metric                | What it measures                                                                                       |
|-----------------------+--------------------------------------------------------------------------------------------------------|
| =globalFilter=        | Typing "United Kingdom" into the page-wide filter until =#mb-filter-status-display= settles            |
| =columnFilter=        | The same, typed into the Country column's own filter input                                             |
| =sort=                | One sort-icon click until =#mb-sort-status-display= settles                                            |
| =uniqDropCold=        | First 📊 open on the Location column — five full =tbody.rows= passes, nothing cached                   |
| =uniqDropWarm=        | Re-opening the same dropdown — Step 4's per-open cache, so this is the cache-hit path                  |
| =headerCountsInitial= | Render-complete to the Event badge reading its true 4158 AND every badge holding still                 |
| =headerCountsRestore= | Clearing the "Bon Jovi" column filter to the full 4174 rows, until the badges are back — Step 3's case |

The last two were added 2026-09-07; the five before them see the header-count
scan only as main-thread pressure delaying a CDP poll. Both carry a ~1 s floor
from =waitForColHeaderCountsStable()=, identical on every arm.

*Every filter number in this file is a SINGLE-PASS number* — recorded 2026-09-09,
because it is not obvious from the metric names and it bounds what these rows can
answer. =measureGlobalFilterOnce=/=measureColumnFilterOnce= type via
=input.pressSequentially(value)= with no per-character delay, so all fourteen
characters of "United Kingdom" land within a few ms. =runFilter()= is debounced at
a 300 ms floor (=_adaptiveFilterDelay()=, whose adaptive term is only 184 ms at
4174 rows), so the debounce swallows every keystroke but the last and exactly one
filter pass is timed.

That makes these rows a fair measure of *one pass*, and no measure at all of
progressive typing — where a pause over ~300 ms, and every backspace, starts
another pass. PERFORMANCE.org's "Findings: the per-keystroke filter cost" section
is about the repeated-pass behaviour, and nothing here observes it. A
=--typing-delay= arm would; it is deliberately not built yet, since the steps it
would judge are verifiable by count instead (see that file's Tier 0).

followed by a slow state that lasts one to two days — and both episodes fit it;
the 2026-09-07/08 one is the one a reboot happened to interrupt. Net:

weaker residue form predicts slow by the first sample and back at the floor in
one to two days; if nothing happens, the session is off the list and the
2026-09-10 to 12 window needs a different explanation. That is three days
instead of eighteen, and it puts the trigger under control. During any slow
sample, also capture what differs — =free -m=, =/proc/pressure/{cpu,memory,io}=,

it lasts. The 18-day uptime case is worth running only if that comes back
negative, and with the current harness so that it records its own =machine=

*Caveats on the data itself.*

- *Old harness.* The pinned 9.99.1049 harness writes no =machine= block and no

  medians above were recovered from the branch's 21 capture commits. Start
  times are the cron log's, uptime is =/proc/uptime= as the wrapper read it, and

  the pinned script could not be changed to.
- *Boot 2's logged uptime runs 16.36 h high.* The kernel's first journal line
  is at 2026-09-15 23:15:43 CEST but its monotonic timestamp already reads
  58 899 s (16.36 h) there, and =/proc/uptime=, which the wrapper logs, counts
  from that. Realtime and monotonic then advance together for the whole boot,
  so the offset is constant: it shifts every boot-2 point by the same 16.36 h
  and cannot create or hide a trend, but "logged 24.1 h" was 7.7 h of wall
  clock since the kernel started. Cause not identified. Boot 1 has no such
  offset: its first line is at 0.0 s and its logged uptimes track wall clock
  since boot to within 0.15 h. The current harness reads =os.uptime()=, the same
  source, and derives =claudeSinceBoot= from it, so both would inherit an
  offset like this one; cross-check against =journalctl --list-boots= whenever
  the number decides something.
- *The first sample is not quite like the others.* Per DEBUG-NOTES.md
  2026-09-10 it ran on an uncommitted =playwright ^1.63.0= drift (Chromium
  revision 1243) that was reverted the next day to the committed 1.62.1 (1234).

- *The gate looks twice a day.* A =claude= started and finished between slots
  is invisible to it, which is why the transcripts were checked as well. Its
  process name is still right: =pgrep -x claude= matched this analysis's own

- *n.* Twenty-one medians of five, one host, one page. Enough to see a 1.5-2x

*The two parts cost more than the whole*: 2 m 6 s + 4 m 48 s = 6 m 54 s
against 5 m 18 s for one full run, i.e. splitting is 1 m 36 s WORSE if you
then run both. In a full run the two =@slow= files occupy workers that would
otherwise idle while the 104 short files drain, so their cost is largely
hidden by parallelism. The tag therefore buys nothing for a merge and
everything for iteration, which is exactly how it is wired: =npm test= for
the loop, =npm run test:full= at the merge gate.

Note the corollary for the earlier figure in this file: the suite's jump from
~1 m 50 s (353 tests) to ~5 m 18 s (403 tests) was NOT 50 tests' worth of
work. It was these two files alone — 14 tests that are almost entirely rate
gate and retry backoff.

* 2026-09-20 — cost of a per-table source-row walk (NB-3641)

Taken to decide how often the per-table =⚠⟳= failed-retry counts may be
recomputed. The page-wide count is =ctx.failedCache.size=, an O(1) read, which
is why it can afford a =requestAnimationFrame= for the whole artwork load. A
per-table count has to attribute entity paths to tables, which is a walk.

| host                    | =NB-3641=                                         |
| date (UTC)              | 2026-09-20                                        |
| page                    | =artist-events= disk fixture, =tableMode: single= |
| rows                    | 4174                                              |
| one walk (median of 10) | *~5 ms*                                           |

What the walk is: one =querySelectorAll('a[href$="/cover-art"]')= per source
row. 5 ms is roughly a third of a 60 fps frame budget, sustained for as long as
artwork is loading — so per-frame was rejected. At one walk per second the same
cost is ~0.5% and invisible, which is what
=_ART_FAILED_TBL_REFRESH_MS= (1000) buys.

*Settle-only was rejected for a non-performance reason*: CLAUDE.md records that
=_showCaaCompletionToast()= never fires at all on a large listing, so controls
gated on settle would never appear on exactly the pages with the most failures.

The Relationships half needed no such decision — its refresh was already not
hooked per frame, and partitioning its existing page-wide pass costs the same
total as the pass it replaces.

* 2026-09-21 — cost of making the join-phrase entity boundary structural (vzell-lap)

Taken because =openUniqDrop()= calls =_findCellJoinPhrases()= once per VISIBLE
ROW of the column being opened, and PERFORMANCE.org Step 4 measures a cold
uniq-dropdown open in tens of seconds on a 4174-row page. The fix
(DEBUG-NOTES.md 2026-09-21) stopped requiring a credited =<a>= to be a DIRECT
CHILD of its =<bdi>= — MusicBrainz's own =<span class="mp">= open-edits wrapper
broke that assumption and hid a whole join phrase — trading a =childNodes= scan
for one =querySelectorAll= per =<bdi>= plus a =closest()= per anchor. The
question was whether that is a visible part of the dropdown's cost or noise
inside it.

The cells reproduce the four shapes in
=tests/fixtures/uniq-drop-join-phrases.html= in roughly a real Artist column's
proportion (6 solo : 2 plain pair : 1 =.mp=-wrapped : 1 with per-entity
comments). Both implementations live in the bench script and run over the same
nodes, so the only thing measured is the boundary resolution.

*Read the two numbers together.* +2.5 ms is 15% of this one function's own
cost and is invisible against a cold dropdown open of tens of seconds — and it
is paid to find TWICE AS MANY phrases, because the old shape could not see an
=.mp=-wrapped anchor at all. The old number is not a baseline to defend; it is
the cost of a pass that was silently skipping work.

No PERFORMANCE.org statement changes: Step 4's "computed on open, then memoized
per (table, column, row set)" is untouched, and nothing there quantifies this
function.
