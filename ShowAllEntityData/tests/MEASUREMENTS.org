#+TITLE: Measurement log
#+STARTUP: showall

Every timing, wall clock and count this project has measured, with the machine
it was measured on.

*Why this file exists.* Timings were previously scattered across
=PERFORMANCE.org=, =DEBUG-NOTES.md=, commit messages and the
=interaction-perf-*.json= arms, and none of them recorded the HOST. That gap
cost real work: two =main= captures three script versions apart came out 1.5-2x
different, and because nothing said which machine either ran on, the difference
was attributed first to machine state and then to concurrent load — both
guesses, and the second was disproved. A number with no machine attached cannot
be compared to a later one, so it is not evidence, it is decoration.

*Rules for adding a row.*

- *Record the hostname AND the time*, from the run itself and not from memory.
  =capture-interaction-perf.js= and =capture-snapshots.js= write a =machine=
  block plus =startedAt=/=finishedAt= (UTC) into their JSON; copy from there.
  The time is not ceremony — "was MusicBrainz busy at that hour" is a real
  hypothesis about any live-page number, and it can only be tested against runs
  that recorded when they happened. It has been tested once, below, and came
  back negative; that answer is only available because the times were
  recoverable from commit timestamps.
- *Say what the measurement was PROBING*, not just which command produced it.
  "Sort click to settled status text" is a measurement; "sort" is a label.
- *Name the page*: pageType, its =tableMode= (single/multi) and its human page
  title, the same four columns =tests/snapshots/registry.org= uses. A bare URL
  or a bare =rendered.html= is unreadable a month later.
- *Mark an unknown host as unknown.* Do not infer it. Rows below that predate
  machine recording say so, and one of them is known to be from a DIFFERENT
  machine.

* Bisect: the 9.99.1045 -> 9.99.1048 gap

*Question*: is =main= genuinely ~1.5-2x slower at 9.99.1048 than at 9.99.1045,
or was the older arm measured in a different environment?

*Answer: the environment. The script is not the cause.* Both endpoints
re-measured on =petri= on 2026-09-08, same session, same harness, machine idle:

| Script    | Commit    | What it contains                                               | global | column |  sort | uniq cold | hdr restore |
|-----------+-----------+----------------------------------------------------------------+--------+--------+-------+-----------+-------------|
| 9.99.1045 | =1983985= | before the CAA/EAA dropdown + sort fixes that became 1046/1047 |   3117 |   3285 |  6044 |     42948 |       11175 |
| 9.99.1048 | =2db4497= | after them, plus the doc renames                               |   3033 |   3295 |  6410 |     45996 |       12319 |
| Δ         |           |                                                                |  -2.7% |  +0.3% | +6.1% |     +7.1% |      +10.2% |

Every delta sits inside the noise band. The SAME 9.99.1045 script measured 1735
/ 1730 / 3968 / 31149 / 863 in the 2026-09-07 arm — roughly half — so the ~2x is
carried entirely by the environment, and 9.99.1046-1047 are exonerated.

*Time of day does not explain it either.* MusicBrainz being busier at some hours
is a natural hypothesis — every sample fetches its page shell from the live site
— but the timestamps do not support it:

| When                           |    Script | global filter | Note                                              |
|--------------------------------+-----------+---------------+---------------------------------------------------|
| 2026-09-07, <= 11:41 (morning) | 9.99.1045 |          1735 | the fast arm                                      |
| 2026-09-07, 18:58-19:56 (eve)  | 9.99.1048 |    3757..3669 | ~2x slower, same day                              |
| 2026-09-08, 08:11-08:27 (morn) | 9.99.1048 |    3033..3168 | still slow, next morning                          |
| 2026-09-08, 17:01 (evening)    | 9.99.1045 |          3117 | slow, and this is the SAME script as the fast arm |

Two things follow. Within a day the spread is small — 3033/3168/3117 across nine
hours on 2026-09-08, about 4% — so the hour is not the variable. And the change
is a persistent STEP during 2026-09-07, somewhere between 11:41 and 18:58, that
never recovered overnight; diurnal load would have. There is also no obvious
mechanism: every measurement bracket starts AFTER its page has loaded, so
MusicBrainz's own response time is outside all seven numbers.

Something on this machine changed that afternoon and stayed changed. What,
specifically, cannot be recovered — the older arm recorded neither host nor
time, which is the whole reason both are now written into the JSON.

* Cost model — the column-header count scan

The number PERFORMANCE.org Step 3 exists to attack, recorded here because it
otherwise lives only in the userscript's own comments.

| Quantity                                   | Value                            | Source                                       |
|--------------------------------------------+----------------------------------+----------------------------------------------|

| Synchronous cost at 8 k+ rows              | 30-120 s                         | =_updateAllColHeaderCounts()='s own comments |

At that size the pass was enough to trigger Chrome's "Page Unresponsive"
dialog, which is why it is deferred behind =_scheduleColHeaderCounts()= and
sliced one event-loop turn per column rather than fixed at the root. Step 3

| Service                    | Limit                                                      | How it was established                                      |
|----------------------------+------------------------------------------------------------+-------------------------------------------------------------|

The last row is why the millisecond-length feature uses the SEARCH endpoint and

page shows ten rows or ten thousand, and cannot serve instrument/isrc/search at
all. Search costs =ceil(rendered rows / 100)=.

The toast these poll is written on the queue's =onIdle=; at the archive's
~1.2 req/s a per-entity metadata sweep of that size simply outlasts any sane
timeout. Poll the thing you care about until it stops changing instead —
=caa-icon-survives-sort-multi.spec.js='s =waitForArtworkSettled()= is the worked
example.

*Consequence worth knowing before blaming a change*:
=releasegroup-releases-filter-sort.spec.js= still waits on both toasts in
=setupExpandedGreetingsPage()=, so all six of its tests fail in setup on that
page regardless of the code under test. A "toast never appeared" timeout is
evidence about the page's size, never about your change.

*Known intermittent, not load-explained*: =release-tracks-ms-length-overflow.spec.js='s
"a row already stamped by the embedded payload is never re-sent to the network"
has failed three times under the parallel =npm test= run and passed every time
in isolation (3.2-4.0 s against a 30 s budget), on both =main= and a feature
branch. Unlike the =pending-edits-filter= five, an idle machine does not make it
go away — it just makes it rarer. Re-run the file alone before believing it
caught anything; if it starts reproducing, that is new information worth a look.

That outage is what prompted =capture-interaction-perf.js='s per-sample retry,
and it exposed a documentation error worth keeping visible: =loadFromDiskFixture()=
is *not* offline. It makes the table DATA deterministic, but passes no
=fixtureFile= to =loadUserscriptPage()=, so no route is registered and the page
SHELL is fetched from the live site. "No network" only ever described the data.
