#+TITLE: Measurement log
#+STARTUP: showall

Every timing, wall clock and count this project has measured, with the machine
it was measured on.

*Why this file exists.* Timings were previously scattered across
=PERFORMANCE.org=, =DEBUG-NOTES.md=, commit messages and the
=interaction-perf-*.json= arms, and none of them recorded the HOST. That gap
cost real work: two =main= captures three script versions apart came out 1.5-2x
different, and because nothing said which machine either ran on, the difference
was attributed first to machine state and then to concurrent load — both
guesses, and the second was disproved. A number with no machine attached cannot
be compared to a later one, so it is not evidence, it is decoration.

*Rules for adding a row.*

- *Record the hostname AND the time*, from the run itself and not from memory.
  =capture-interaction-perf.js= and =capture-snapshots.js= write a =machine=
  block plus =startedAt=/=finishedAt= (UTC) into their JSON; copy from there.
  The time is not ceremony — "was MusicBrainz busy at that hour" is a real
  hypothesis about any live-page number, and it can only be tested against runs
  that recorded when they happened. It has been tested once, below, and came
  back negative; that answer is only available because the times were
  recoverable from commit timestamps.
- *Say what the measurement was PROBING*, not just which command produced it.
  "Sort click to settled status text" is a measurement; "sort" is a label.
- *Name the page*: pageType, its =tableMode= (single/multi) and its human page
  title, the same four columns =tests/snapshots/registry.org= uses. A bare URL
  or a bare =rendered.html= is unreadable a month later.
- *Mark an unknown host as unknown.* Do not infer it. Rows below that predate
  machine recording say so, and one of them is known to be from a DIFFERENT
  machine.

** What each metric probes

| Metric                | What it measures                                                                                       |
|-----------------------+--------------------------------------------------------------------------------------------------------|
| =globalFilter=        | Typing "United Kingdom" into the page-wide filter until =#mb-filter-status-display= settles            |
| =columnFilter=        | The same, typed into the Country column's own filter input                                             |
| =sort=                | One sort-icon click until =#mb-sort-status-display= settles                                            |
| =uniqDropCold=        | First 📊 open on the Location column — five full =tbody.rows= passes, nothing cached                    |
| =uniqDropWarm=        | Re-opening the same dropdown — Step 4's per-open cache, so this is the cache-hit path                  |
| =headerCountsInitial= | Render-complete to the Event badge reading its true 4158 AND every badge holding still                 |
| =headerCountsRestore= | Clearing the "Bon Jovi" column filter to the full 4174 rows, until the badges are back — Step 3's case |

The last two were added 2026-09-07; the five before them see the header-count
scan only as main-thread pressure delaying a CDP poll. Both carry a ~1 s floor
from =waitForColHeaderCountsStable()=, identical on every arm.

*Every filter number in this file is a SINGLE-PASS number* — recorded 2026-09-09,
because it is not obvious from the metric names and it bounds what these rows can
answer. =measureGlobalFilterOnce=/=measureColumnFilterOnce= type via
=input.pressSequentially(value)= with no per-character delay, so all fourteen
characters of "United Kingdom" land within a few ms. =runFilter()= is debounced at
a 300 ms floor (=_adaptiveFilterDelay()=, whose adaptive term is only 184 ms at
4174 rows), so the debounce swallows every keystroke but the last and exactly one
filter pass is timed.

That makes these rows a fair measure of *one pass*, and no measure at all of
progressive typing — where a pause over ~300 ms, and every backspace, starts
another pass. PERFORMANCE.org's "Findings: the per-keystroke filter cost" section
is about the repeated-pass behaviour, and nothing here observes it. A
=--typing-delay= arm would; it is deliberately not built yet, since the steps it
would judge are verifiable by count instead (see that file's Tier 0).

MusicBrainz's own response time is outside all seven numbers.

Something on this machine changed that afternoon and stayed changed. What,
specifically, cannot be recovered — the older arm recorded neither host nor
time, which is the whole reason both are now written into the JSON.
