* Expected drift — read this before treating a re-capture diff as a regression

These baselines are captured against the LIVE musicbrainz.org, so some of what
they record is MusicBrainz's data rather than this script's behaviour. A diff in
one of the following is upstream movement, not a defect:

** ⏳ pending edits (~7-day review window)

MusicBrainz marks an entity whose /open_edits list is non-empty with its own
=<span class="mp">=. That state expires: edits enter a voting period of about a
week and the marker disappears once they are applied or rejected. The script
reads that marker for the 📊 "Pending edits" dropdown sections and the ⏳
filter-bar toggle (9.99.1024/9.99.1026), so the marker's presence is baked into
whatever was pending on capture day.

As captured on 2026-09-06, exactly two baselines carry it, one marker each, with
=#mb-pending-edits-btn= serialized =display: inline-block=:

  - artist-events/rendered.html
  - artist-releasegroups/rendered.html

When those edits close, a re-capture will drop the =mp= span and flip that
button to =display: none=. **That is the correct new baseline — commit it.** The
button is created unconditionally and merely hidden when a page has nothing
pending, so it never disappears from the DOM entirely; if it vanishes outright,
THAT is a real regression.

Not affected, and worth knowing so the diff is not over-read:

  - artist-events/post-filter.html and post-sort.html also contain =mp= markers
    (3 each), but they are generated from the frozen disk fixture
    tests/fixtures/saved-data/artist-events.json.gz, so they reproduce
    byte-identically and must NOT change. A diff there IS a script change.
  - Every pending-edits TEST runs against committed static fixtures
    (pending-edits-multi.html, uniq-drop-pending-edits.html,
    entity-refs-mp-wrapper.html) with hand-written markers, and nothing in
    `npm test` reads a snapshot baseline at all. The review window expiring can
    never turn the suite red.

** Column-header count badges filling in

Unlike everything else in this section, this one is OUR movement, not
MusicBrainz's — recorded here because a re-capture makes it look like a large,
alarming diff spread across every =<thead>=.

The =.mb-col-uniq-count= badges are written by =_updateAllColHeaderCounts()=,
which used to abandon itself on multi-table pages: one module-level coalescing
token, one schedule per sub-table, so every sub-table but the last cancelled
before writing anything (PERFORMANCE.org Step 22). What the current baselines
therefore record is mostly EMPTY badges:

| Baseline                            | uniq badges | before | after |
|-------------------------------------+-------------+--------+-------|
| artist-releasegroups/rendered.html  |         423 |      1 |   286 |
| releasegroup-releases/rendered.html |          42 |     14 |    32 |

Both were re-captured on 2026-09-08 and those are the committed numbers now.
Badges going the other way, from populated to empty, is a real regression.

*"After" is not the full 423, and that is correct*: =_updateAllColHeaderCounts()=
writes an empty badge when a column has no distinct values to count
(=textContent = n > 0 ? String(n) : ''=). What Step 22 fixed is entire
sub-tables reading empty — artist-releasegroups went from 46 of its 47 tables
having nothing at all to every one of them populated, a steady 6 of 9 columns
each.

Two things had to change before a re-capture could show any of this:
=captureOne()= now waits on =waitForColHeaderCountsStable()= before snapshotting
(it previously took the snapshot straight after =waitForRenderComplete()=, which
is why =artist-events/rendered.html= records 1 of 21 despite that page having a
single table and no cancellation problem at all — its scan was simply still
running). The wait is non-fatal: a page whose scan outlasts 180 s is captured
anyway, with a warning naming how many badges are still empty.

Expect unrelated drift in the same re-capture, already seen in this one: the
=td[data-mb-len-flag]= tint rules gained =!important= and an explanatory comment
on =main= long after the 9.99.953 baseline, and the Wikipedia extract flapped
per the section below.

*** Do not count this with =grep -o= — the injected stylesheet is in the file

  - =scripts/summarize-snapshot-diff.py <pageType>…= — the committed-vs-working

  - =scripts/which-column-has-class.py= — which COLUMN (header name and index)

    which column it is decides whether the diff is yours.

  - =.mb-uniq-rel-collapsed-note=

*That is style-block text — but see the correction below, because it is NOT the
whole drift.* No ELEMENT in any current baseline gains an attribute or a class
from this change, and that much is checked rather than assumed:

  - Every rel-carrying entry in =tests/pagetypes.json= seeds
    =sa_enable_relationships_column: false=, so no baseline has a
    =td.mb-rel-cell= at all — the 9 =mb-rel-cell= hits already in each file are
